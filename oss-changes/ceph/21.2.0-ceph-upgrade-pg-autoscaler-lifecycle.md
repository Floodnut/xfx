## 개요

Ceph의 cephadm은 OSD를 포함하는 업그레이드를 시작할 때 기본적으로 PG autoscaling을 억제하고, 업그레이드가 끝나거나 명시적으로 중단되면 저장한 상태를 기준으로 복원하는 경로를 추가했다. 운영자가 별도로 맞추던 업그레이드와 PG 수 조정의 시점을 하나의 수명주기 안에서 관리하려는 변경이다. 다만 저장하는 정보는 클러스터의 `noautoscale` 플래그 상태이며, 모든 관련 설정의 원본을 보존하는 트랜잭션은 아니다. 또한 `pg_autoscale_during_upgrade=true`는 자동 억제를 건너뛰는 옵션으로, 이미 꺼진 autoscaling을 켜는 동작은 구현되어 있지 않다. [PR diff](https://github.com/ceph/ceph/pull/67694/files)

## 사전 지식

### OSD 교체와 PG 수 조정은 서로 다른 작업

Ceph의 OSD는 데이터를 저장하는 데몬이다. cephadm의 업그레이드는 새 버전의 데몬으로 순차 교체하는 작업이며, `upgrade_start()`가 대상과 진행 상태를 만들고 이후 진행 경로가 이를 이어간다. 대상은 전체 데몬일 수도 있고 데몬 유형, 서비스, 호스트로 제한될 수도 있다. 이 상태는 manager의 저장소에 직렬화되므로 단일 함수 호출이 끝난 뒤에도 유지된다. [기존 업그레이드 코드](https://github.com/ceph/ceph/blob/5bc17c8c3186dd8686b1a86398d68e9b569963e6/src/pybind/mgr/cephadm/upgrade.py)

PG(placement group)는 풀의 객체 배치를 묶어 관리하는 단위다. PG autoscaler는 필요한 PG 수를 조정하는 별도 기능이다. 데몬 교체 중에도 PG 수가 바뀌면 업그레이드 진행과 데이터 배치 조정이 겹칠 수 있다. 기존 업그레이드 안내는 이 중첩을 피하도록 운영자가 업그레이드 전후에 autoscaling을 수동으로 억제하고 해제하는 절차를 제시했다. 이번 변경은 그 절차의 실행 주체를 cephadm 안으로 옮긴다. 구현상의 출발점은 PR에서 `upgrade_start()`에 새 제어 분기를 추가한 부분이다. [변경 diff](https://github.com/ceph/ceph/pull/67694/files)

### 구분해야 할 세 가지 설정

| 설정 | 이 변경에서의 역할 |
| --- | --- |
| OSDMap의 전역 `noautoscale` 플래그 | 현재 클러스터의 autoscaling 허용 여부를 판정하고 복원할 기준 |
| `osd_pool_default_pg_autoscale_mode` | 새 풀에 적용되는 기본 모드. 억제 과정에서 `off`로 쓰고 복원 과정에서 `on`/`off`로 재설정하는 값 |
| `mgr/cephadm/pg_autoscale_during_upgrade` | 업그레이드 시작 시 자동 억제를 수행할지 결정하는 옵션, 기본값 `false` |

기존 풀 각각의 autoscale 모드와 새 풀의 기본 모드는 같은 값이 아니다. 특히 전역 플래그를 읽어서 얻은 허용 여부 하나로 기존 기본 모드까지 정확하게 복원할 수는 없다. 이 차이는 뒤의 복원 한계를 이해하는 데 중요하다. [옵션 정의](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/module.py#L435), [설정/복원 구현](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L1165)

## 변경 분석

### 변경 전: 두 작업의 조정을 운영자가 담당

PR 이전의 업그레이드 상태에는 `noautoscale_set`과 `prior_autoscale` 필드가 없었다. 업그레이드를 시작하거나 종료하는 경로에도 이번 변경의 PG autoscaler 제어 호출이 없었다. 따라서 업그레이드 자체의 진행 상태와 운영자가 적용한 autoscaling 억제 상태가 별도로 관리됐다. 수동 억제를 생략하면 업그레이드와 autoscaling이 겹칠 수 있고, 해제를 놓치면 업그레이드가 끝난 뒤에도 억제가 남는다. 이 두 경우는 코드 구조에서 도출한 가능성이며, 이번 조사에서 발생 빈도를 측정한 결과는 아니다. [기준 코드](https://github.com/ceph/ceph/blob/5bc17c8c3186dd8686b1a86398d68e9b569963e6/src/pybind/mgr/cephadm/upgrade.py), [추가된 필드와 호출](https://github.com/ceph/ceph/pull/67694/files)

direction: down

  - id: operator
    label: 운영자의 업그레이드 준비
  - id: manual

  - id: upgrade

### 시작 시 결정하고, 수행한 변경을 상태에 기록

새 `upgrade_start()`는 먼저 `_upgrade_includes_osds()`로 대상에 OSD가 포함되는지 판단한다. 데몬 유형 필터가 있으면 그 목록을, 없으면 서비스나 호스트 범위를 확인하며, 필터가 없으면 전체 업그레이드로 취급한다. OSD가 제외된 작업은 이 PG 제어 경로를 타지 않는다. [범위 판정과 시작 경로](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py)

OSD가 포함되면 현재 OSDMap의 `noautoscale` 존재 여부를 읽는다. 기본 옵션에서는 `_set_noautoscale()`가 새 풀 기본 모드를 `off`로 쓰고 전역 `noautoscale` 플래그를 설정한다. 두 명령이 성공해야 `noautoscale_set=true`와 기존 허용 여부인 `prior_autoscale`을 업그레이드 상태에 기록한다. 이 두 필드는 `to_json()`에도 추가되어 후속 실행이 복원 필요 여부를 알 수 있다. [시작 시 결정](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L751), [상태 직렬화](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L256)

### 옵션 이름보다 실제 분기가 좁은 동작

`pg_autoscale_during_upgrade=true`이면 시작 경로가 억제 함수를 호출하지 않는다. 이 분기에는 기존 `noautoscale`을 해제하는 명령이 없다. 따라서 PR 설명의 결정표에서 제시한 기존 off 상태의 강제 활성화와 실제 코드가 다르다. 구현 기준의 동작은 다음과 같다. [PR head의 시작 코드](https://github.com/ceph/ceph/blob/da4b361e63c1563a7d13deaceeb25205b162aafe/src/pybind/mgr/cephadm/upgrade.py), [추가 테스트](https://github.com/ceph/ceph/blob/da4b361e63c1563a7d13deaceeb25205b162aafe/src/pybind/mgr/cephadm/tests/test_upgrade.py)

| 시작 전 전역 플래그 | 옵션 | 시작 시 코드 동작 |
| --- | --- | --- |
| 해제, autoscaling 허용 | `false` | 억제 설정 후 복원 상태 기록 |
| 설정, autoscaling 억제 | `false` | 억제 설정 후 기존 억제 상태 기록 |
| 해제, autoscaling 허용 | `true` | 변경 없음 |
| 설정, autoscaling 억제 | `true` | 변경 없음, 억제 유지 |

## 설계 결정 및 트레이드오프

### 종료와 일시정지를 구분한 복원

`upgrade_stop()`과 `_mark_upgrade_complete()`는 `noautoscale_set`이 참일 때 복원 함수를 호출한다. 반면 오류를 처리하는 `_fail_upgrade()`는 작업을 일시정지 상태로 저장하고 억제를 유지한다. 재개할 업그레이드에서 autoscaling을 먼저 풀지 않기 위한 구분이 코드 주석에 명시되어 있다. 따라서 옵션 설명에 있는 failure라는 단어만 보고 모든 실패에서 즉시 복원된다고 해석하면 안 된다. [중단 경로](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L895), [실패 일시정지](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L1256), [완료 경로](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L2060)

### 수명주기 자동화의 범위와 한계

기존 수동 절차를 유지하면 운영자가 업그레이드와 플래그를 맞춰야 한다. 이번 구현은 작업 상태에 복원 정보를 넣어 그 부담을 줄이는 대신, 업그레이드 시작 경로가 클러스터 전역 설정을 수정하도록 만든다. OSD 범위를 확인하고 옵션으로 억제를 건너뛰게 한 것은 이 개입의 범위를 제한하는 선택이다. 별도 설계 문서에서 대안을 비교한 기록은 확인하지 못했으며, 다음 한계는 실제 코드에서 확인한 것이다. [구현 diff](https://github.com/ceph/ceph/pull/67694/files)

- **전역 플래그 기준 복원**: `prior_autoscale`만 보존하므로 원래의 `osd_pool_default_pg_autoscale_mode=warn` 같은 값을 그대로 복구하지 못하는 구조
- **두 명령의 비원자적 적용**: 기본 모드를 `off`로 쓴 다음 플래그 설정에 실패하면 부분 적용 경고와 `False` 반환, 복원 표식은 기록되지 않는 경로
- **복원 실패의 제한적 처리**: 세 번까지 복원을 시도한 뒤 경고를 남기고 반환, 완료 경로는 이후 복원 표식을 해제하므로 복원 성공을 강제하는 완료 조건은 아닌 구조

이 변경은 모든 설정을 원상복구하는 일반적인 트랜잭션이 아니라, 정상적인 업그레이드 수명주기에서 PG autoscaling 제어를 자동으로 연결하는 구현으로 이해해야 한다. 원래 설정 전체를 저장하는 방식이나 설정 실패 시 업그레이드를 시작하지 않는 방식은 비교 가능한 대안이지만, 이 PR에 구현되거나 채택된 것으로 확인되지는 않았다. [설정/복원 함수](https://github.com/ceph/ceph/blob/0719e29cb2efc4c4c36b8f67909371d26c1bdcb7/src/pybind/mgr/cephadm/upgrade.py#L1173)

## 더 살펴볼 점

1. 원래 새 풀 기본 모드가 `warn`인 경우까지 보존하려면 업그레이드 상태에 어떤 정보를 추가해야 할까?
2. 플래그 설정이나 복원이 실패했을 때 현재의 로그 경고만으로 운영자가 부분 적용 상태를 식별할 수 있을까?
3. 업그레이드 도중 운영자가 전역 플래그를 변경하면 종료 시 복원과 어떤 우선순위로 조정해야 할까?
