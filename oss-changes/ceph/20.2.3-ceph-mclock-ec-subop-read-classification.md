## 개요

Ceph의 mClock I/O 스케줄러에서 Erasure Coding(EC) SubOp 읽기가 출처에 관계없이 모두 **immediate** 큐로 분류되어 스케줄러를 우회하던 문제를 수정했다. 복구/백필 작업에서 발생한 EC SubOp 읽기가 클라이언트 I/O와 동일한 우선순위로 대량 처리되면서, 2,000개 이상 OSD 규모의 EC 클러스터에서 OSD 드레인 시 30초 이상의 slow op이 발생했다. 이 변경은 메시지의 priority 필드를 기준으로 복구 출처의 SubOp 읽기를 `background_recovery` 또는 `background_best_effort` 클래스로 분류하고, 프로파일 파라미터를 조정해 `background_best_effort`에 최소 5% reservation을 부여한다.

## 사전 지식

### mClock 스케줄러의 세 가지 클라이언트 클래스와 immediate 우회 경로

Ceph OSD는 dmClock 알고리즘 기반의 mClock 스케줄러로 I/O를 분배한다. 각 클라이언트 클래스에 세 가지 파라미터가 설정된다.

- **reservation**(R): OSD 용량 대비 최소 보장 IOPS 비율
- **weight**(W): 모든 reservation을 충족한 뒤 남은 용량의 비례 배분 가중치
- **limit**(L): 최대 IOPS 상한(0은 무제한)

세 클래스는 다음과 같다.

- **client**: 사용자/애플리케이션 I/O (RADOS 읽기/쓰기)
- **background_recovery**: 저하(degraded) 상태 복구, 리밸런싱
- **background_best_effort**: 백필, 스크럽, 스냅트림 등 우선순위가 가장 낮은 백그라운드 작업

이 세 클래스 외에 **immediate** 경로가 있다. immediate로 분류된 op은 mClock 큐를 완전히 우회하는 고우선순위 큐에 들어가며, mClock이 관리하는 어떤 작업보다 먼저 처리된다.

### Erasure Coding의 다중 OSD 읽기 파이프라인

EC 풀에서 읽기가 발생하면 다음 단계를 거친다.

1. 클라이언트가 해당 PG의 **primary OSD**에 읽기 요청 전송
2. primary OSD가 필요한 데이터 **샤드**(청크)를 결정
3. primary가 각 샤드를 보관하는 OSD에 `MSG_OSD_EC_READ`(SubOp 읽기) 메시지 전송
4. 각 샤드 OSD가 로컬 스토리지에서 청크를 읽어 응답
5. primary가 데이터를 재조립해 클라이언트에 응답

복구/백필에서도 동일한 파이프라인을 사용한다. 드레인된 OSD의 데이터를 복원하기 위해, primary가 나머지 샤드 OSD에 `MSG_OSD_EC_READ`를 보내 데이터를 모은 뒤 대체 OSD에 쓴다. 메시지 타입은 클라이언트 읽기와 동일한 `MSG_OSD_EC_READ`이다.

### SubOp 읽기의 비용과 priority 필드

`MSG_OSD_EC_READ` 메시지에는 sender가 설정하는 `priority` 필드가 있다. 복구 시에는 PG의 복구 긴급도에 따라 `recovery_msg_priority_t` 열거형 값이 할당된다.

- `FORCED`(20): 강제 복구
- `UNDERSIZED`(15): PG 크기 미달 복구
- `DEGRADED`(10): 저하 상태 복구
- `BEST_EFFORT`(5): 백필 등 최선 노력 복구

클라이언트 읽기에서 파생된 SubOp은 이보다 높은 priority(CEPH_MSG_PRIO_HIGH 이상)를 받는다. 이 값은 변경 전에는 스케줄링에 사용되지 않았다.

## 변경 분석

### 변경 전: 모든 EC SubOp 읽기가 immediate로 분류되어 스케줄러를 우회했다

`PGOpItem::get_scheduler_class()`의 분류 로직은 메시지 타입만 확인했다. `CEPH_MSG_OSD_OP`(클라이언트 요청)과 `CEPH_MSG_OSD_BACKOFF`만 `client` 클래스로 분류하고, 그 외 모든 메시지를 `immediate`로 보냈다.

```cpp
// src/osd/scheduler/OpSchedulerItem.h (변경 전)
SchedulerClass get_scheduler_class() const final {
    auto type = op->get_req()->get_type();
    if (type == CEPH_MSG_OSD_OP ||
        type == CEPH_MSG_OSD_BACKOFF) {
      return SchedulerClass::client;
    } else {
      return SchedulerClass::immediate;
    }
}
```

`MSG_OSD_EC_READ`는 `CEPH_MSG_OSD_OP`이 아니므로, 출처가 클라이언트 읽기든 복구 백필이든 모두 immediate 큐로 들어갔다. mClock의 reservation/weight/limit 기반 QoS가 EC SubOp 읽기에는 적용되지 않은 것이다.

```
[변경 전]

                    EC SubOp 읽기 분류
                    ─────────────────

클라이언트 읽기에서 파생
  Primary OSD ──▶ MSG_OSD_EC_READ(prio=HIGH) ──▶ Shard OSD
                                                     │
복구/백필에서 파생                                    │
  Primary OSD ──▶ MSG_OSD_EC_READ(prio=LOW)  ──▶ Shard OSD
                                                     │
                                                     ▼
                                          ┌─────────────────────┐
                                          │   immediate 큐      │
                                          │   (mClock 우회)      │
                                          │                     │
                                          │  클라이언트 SubOp    │
                                          │  복구 SubOp          │
                                          │  백필 SubOp          │
                                          │  ← 모두 섞여서 처리  │
                                          └─────────┬───────────┘
                                                    ▼
                                              OSD 처리 스레드
```

### OSD 드레인 시 immediate 큐의 복구 SubOp이 클라이언트 I/O를 압도했다

트래커 #71655는 2,080개 OSD, EC 3+2/10+2 구성의 대규모 클러스터에서 보고됐다. 하나의 OSD를 드레인하면 약 150개 PG가 동시에 백필을 시작하고, 각 PG가 여러 샤드 OSD에 `MSG_OSD_EC_READ`를 보낸다. 이 SubOp 읽기가 모두 immediate로 분류되면서 고우선순위 큐를 점령했다.

문제는 단순한 큐 경쟁 이상이었다. 트래커의 성능 카운터 스냅샷은 immediate 큐에 139개의 op이 쌓여 있고 client 큐에는 6개만 있는 상태를 보여준다. 클라이언트 op은 mClock 큐를 빠르게 통과했지만, primary OSD가 백필 SubOp 응답을 기다리며 내부 락(BlueStore 트랜잭션 락, PG 락, 오브젝트 락)을 점유한 상태에서 클라이언트 op이 같은 락에 걸렸다. 한 예시에서는 클라이언트 op이 큐에 진입한 뒤 디큐까지 약 40초가 걸렸고, `started` 상태에서 29~62초의 지연이 관측됐다.

`background_best_effort` 프로파일의 reservation이 0%(MIN)이었던 점도 문제를 심화시켰다. 백필 SubOp 읽기가 mClock 큐 안에 있었더라도, reservation이 0이면 client와 recovery의 reservation이 모두 소진될 때까지 스케줄링 기회를 얻지 못해 SubOp가 큐에 체류하는 시간이 길어지고, 그만큼 primary의 락 점유 시간도 늘어난다.

| 프로파일 | background_best_effort reservation (변경 전) | weight | limit |
| --- | --- | --- | --- |
| balanced | 0%(MIN) | 1 | 90% |
| high_client_ops | 0%(MIN) | 1 | 70% |
| high_recovery_ops | 0%(MIN) | 1 | MAX |

## 설계 결정 및 트레이드오프

### priority 필드로 출처를 구분하고 복구 SubOp만 mClock 스케줄링 대상으로 편입

변경의 핵심은 `MSG_OSD_EC_READ`의 기존 priority 필드를 스케줄링 분류에 활용하는 것이다. 새 코드는 priority 값이 `FORCED`(20) 이하인 SubOp 읽기를 복구 출처로 판단하고, `priority_to_scheduler_class()` 함수로 적절한 mClock 클래스에 매핑한다. priority가 `FORCED`보다 높으면 기존과 동일하게 immediate로 분류한다.

```cpp
// src/osd/scheduler/OpSchedulerItem.h (변경 후, 핵심 부분)
SchedulerClass get_scheduler_class() const final {
    switch (op->get_req()->get_type()) {
    case CEPH_MSG_OSD_OP:
    case CEPH_MSG_OSD_BACKOFF:
      return SchedulerClass::client;
    case MSG_OSD_EC_READ: {
      auto prio = op->get_req()->get_priority();
      if (prio <= PeeringState::recovery_msg_priority_t::FORCED) {
        return priority_to_scheduler_class(prio);
      }
      [[fallthrough]];
    }
    default:
      return SchedulerClass::immediate;
    }
}
```

priority에서 클래스로의 매핑은 다음과 같다.

| priority 범위 | 매핑 클래스 | 해당하는 상황 |
| --- | --- | --- |
| CEPH_MSG_PRIO_HIGH 이상 | immediate | 클라이언트 읽기에서 파생된 SubOp |
| DEGRADED(10) ~ FORCED(20) | background_recovery | 강제/축소/저하 상태 복구 SubOp |
| BEST_EFFORT(5) 미만 | background_best_effort | 백필, 스크럽 등 최선 노력 SubOp |

EC SubOp **쓰기**와 **응답**은 여전히 immediate로 분류된다. 쓰기는 primary가 이미 읽기를 완료한 뒤 데이터를 대체 OSD에 기록하는 단계이므로, 여기서 지연하면 primary의 락 점유만 길어진다.

### SubOp 읽기에 실제 바이트 기반 비용을 계산해 mClock에 전달

변경 전 `MOSDECSubOpRead::get_cost()`는 하드코딩된 0을 반환했다. immediate 큐에서는 비용이 무의미했지만, mClock 큐에서는 비용이 op의 가중치 계산에 쓰이므로 실제 I/O 크기를 반영해야 한다. 새 `ECSubRead::cost()` 메서드는 요청된 청크/서브청크 레이아웃에서 실제 바이트 수를 계산한다. WPQ 스케줄러와의 호환성을 위해, WPQ에서는 이전과 동일하게 0을 반환한다.

메시지 포맷도 버전 4로 올라갔다. `cost` 필드가 메시지에 직렬화되어, primary OSD가 계산한 비용을 shard OSD가 그대로 사용한다. 버전 3 이하 메시지에는 필드가 없으므로 기본값 0이 적용되어 하위 호환을 유지한다.

### 프로파일 파라미터를 조정해 background_best_effort에 최소 보장 대역폭 부여

분류 변경만으로는 성능이 오히려 악화됐다. PR의 NVMe 테스트에서 비용 수정만 적용한 경우 평균 지연이 약 25% 증가했다. 복구 SubOp가 immediate에서 나와 mClock 큐에 들어갔지만, `background_best_effort`의 reservation이 0이어서 client와 recovery의 reservation이 소진될 때까지 처리 기회를 받지 못했기 때문이다. SubOp가 큐에서 대기하는 동안 primary의 락 점유가 길어지면서 클라이언트 op이 락 계층에서 지연되는 구조는 그대로였다.

세 프로파일 모두 `background_best_effort`의 reservation을 5%로, weight를 2~4배로 조정했다.

| 프로파일 | reservation (변경 전/후) | weight (변경 전/후) | limit |
| --- | --- | --- | --- |
| balanced | 0% → **5%** | 1 → **2** | 90% |
| high_client_ops | 0% → **5%** | 1 → **4** | 70% |
| high_recovery_ops | 0% → **5%** | 1 → **2** | MAX |

5% reservation은 클라이언트 부하가 최대인 상황에서도 백필/스크럽 SubOp에 OSD 용량의 5%를 보장한다. SubOp가 빠르게 처리되면 primary의 락 점유 시간이 줄고, 락 계층에서 대기하던 클라이언트 op도 빠르게 진행된다. 분류 변경과 프로파일 조정을 함께 적용한 NVMe 테스트에서, `balanced` 프로파일 기준 평균 지연이 약 9.5% 감소하고 백필 처리량의 표준편차가 약 58% 줄어 안정성도 개선됐다.

```
[변경 후]

                    EC SubOp 읽기 분류
                    ─────────────────

클라이언트 읽기에서 파생
  Primary OSD ──▶ MSG_OSD_EC_READ(prio=HIGH)       ──▶ Shard OSD
                                                           │
                                                           ▼
                                                ┌───────────────────┐
                                                │  immediate 큐     │
                                                │  (mClock 우회)     │
                                                └───────┬───────────┘
                                                        │
복구(degraded/undersized/forced)에서 파생                │
  Primary OSD ──▶ MSG_OSD_EC_READ(prio=DEGRADED)  ──▶ Shard OSD
                                                           │
                                                           ▼
                                                ┌───────────────────┐
                                                │ background_       │
                                                │  recovery 큐      │
                                                │ (R/W/L 적용)      │
                                                └───────┬───────────┘
                                                        │

```

### 분류 변경과 프로파일 조정이 반드시 함께 적용되어야 하는 이유

이 변경은 분류 로직과 프로파일 파라미터라는 두 축으로 구성되며, 한쪽만 적용하면 오히려 성능이 악화된다. 분류만 변경하면 SubOp 읽기가 reservation 0인 큐에서 기아 상태에 빠지고, 프로파일만 변경하면 SubOp가 여전히 immediate에 있어 효과가 없다. PR이 약 11개월간 개발/리뷰를 거친 과정에서 이 결합 관계가 NVMe 테스트로 검증됐다.

### 복구 청크 크기 수정으로 소형 오브젝트의 비용 과대평가 방지

`ECBackendL.cc`에서 복구 읽기량이 `get_recovery_chunk_size()`(약 8MiB)로 고정되어 있었다. 오브젝트 크기가 이보다 작아도 8MiB를 요청했고, mClock에 전달되는 비용이 실제 I/O보다 크게 계산됐다. 변경 후에는 오브젝트의 남은 크기와 복구 청크 크기 중 작은 값을 사용한다. 이 수정 없이는 HDD 테스트에서 백필이 WPQ 대비 5배 느린 결과가 나왔다.

## 더 살펴볼 점

- EC SubOp 쓰기와 응답도 immediate에서 분리해 mClock 스케줄링 대상으로 편입하면 어떤 트레이드오프가 생길까?
- 혼합 버전 클러스터에서 메시지 버전 3(cost 필드 없음) OSD와 버전 4 OSD가 공존할 때, mClock의 비용 기반 스케줄링 정확도에 어느 정도 영향이 있을까?
- 5% reservation 값이 OSD 수, EC 프로파일 종류, 디스크 타입(NVMe vs HDD)에 따라 조정이 필요한 임계점은 어디일까?
