## 개요

RabbitMQ v4.3.4는 queue federation의 업스트림을 삭제할 때 exchange federation 전용 메타데이터를 함께 정리하던 경로를 분리했다. 이전 경로는 같은 vhost 안에서 큐와 교환기가 이름까지 같을 경우, 큐의 삭제 요청을 교환기의 Khepri 레코드 갱신으로 잘못 해석할 수 있었다. 그 결과 교환기의 decorator 상태가 손상되고 이후 bind 또는 publish가 실패했다. 이번 변경은 queue federation에서는 링크 중지만 수행하고, exchange federation일 때만 exchange scratch 상태를 지우도록 경계를 복구한다.

## 사전 지식

### Federation 링크와 scratch 상태의 역할

Federation은 다른 브로커의 업스트림과 연결해 로컬 큐 또는 교환기로 메시지를 전달하는 기능이다. 링크의 업스트림 설정이 삭제되면 해당 링크를 멈추고, 더 이상 유효하지 않은 로컬 상태도 정리해야 한다.

Exchange federation에는 이 정리에 쓰이는 `federation` scratch 상태가 있다. 적용 revision의 [`rabbit_federation_db:prune_scratch/2`](https://github.com/rabbitmq/rabbitmq-server/blob/4850ab3f1b2b025c22954fd60c36ce574f2c2fa6/deps/rabbitmq_federation_common/src/rabbit_federation_db.erl#L33-L39)는 남아 있는 업스트림 키만 남기도록 상태를 걸러 `rabbit_exchange:update_scratch/3`에 넘긴다. 같은 파일의 `get_active_suffix/3`와 `set_active_suffix/3`가 보이듯 이 데이터는 exchange federation의 활성 suffix를 찾고 갱신하는 용도다.

반면 큐와 교환기는 이름 문자열이 같을 수 있지만 서로 다른 리소스 종류다. 이 구분이 메타데이터 경계까지 유지되어야 큐의 lifecycle 작업이 교환기의 라우팅 상태를 바꾸지 않는다.

### Khepri 갱신 경로는 교환기 레코드를 직접 수정한다

[`rabbit_exchange:update_scratch/3`](https://github.com/rabbitmq/rabbitmq-server/blob/4850ab3f1b2b025c22954fd60c36ce574f2c2fa6/deps/rabbit/src/rabbit_exchange.erl#L298-L320)는 먼저 전달받은 이름으로 교환기를 읽고, 찾지 못하면 빈 decorator 목록을 준비한 뒤 `rabbit_db_exchange:update/2`를 호출한다. 이후 [`rabbit_db_exchange:update/2`](https://github.com/rabbitmq/rabbitmq-server/blob/4850ab3f1b2b025c22954fd60c36ce574f2c2fa6/deps/rabbit/src/rabbit_db_exchange.erl#L219-L243)는 Khepri의 교환기 경로를 찾아 레코드를 갱신한다.

이 경로의 [`khepri_exchange_path/1`](https://github.com/rabbitmq/rabbitmq-server/blob/4850ab3f1b2b025c22954fd60c36ce574f2c2fa6/deps/rabbit/src/rabbit_db_exchange.erl#L640-L646)는 resource에서 vhost와 이름을 꺼내 교환기 저장소 경로를 만든다. 따라서 이 API에는 교환기 리소스를 넘긴다는 호출자 계약이 중요하다. 큐 이름을 실수로 전달하면, 같은 vhost와 이름을 가진 교환기 경로를 가리킬 수 있다.

## 변경 분석

### 변경 전

변경 전 [`adjust/4`](https://github.com/rabbitmq/rabbitmq-server/blob/03e717826f34e03bc200bea2cd83f3724a279fb1/deps/rabbitmq_federation_common/src/rabbit_federation_link_sup.erl#L55-L59)는 `{clear_upstream, UpstreamName}` 요청에서 대상이 큐인지 교환기인지 구분하지 않고 `prune_scratch`를 실행했다. queue federation에는 정리할 scratch 상태가 없지만, 큐 이름이 교환기 갱신 API까지 전달될 수 있었다.

이 조합은 큐와 교환기가 같은 `{vhost, name}`을 공유할 때만 드러났다. `update_scratch`의 읽기 단계는 큐 resource로 교환기를 찾지 못해 빈 decorator 목록을 만들고, 갱신 단계는 같은 vhost와 이름의 교환기 Khepri 경로를 찾아 그 목록을 저장했다. [#16991](https://github.com/rabbitmq/rabbitmq-server/issues/16991)은 이 상태에서 교환기의 decorator가 bare `[]`가 되고, 이후 decorator 선택이 `function_clause`로 실패하는 재현을 기록한다.

```text
[변경 전] queue federation 업스트림 삭제

Queue federation
  clear_upstream
        |
        v
adjust/4, 대상 종류 미구분
        |
        v
prune_scratch(queue 이름)
        |
        v
exchange update_scratch
        |
        v
Khepri의 같은 {vhost, name} 교환기 레코드 갱신
        |
        v
decorator 상태 손상, 이후 bind 또는 publish 실패
```

적용 커밋의 회귀 테스트는 같은 이름의 durable fanout 교환기와 federated queue를 만들고 업스트림을 지운다. 수정 전에는 교환기의 decorator tuple이 빈 목록으로 바뀌고 publish가 실패했지만, 테스트는 수정 후 삭제 전후 모두 tuple을 유지하고 메시지가 큐로 전달되는지를 확인한다. 이는 단순 예외 방지가 아니라 큐 lifecycle과 교환기 라우팅 상태의 분리를 검증한다.

## 설계 결정 및 트레이드오프

### 변경 후

[`4850ab3f`의 diff](https://github.com/rabbitmq/rabbitmq-server/commit/4850ab3f1b2b025c22954fd60c36ce574f2c2fa6)는 `clear_upstream`을 두 절로 나눴다. `#exchange{}`일 때만 scratch를 prune한 후 링크를 중지하고, 큐일 때는 scratch 갱신 없이 링크만 중지한다. 이로써 exchange federation 전용 상태가 queue federation의 teardown 경로에 들어가지 않는다.

```text
[변경 후] 리소스 종류별 teardown

clear_upstream
      |
      +-- exchange --> prune_scratch(exchange 이름) --> 링크 중지
      |
      +-- queue ----> 링크 중지

queue 이름은 exchange metadata 갱신 경로에 전달되지 않음
```

커밋 설명은 `rabbit_db_exchange:update/2` 자체에서 resource kind를 검증하는 방법도 언급하지만, 호환성 위험이 있고 문제를 완전히 해결하지 못한다고 판단했다. 대신 잘못된 연산을 발생시킨 호출자에서 exchange 전용 동작을 제한했다.

대안과 트레이드오프는 다음과 같다.

- 저장소 계층의 모든 `update/2` 호출에 kind 검증 추가: 방어 범위는 넓지만 기존 호출 계약과 호환성 위험
- queue federation에도 scratch 정리 유지: 공통 흐름은 짧지만 의미 없는 교환기 갱신 경로와 이름 충돌 위험 유지
- `clear_upstream`에서 리소스 종류로 분기: 수정 범위를 결함의 원인 경로로 제한하고 기존 exchange federation 정리 유지

선택한 방식은 저장소 계층을 범용 type-safety 계층으로 바꾸지는 않는다. 대신 federation teardown이 호출하는 API의 도메인 계약을 명확히 하며, 실제로 필요한 exchange scratch 정리와 queue 링크 중지를 각각 보존한다.

## 더 살펴볼 점

- 다른 `rabbit_exchange` 갱신 호출부가 queue resource를 넘기지 않는지 정적 검사로 확인할 방법
- Khepri 경로의 vhost와 이름만으로 충분한 API 경계가 다른 리소스 종류에도 존재하는지
- federation 링크 상태를 운영자가 관찰할 때 queue와 exchange의 이름 충돌을 구분해 표시하는지
