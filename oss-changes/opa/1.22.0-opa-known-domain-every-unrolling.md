# v1.22.0 OPA 알려진 컬렉션의 every를 필터 조건으로 전개

## 개요

OPA v1.22.0은 부분 평가에서 컬렉션의 값은 알지만 조건 본문에 미지수가 남아 있는 `every`를 원소별 조건의 논리곱으로 전개한다. 이전에는 이 경우 `every` 자체가 잔여 정책에 남아 Compile API의 데이터 필터링 대상에서 거부됐다. 새 구현은 작고 알려진 컬렉션을 기존 비교식으로 바꾸어 SQL 필터 등으로 변환할 수 있는 정책 범위를 넓힌다. 전개 한도는 32이며, 중첩된 컬렉션의 크기도 함께 계산한다. 미지의 컬렉션이나 한도를 넘는 경우에는 기존 표현을 유지한다.

## 사전 지식

### 결정 평가와 부분 평가

OPA는 Rego 정책과 입력을 받아 허용 여부 같은 결정을 계산한다. 모든 입력을 알고 있다면 조건을 실제로 평가하면 된다. 반면 데이터 필터링에서는 데이터베이스에서 아직 읽지 않은 행의 속성을 알 수 없다. 사용자의 권한이나 금지 목록은 알고 있어도 각 행의 이름은 모르는 상태다.

**부분 평가**는 이처럼 알려진 값으로 계산할 수 있는 부분을 먼저 처리하고, 미지의 값에 대한 조건을 잔여 쿼리로 남긴다. Compile API의 필터 변환 단계는 이 잔여 조건을 대상 언어가 지원하는 표현으로 옮긴다. Rego에서 유효한 표현이라고 해서 모든 표현을 SQL 등으로 변환할 수 있는 것은 아니다. 이번 변경의 문서와 통합 테스트는 그 경계에 있던 `every`를 다룬다. [변경 문서와 테스트](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

### every의 컬렉션과 본문

`every`는 컬렉션의 모든 원소에 대해 본문 조건이 성립해야 성공하는 표현이다. 예를 들어 알려진 금지 이름 목록의 모든 원소와 행의 이름이 달라야 한다는 정책을 생각할 수 있다. 목록이 두 개의 문자열이라면 필요한 조건은 행의 이름이 첫 문자열과 다르고, 두 번째 문자열과도 다르다는 것이다.

여기서 **컬렉션을 안다는 사실과 본문을 평가할 수 있다는 사실은 별개**다. 행의 이름을 미지수로 두면 비교 결과는 아직 계산할 수 없다. 변경 전 `evalEvery.eval`은 컬렉션 또는 본문에 미지수가 있으면 `save` 경로로 들어가 `every` 표현을 보존했다. 따라서 이미 아는 작은 목록이라도 일반적인 비교식의 논리곱으로 바뀌지 않았다. 이 동작은 변경 diff의 삭제된 분기와 기존 테스트 기대값에서 직접 확인된다. [변경 전후 diff](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

## 변경 분석

### 변경 전: 알려진 반복 범위도 잔여 every로 보존

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: policy
    label: 알려진 목록과 미지의 행 속성
  - id: partial
    label: 본문에 미지수가 있는 every
  - id: residual
    label: every를 잔여 정책에 보존
  - id: reject
    label: 필터 변환 단계에서 거부
edges:
  - from: policy
    to: partial
  - from: partial
    to: residual
  - from: residual
    to: reject
```

이 구조는 일반 Rego 표현을 유지한다는 점에서는 자연스럽지만, 컬렉션이 이미 알려져 있다는 정보를 필터 변환에 활용하지 못한다. 예전 테스트에서 `[1, 2, 3]`의 모든 원소가 미지의 `input`보다 커야 한다는 조건은 반복 표현 그대로 남았다. 새 테스트 기대값은 `1 > input; 2 > input; 3 > input`이다. Rego 본문의 세 조건을 모두 만족해야 하므로 이 전개는 원래의 전칭 조건에 대응한다. [부분 평가 테스트 diff](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

### 알려진 범위를 먼저 구별하는 분기

새 구현은 `domainUnknown`을 별도로 구한다. 컬렉션 자체가 미지수면 그대로 저장하지만, 컬렉션을 알고 본문에만 미지수가 있으면 `knownDomain`을 호출한다. 이 함수는 바인딩을 반영한 값이 배열, 객체 또는 집합인지 확인하고 전개 한도를 검사한 뒤, 기존 generator로 키/값 쌍을 수집한다. 지원하지 않는 값이나 한도 초과에는 전개를 선택하지 않는다. [릴리스 구현](https://github.com/open-policy-agent/opa/blob/d4c8d0c8812290c3e3715ca4cf958f75283f6ec4/v1/topdown/eval.go#L4688)

`unroll`은 원소마다 만든 본문을 하나의 본문에 이어 붙여 평가한다. 단순한 텍스트 복제로 끝낼 수는 없다. 원소별 본문이 한 평가 범위에서 함께 살아 있으므로 지역 변수 이름이 충돌할 수 있기 때문이다. `elementBody`는 원소의 스칼라 값을 직접 대입하고, 객체나 배열 같은 복합 값은 새 변수에 바인딩한다. 본문 자체의 지역 변수에는 고유 접미사를 붙이고, 외부에서 바인딩된 변수와 `input`/`data` 같은 참조 시작점은 보존한다. 복합 값을 새 변수로 연결하는 이유도 코드 주석에 명시되어 있다. 복합 값 자체를 참조의 시작점으로 놓을 수 없기 때문이다. [변수 변환 구현](https://github.com/open-policy-agent/opa/blob/d4c8d0c8812290c3e3715ca4cf958f75283f6ec4/v1/topdown/eval.go#L4729)

### 의미 보존과 필터 변환의 경계

추가된 테스트가 명시하는 결과는 다음과 같다.

- 빈 컬렉션: 조건 없는 참 쿼리
- 한 원소의 본문이 거짓인 경우: 만족 가능한 잔여 쿼리 없음
- 원소별 지역 변수와 복합 값 참조: 이름 충돌 방지와 참조 평가 유지
- 두 개의 알려진 금지 문자열: PostgreSQL 필터에서 두 비교식의 `AND` 결합
- 원소 33개: `every`가 남아 필터 변환에서 거부

이는 테스트 코드를 읽어 확인한 기대 동작이며, 이번 조사에서 테스트를 실행한 결과는 아니다. 별도의 동등성 테스트는 정의되지 않은 값과 두 종류의 `not` 의미를 포함해 원래 정책과 잔여 정책의 결과를 비교한다. 다만 외부 변수 할당과 개선된 `not`이 결합된 일부 입력은 기존 부분 평가의 동작 차이 때문에 테스트에서 제외하므로, 모든 Rego 표현에 대한 일반적인 동등성 증명으로 확대할 수는 없다. [테스트 변경](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

## 설계 결정 및 트레이드오프

### 변경 후: 작은 반복을 기존 조건 표현으로 낮추기

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: input
    label: 미지수가 포함된 every
  - id: check
    label: 알려진 컬렉션과 전개 한도 검사
  - id: expand
    label: 원소별 본문 복제와 변수 분리
  - id: conjunction
    label: 조건의 논리곱을 부분 평가
  - id: translate
    label: 지원되는 잔여 조건을 필터로 변환
  - id: preserve
    label: 기존 every 표현 보존
edges:
  - from: input
    to: check
  - from: check
    to: expand
    label: 전개 가능
  - from: expand
    to: conjunction
  - from: conjunction
    to: translate
  - from: check
    to: preserve
    label: 미지의 범위 또는 한도 초과
```

구현은 각 필터 대상에 일반적인 `every` 변환 기능을 추가하는 대신, 부분 평가 단계에서 이미 지원되는 조건의 조합으로 낮춘다. 이 선택과 비교할 수 있는 대안 및 비용은 다음과 같다. 대안 비교는 코드 구조에 대한 분석이며, 별도의 설계 문서에서 모두 논의되었다는 의미는 아니다.

- 기존 표현 유지: 일반 Rego 의미 보존에 단순하지만 필터 변환의 제약 유지
- 필터 대상마다 전칭 표현 지원: 각 대상 언어의 표현력과 변환 규칙에 추가 의존
- 작은 알려진 범위의 전개: 기존 조건 변환 재사용, 원소 수에 따른 본문 복제 비용 수용

`knownDomain`은 현재 컬렉션의 크기와 바깥쪽에서 전개한 크기의 누적값을 곱해 32를 넘으면 전개하지 않는다. 예를 들어 2개 안에 17개가 중첩되면 바깥쪽은 전개하되 안쪽의 `every` 두 개는 남는다. 이는 중첩 반복의 곱셈식 팽창을 제한하는 장치다. 32라는 값이 측정으로 최적화된 수치라고 볼 근거는 없으며, 구현에서 정한 상수다. [한도 검사와 중첩 테스트](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

또한 이 한도는 **최종 쿼리 개수나 출력 바이트 수의 상한이 아니다**. 본문 자체에 여러 성공 경로가 있으면 원소별 경로가 조합된다. 추가된 테스트에서도 두 원소 각각에 두 대안이 있는 본문은 네 개의 잔여 쿼리를 만든다. 따라서 전개가 가능해졌다는 사실과 결과 필터가 작고 저렴하다는 판단은 분리해야 한다. 전개 뒤에도 지원하지 않는 다른 표현이 남을 수 있으므로, 모든 `every` 정책을 SQL로 변환할 수 있다는 의미도 아니다. [대안 경로 테스트와 필터 문서 변경](https://github.com/open-policy-agent/opa/commit/6d3fadd3724fc461073de43bed1faf6891967a0d)

## 더 살펴볼 점

전개 원소 수 외에 본문의 대안 개수와 잔여 쿼리 크기를 함께 측정하면 한도 조정에 어떤 근거를 제공할 수 있을까?

필터 생성 시스템은 컬렉션 크기가 32에서 33으로 늘어 변환이 거부될 때 어떤 오류와 대체 경로를 사용자에게 보여줘야 할까?
