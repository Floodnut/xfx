## 개요

Linux Kernel v7.2는 공정 스케줄러의 load-balance 이주에 프로세스 단위 Last Level Cache, LLC 선호도를 넣었다. 같은 주소 공간을 공유하는 스레드는 작업 집합을 공유할 가능성이 있다는 휴리스틱으로, 최근 실행 시간이 큰 LLC를 선호 대상으로 삼는다. 다만 이는 hard pinning이 아니다. CPU 과부하, NUMA locality, 과도한 스레드 수, 큰 추정 메모리 footprint가 있으면 일반 부하 균형을 우선한다.

## 사전 지식

### CPU cache domain과 CFS 이주 판단

하나의 LLC는 여러 CPU 코어가 공유하는 마지막 캐시 계층이다. 같은 프로세스의 여러 스레드가 같은 LLC에서 실행되면 공유 데이터를 다시 메모리나 다른 LLC에서 가져오는 일을 줄일 수 있다. 반대로 load balancer가 스레드를 다른 LLC로 옮기면 CPU 이용률은 고르게 만들 수 있어도 캐시 재사용은 약해질 수 있다.

기존 CFS load balancer는 `sched_domain`과 `sched_group`에서 CPU utilization과 runnable task를 비교해 가장 바쁜 group과 runqueue를 고른다. `can_migrate_task()`도 affinity, 실행 중 상태, 현재 CPU에서의 cache-hot 상태, NUMA locality를 확인했다. 따라서 변경 전에도 현재 CPU의 캐시를 지키는 단기 보호는 있었지만, 같은 `mm_struct`를 공유하는 스레드가 어느 LLC에 모여 있는지를 프로세스 단위 배치 신호로 집계하지는 않았다.

`mm_struct`는 같은 프로세스의 스레드가 공유하는 주소 공간 객체다. v7.2의 설계는 이 공유 관계를 실제 cache hit의 증명이 아니라, 작업 집합을 공유할 가능성이 있는지 판단하는 휴리스틱으로 사용한다. 이 구분이 중요하다. 모든 같은-프로세스 스레드가 항상 같은 데이터를 쓰는 것은 아니다.

## 변경 분석

### 현재 CPU 보호에서 프로세스별 LLC 선호도로

`df0d984`는 기본 활성화된 `CONFIG_SCHED_CACHE`와 `mm_struct`의 per-CPU 최근 실행 시간 통계를 추가했다. 스케줄러는 그 통계에서 최근 runtime이 가장 큰 CPU가 속한 LLC를 프로세스의 선호 LLC 후보로 얻는다. 이어 `f38cc2f`는 목적지 LLC를 선호하는 태스크가 가장 많은 `sched_group`을 찾고, `e4c9a4c`는 그 이주를 `migrate_llc_task` 유형으로 구분한다.

```text
변경 전

[sched_group / runqueue]
        |
        v
[CPU utilization, runnable task 비교]
        |
        v
[can_migrate_task]
  | affinity, 실행 중, 현재 CPU cache-hot, NUMA locality
  |
  +--> 다른 LLC로도 이주 가능

같은 mm_struct 스레드가 어느 LLC에 있는지는 group 선택 신호가 아님
```

`5b1d5e6`는 이 정보를 실제 migration gate에 연결한다. 일반 load balance가 태스크를 선호 LLC 밖으로 옮기려 하면 `can_migrate_task()`가 locality를 보존하도록 거부할 수 있다. 반대로 cache-aware balance는 목적지 LLC를 선호하는 태스크가 많은 source group과 runqueue를 골라 그 LLC 쪽 이주를 시도한다.

이 변경의 핵심은 scheduler가 CPU 균형만 최적화하는 대신 cache locality만 최적화하도록 바뀌었다는 뜻이 아니다. `group_llc_balance`의 우선순위는 과부하 group보다 낮다. CPU 과부하 해소가 LLC 응집보다 앞선다.

## 설계 결정 및 트레이드오프

### soft preference, 용량 판단, 회계 분리

v7.2는 LLC 선호를 absolute affinity로 구현하지 않았다. LLC별 utilization과 capacity를 기록해 선호 LLC가 과밀해질 때는 기존 generic load balance로 되돌아간다. NUMA balancing의 선호 노드와 충돌하면 태스크의 LLC 선호도도 무효화한다.

```text
변경 후

[mm_struct의 per-CPU 최근 runtime]
                |
                v
[선호 LLC 추정]
                |
                v
[LLC utilization / capacity, NUMA 충돌 검사]
       |                        |
       | 수용 가능               | 과부하 또는 충돌
       v                        v
[migrate_llc_task]      [generic load balance]
       |
       v
[선호 LLC로 이주 시도]
       |
       +-- 일반 balance의 선호 LLC 이탈은 억제
```

기존 `nr_balance_failed` 회계도 함께 바꿨다. LLC locality 때문에 의도적으로 이주하지 않은 경우는 balance failure가 아니므로, `LBF_LLC_PINNED`로 표시해 실패 횟수가 부당하게 늘지 않게 했다. locality 보존 정책이 다시 더 공격적인 균형 조정을 촉발하는 피드백을 막는 장치다.

회귀를 반영한 guardrail도 추가됐다.

- 활성 스레드 수가 LLC 내 core와 SMT 조건을 넘는 프로세스 제외, `deee5e2`
- NUMA fault statistic으로 추정한 memory footprint가 LLC보다 큰 프로세스 제외, `808915f`
- 집결 강도를 조절하거나 끌 수 있는 `aggr_tolerance`와 debugfs tunable, `c1e7fe5`

이 선택은 같은 프로세스 스레드를 더 모아 cache reuse를 기대하는 대신, memory bandwidth나 LLC contention으로 성능이 떨어질 수 있음을 인정한다. 특히 footprint는 실제 working set을 직접 측정한 값이 아니라 근사치다. 그래서 기본 정책과 사용자 조절 값을 함께 둔 것이다.

## 더 살펴볼 점

- 다양한 LLC 크기와 SMT 폭에서 `aggr_tolerance` 기본값이 실제 workload에 미치는 영향
- user-space가 실제 working set 또는 작업 그룹 힌트를 scheduler에 제공하는 방식
- NUMA locality와 LLC locality가 충돌하는 다중 소켓 시스템의 장기 정책
