## 개요

x86에서 인터럽트/예외/시스템 콜이 커널로 들어오는 경로는 40년 가까이 IDT(Interrupt Descriptor Table) 기반이었다. 벡터 번호 하나로 게이트 디스크립터를 찾아 핸들러로 점프하는 이 방식은 하드웨어가 커널 컨텍스트를 절반만 세워주기 때문에, 나머지 절반(CR3 전환, GS base 판별, 중첩 NMI 방어)을 커널이 어셈블리로 직접 메워야 했다.

Intel FRED(Flexible Return and Event Delivery)는 이 링 전환 자체를 새로 정의한 명령어 아키텍처로, 진입 시 완전한 커널 컨텍스트를, 복귀 시 완전한 유저 컨텍스트를 하드웨어가 원자적으로 확립한다. 리눅스는 2024년 6.9에서 FRED 지원을 병합했지만 1세대 하드웨어의 버그를 우려해 **명시적 opt-in**(`fred=on`)으로 두었다. 7.1은 이 기본값을 뒤집어, FRED를 지원하는 CPU에서는 별도 지정 없이 FRED가 쓰이고 `fred=off`로만 끌 수 있게 했다. 코드 한 줄짜리 조건문 변경이지만, x86-64의 기본 이벤트 전달 경로가 IDT에서 FRED로 넘어갔다는 의미다.

## 사전 지식

### IDT 기반 이벤트 전달이 하는 일과 하지 않는 일

x86에서 인터럽트, 예외, 트랩이 발생하면 CPU는 IDT에서 해당 벡터 번호의 게이트 디스크립터를 읽어 그 안에 적힌 핸들러 주소로 점프한다. 디스패치가 하드웨어에서 벡터 단위로 일어나므로 커널은 벡터마다 별도의 어셈블리 스텁을 등록해야 하고, 벡터 공간(256개)이 곧 표현 가능한 이벤트의 상한이 된다.

문제는 이때 CPU가 스택에 밀어 넣어주는 정보가 CS, RIP, RFLAGS, RSP, SS와 (일부 예외의) 에러 코드뿐이라는 점이다. 예외의 원인 정보는 별도 레지스터에 남는다. 페이지 폴트의 폴트 주소는 CR2에, 디버그 예외의 상태는 DR6에 들어가는데, 이 레지스터들은 하나뿐이다. 페이지 폴트 처리 도중에 NMI가 들어오고 그 NMI 핸들러가 다시 페이지 폴트를 내면 CR2가 덮어써지므로, 커널은 이런 중첩 시나리오마다 원본 값을 소프트웨어로 저장하고 복원해야 한다. `arch/x86/kernel/nmi.c`가 `nmi_cr2` per-CPU 변수를 두고 NMI 진입 시 `read_cr2()`를 저장했다가 빠져나올 때 값이 달라졌으면 `write_cr2()`로 되돌리는 코드가 정확히 이 대응이다.

또 하나 빠져 있는 것이 **진입 출처**다. IDT 이벤트 전달은 커널 코드에서 발생한 예외와 유저 코드에서 발생한 예외를 같은 핸들러 주소로 보낸다. 그런데 커널이 per-CPU 변수에 접근하려면 GS base가 커널 값이어야 하고, 유저에서 들어왔다면 `swapgs`를 실행해야 하지만 커널에서 들어왔다면 실행하면 안 된다. 커널은 이 판별을 스스로 해야 한다. `arch/x86/entry/entry_64.S`의 `paranoid_entry`가 그 결과물이다.

```
	ALTERNATIVE "jmp .Lparanoid_entry_checkgs", "", X86_FEATURE_FSGSBASE
	SAVE_AND_SET_GSBASE scratch_reg=%rax save_reg=%rbx
	jmp .Lparanoid_gsbase_done

.Lparanoid_entry_checkgs:
	/* EBX = 1 -> kernel GSBASE active, no restore required */
	movl	$1, %ebx
	/*
	 * The kernel-enforced convention is a negative GSBASE indicates
	 * a kernel value. No SWAPGS needed on entry and exit.
	 */
	movl	$MSR_GS_BASE, %ecx
	rdmsr
	testl	%edx, %edx
	js	.Lparanoid_kernel_gsbase
```

FSGSBASE 명령어가 있는 CPU에서는 현재 GS base를 읽어 저장한 뒤 커널 값을 무조건 써넣고, 없는 CPU에서는 "GS base가 음수면 커널 값"이라는 커널 내부 규약에 의존해 `swapgs` 실행 여부를 결정한다. 하드웨어가 알려주지 않는 정보를 규약과 MSR 읽기로 복원하는 것이며, CR3 전환(`SAVE_AND_SWITCH_TO_KERNEL_CR3`)과 투기 실행 방어(`IBRS_ENTER`, `FENCE_SWAPGS_KERNEL_ENTRY`)까지 같은 자리에 얹혀 있다.

### IST와 중첩 NMI: 재진입 불가능한 스택 교체

예외 중에는 커널 스택 자체가 망가진 상황에서도 처리돼야 하는 것들이 있다. NMI, #DB, #MC, #DF가 그렇다. IDT는 이를 위해 IST(Interrupt Stack Table)를 제공하는데, 게이트 디스크립터에 IST 인덱스를 적어두면 그 벡터의 이벤트가 발생할 때 CPU가 TSS의 해당 슬롯에 적힌 고정 주소로 스택 포인터를 **무조건** 바꾼다. `arch/x86/kernel/idt.c`의 `def_idts` 테이블이 `ISTG(X86_TRAP_NMI, asm_exc_nmi, IST_INDEX_NMI)` 형태로 이 인덱스를 등록한다.

무조건이라는 점이 문제다. 이미 NMI 스택 위에서 실행 중일 때 또 NMI가 들어오면 스택 포인터가 다시 스택 꼭대기로 되감기면서 실행 중이던 프레임을 덮어쓴다. 여기에 IRET의 동작이 겹친다. IRET는 NMI 차단을 **무조건** 해제하므로, NMI 핸들러 도중 페이지 폴트가 나서 그 폴트 핸들러가 IRET로 복귀하는 순간 NMI가 다시 열린다. NMI 처리 중에 NMI가 중첩될 수 있다는 뜻이다.

커널은 이것을 3상태 소프트웨어 상태 기계로 막아왔다.

```
enum nmi_states {
	NMI_NOT_RUNNING = 0,
	NMI_EXECUTING,
	NMI_LATCHED,
};
```

`exc_nmi()`는 진입 시 상태가 `NMI_NOT_RUNNING`이 아니면 `NMI_LATCHED`로 표시하고 즉시 돌아가며(중첩된 NMI는 실행하지 않고 기록만 함), 처리를 마친 뒤 `this_cpu_dec_return(nmi_state)`가 0이 아니면 `goto nmi_restart`로 핸들러 본문을 다시 돈다. 놓친 NMI를 나중에 대신 실행해주는 구조이며, 이 상태 기계가 성립하려면 `nmi_restart` 이전 구간에서 브레이크포인트도 페이지 폴트도 발생해서는 안 된다는 제약이 따라붙는다. 소스의 주석 40여 줄이 이 제약을 설명하는 데 쓰인다.

### FRED가 정의하는 새 전환

FRED는 이 전환들을 하드웨어 수준에서 다시 설계한다. 공식 문서 `Documentation/arch/x86/x86_64/fred.rst`가 밝히는 설계 목표는 두 가지로, 성능/응답시간 개선과 소프트웨어 견고성이다. 핵심 요소는 다음과 같다.

- **진입점 2개**: 벡터마다의 게이트 대신, ring 3에서 발생한 이벤트와 ring 0에서 발생한 이벤트가 각각 다른 고정 주소로 들어간다. 하드웨어가 진입 출처를 구분해준다는 뜻
- **확장된 스택 프레임**: 64바이트 프레임에 이벤트 타입, 벡터, 에러 코드, 그리고 event data(#PF의 CR2, #DB의 DR6)까지 CPU가 직접 push
- **스택 레벨 0~3**: 재진입 불가능한 IST를 대체. 현재 레벨보다 높은 레벨의 이벤트일 때만 스택을 바꾸고, 같거나 낮으면 현재 스택을 그대로 씀. 되감기가 일어나지 않음
- **ERETS/ERETU**: ring 0을 유지하는 복귀와 ring 3으로 내려가는 복귀를 분리한 두 명령어. NMI 차단 해제는 스택 프레임이 지시할 때만 발생
- **LKGS**: GS 디스크립터 캐시 대신 `IA32_KERNEL_GS_BASE` MSR에 base를 적재하는 명령어. FRED 활성 시 `swapgs`는 아예 금지되어 실행하면 #UD
- **소프트웨어 2단계 디스패치**: 하드웨어가 핸들러를 골라주지 않으므로, 커널이 이벤트 타입으로 1차 분기하고 벡터로 2차 분기

## 변경 분석

### 2년간 opt-in으로 묶여 있던 기능을 기본값으로 뒤집기

FRED 코드 자체는 이미 6.9(2024년 3월 병합, 38개 커밋)에 들어와 있었다. 당시 최초 병합 커밋 메시지는 IDT의 문제를 7가지로 열거하며 FRED가 각각을 어떻게 해소하는지 정리했는데, 정작 기능은 켜지지 않았다. 같은 시리즈의 `3810da12`가 `fred=` 커맨드라인 파라미터를 추가하면서 "기본 동작은 FRED 비활성화, 켜려면 커널 커맨드라인에 `fred=on`을 붙이라"고 못박았기 때문이다.

이유는 하드웨어였다. 7.1 병합 요청에서 Borislav Petkov가 직접 쓴 표현대로, FRED 지원 1세대 머신에 하드웨어 버그가 있을 경우 커널이 광범위하게 깨질 것을 우려한 결정이었다. 실제로 병합 시점에는 FRED를 지원하는 CPU가 일반에 출시되지도 않은 상태여서, 테스트는 시뮬레이션과 제한된 실물에 의존했다.

그 결과 2년 가까이 FRED 코드는 **기본적으로 아무도 실행하지 않는 경로**로 남았다. 이 기간의 실제 상태는 두 갈래였다. 한쪽에서는 코드가 계속 다듬어졌고, 다른 쪽에서는 그 다듬기가 대부분 실사용이 아니라 코드 리뷰와 특정 환경 테스트에서 나왔다. 7.1 직전 몇 달의 수정만 봐도 성격이 드러난다.

- [x86/fred: Correct speculative safety in fred_extint() (aa280a08)](https://github.com/torvalds/linux/commit/aa280a08e7d8fae58557acc345b36b3dc329d595) (2026-01, Andrew Cooper): `array_index_nospec()`의 결과가 스택으로 스필되면 투기 실행 방어가 무력화되므로, 배열 접근 식 안으로 위치를 옮긴 수정. `Fixes: 14619d912b65 ("x86/fred: FRED entry/exit and dispatch code")`로 최초 구현까지 거슬러 올라간다
- [x86/fred: Fix early boot failures on SEV-ES/SNP guests (3645eb7e)](https://github.com/torvalds/linux/commit/3645eb7e3915990a149460c151a00894cb586253) (2026-03, Nikunj A Dadhania): FRED 디스패치 로직에 #VC 핸들러가 아예 없어서 SEV-ES/SNP 게스트가 부팅에 실패하던 문제. `Cc: stable # 6.12+`

두 수정 모두 최초 구현의 누락을 2년 뒤에야 잡은 것이고, 뒤집어 말하면 그동안 그 경로를 밟은 사람이 적었다는 증거다.

전환의 방아쇠를 당긴 것은 하드웨어 출시다. 커밋 `ac66a73b`의 메시지는 Panther Lake(Core Ultra 300 시리즈)가 출시됐고 벤치마크상 대부분의 워크로드에서 유의미한 성능 이득이 확인됐다는 점을 근거로 들며, "CPU가 지원하면 FRED를 기본으로 켠다"고 밝힌다.

실제 코드 변경은 대단히 작다.

```
 	/* Minimize the gap between FRED is available and available but disabled. */
 	arglen = cmdline_find_option(boot_command_line, "fred", arg, sizeof(arg));
-	if (arglen != 2 || strncmp(arg, "on", 2))
+	if (arglen == 3 && !strncmp(arg, "off", 3))
 		setup_clear_cpu_cap(X86_FEATURE_FRED);
```

이전 조건은 "인자가 정확히 `on`이 아니면 FRED 기능 비트를 지운다"였고, 바뀐 조건은 "인자가 정확히 `off`일 때만 지운다"다. `X86_FEATURE_FRED`는 CPUID로 감지되는 하드웨어 기능 비트이므로, 이 비트를 지우지 않으면 CPU가 지원하는 한 FRED 경로가 선택된다. 나머지 변경은 `Documentation/admin-guide/kernel-parameters.txt`에서 어느 쪽이 기본값인지 뒤집어 적은 것과 Kconfig 도움말의 "try to use"를 "use"로 고친 것뿐이다.

여기서 정확히 짚어둘 점이 있다. 뒤집힌 것은 **런타임 기본값**이다. `CONFIG_X86_FRED` 자체는 지금도 `default y`가 붙어 있지 않은 빌드 타임 옵션이라, 배포판이 이 옵션을 켜서 빌드해야 FRED 코드가 커널에 들어간다. 7.1의 변경은 "빌드에 포함돼 있고 CPU가 지원하면 쓴다"로 바뀐 것이지, 모든 커널이 자동으로 FRED가 되는 것은 아니다.

기능 비트가 결정되고 나면 실제 분기는 `arch/x86/kernel/cpu/common.c`에서 갈린다.

```
	if (cpu_feature_enabled(X86_FEATURE_FRED)) {
		/* The boot CPU has enabled FRED during early boot */
		if (!boot_cpu)
			cpu_init_fred_exceptions();

		cpu_init_fred_rsps();
	} else {
		load_current_idt();
	}
```

FRED 쪽으로 가면 `cpu_init_fred_exceptions()`가 진입점 MSR을 설정하고 CR4의 FRED 비트를 세운 뒤 `idt_invalidate()`로 IDT를 무효화한다. 소스 주석이 "Any further IDT use is a bug"라고 적은 그대로, 두 메커니즘이 공존하지 않고 CPU마다 완전히 한쪽으로 정해진다.

```
[변경 전] IDT 기반 이벤트 전달 (6.9 ~ 7.0 기본값, FRED 미지원 CPU는 지금도 동일)

  이벤트 발생 (인터럽트 / 예외 / 시스템 콜)
        │
        ▼
  ┌────────────────────────────────────────────────┐
  │ CPU: IDT[vector] 게이트 디스크립터 조회          │ ← 벡터 하나로 핸들러 결정
  │  - 게이트에 IST 인덱스가 있으면 스택을 무조건 교체 │   (하드웨어 디스패치)
  │  - CS/RIP/RFLAGS/RSP/SS (+에러 코드)만 push     │
  │  - CR2(#PF), DR6(#DB)는 레지스터에 그대로 방치   │ ← 중첩되면 덮어써짐
  │  - 커널/유저 어디서 왔는지는 알려주지 않음        │
  └───────────────────┬────────────────────────────┘
                      ▼
       asm_exc_*  (벡터마다 별도의 어셈블리 스텁)
                      │
        ┌─────────────┴──────────────┐
        │ paranoid_entry             │ 커널 컨텍스트를 소프트웨어로 확립
        │  - CR3 저장 후 커널 CR3     │
        │  - GSBASE 판별 후 swapgs    │ ← 규약/MSR 읽기로 출처를 역산
        │  - IBRS_ENTER, 펜스         │
        └─────────────┬──────────────┘
                      ▼
        C 핸들러 (exc_nmi 등)
          └ 중첩 NMI 방어: nmi_state 3상태 + goto nmi_restart
          └ CR2 훼손 방어: nmi_cr2 저장/복원
                      │
                      ▼
                    IRET  ← NMI 차단을 무조건 해제 (중첩 문제의 근원)
```

## 설계 결정 및 트레이드오프

### 하드웨어 디스패치를 버리고 소프트웨어 2단계 디스패치를 택한 이유

FRED는 벡터별 핸들러 점프를 없앴다. 대신 진입점이 유저용/커널용 두 개뿐이고, 어떤 이벤트였는지는 스택 프레임의 필드를 커널이 읽어 판단한다. `arch/x86/entry/entry_64_fred.S`가 보여주듯 두 진입점은 물리적으로 붙어 있다. 유저 진입점은 4K 정렬돼야 하고(FRED가 확립하는 RIP가 `IA32_FRED_CONFIG & ~FFFH`이므로), 커널 진입점은 `.org asm_fred_entrypoint_user + 256`으로 정확히 256바이트 뒤에 배치된다.

디스패치는 `arch/x86/entry/entry_fred.c`에서 C로 이뤄진다. 1단계는 이벤트 타입 분기다.

```
	switch (regs->fred_ss.type) {
	case EVENT_TYPE_EXTINT:
		return fred_extint(regs);
	case EVENT_TYPE_NMI:
		if (likely(regs->fred_ss.vector == X86_TRAP_NMI))
			return fred_exc_nmi(regs);
		break;
	case EVENT_TYPE_HWEXC:
		return fred_hwexc(regs, error_code);
	...
```

2단계는 벡터 분기이며, `fred_hwexc()`는 switch 문에 들어가기 전에 페이지 폴트를 먼저 검사한다. 주석이 이유를 밝힌다: "Optimize for #PF. That's the only exception which matters performance wise."

하드웨어가 해주던 일을 소프트웨어가 하게 됐으니 분기 몇 개가 늘어난 셈이지만, 그 대가로 얻은 것이 세 가지다.

- **벡터 공간 제약 해소**: 이벤트 종류가 벡터 번호 256개에 묶이지 않음. 최초 병합 커밋 메시지는 이 덕분에 미래 하드웨어에서 NMI 벡터를 여러 개 둘 수 있다고 언급(다만 로컬 APIC 변경이 함께 필요)
- **C 핸들러 재사용**: 디스패치가 C에서 끝나므로 기존 `exc_page_fault()`, `exc_general_protection()` 같은 핸들러를 그대로 호출. IDT 경로와 FRED 경로가 저수준 진입/복귀만 다르고 그 위는 공유
- **진입 스텁 소멸**: 벡터마다의 어셈블리 스텁 대신 진입점 2개

### NMI 처리가 실제로 얼마나 단순해졌는가

설계 목표가 코드로 확인되는 가장 선명한 자리가 NMI다. FRED에서는 CR2/DR6가 스택 프레임에 실려 들어오므로 저장/복원 왕복이 필요 없고, NMI 차단 해제는 ERETS/ERETU가 스택 프레임의 지시를 따를 때만 일어나므로 중첩 자체가 하드웨어에서 막힌다. `arch/x86/kernel/nmi.c`의 FRED용 진입 스텁 위에 붙은 주석이 결론을 그대로 적어놨다.

```
/*
 * With FRED, CR2/DR6 is pushed to #PF/#DB stack frame during FRED
 * event delivery, i.e., there is no problem of transient states.
 * And NMI unblocking only happens when the stack frame indicates
 * that so should happen.
 *
 * Thus, the NMI entry stub for FRED is really straightforward and
 * as simple as most exception handlers. As such, #DB is allowed
 * during NMI handling.
 */
DEFINE_FREDENTRY_NMI(exc_nmi)
```

IDT 경로에서는 NMI 처리 중 #DB가 금지 사항이었지만, FRED에서는 허용된다. `nmi_state` 3상태 기계도, `goto nmi_restart` 루프도 FRED 스텁에는 없다.

스택 교체 역시 IST의 무조건 교체에서 레벨 비교로 바뀌었다. `arch/x86/kernel/fred.c`는 #DB를 레벨 1, NMI와 #MC를 레벨 2, #DF를 최상위인 레벨 3에 배치하고 각 레벨의 RSP MSR에 기존 IST 스택 주소를 그대로 물려준다. #DF를 최상위로 둔 이유는 소스 주석이 밝히듯 "예외를 전달하는 도중에 뭔가 잘못됐다"는 의미이기 때문이고, FRED에서는 그런 경우가 사실상 "가리킨 스택이 망가졌다"로 좁혀진다.

### 받아들인 트레이드오프

**1. 두 진입 경로의 영구적 공존**

FRED는 CPU가 지원해야 쓸 수 있으므로, 지원하지 않는 x86-64 CPU는 앞으로도 IDT 경로를 쓴다. 커널은 `entry_64.S`(IDT)와 `entry_64_fred.S`(FRED) 두 벌의 저수준 진입/복귀 코드를 동시에 유지해야 한다. 이 부담을 줄이기 위해 최초 시리즈는 C 핸들러를 공유하고, 컨텍스트 스위칭처럼 갈리는 지점은 `ALTERNATIVE` 매크로로 런타임 패치하는 방식을 택했다. `asm_fred_entry_from_kvm`의 복귀 부분이 전형적이다.

```
	ALTERNATIVE "nop; nop; mov %rbp, %rsp", \
	            __stringify(add $C_PTREGS_SIZE, %rsp; ERETS), \
		    X86_FEATURE_FRED
```

**2. 32비트 시스템 콜 고속 경로 포기**

`cpu_init_fred_exceptions()`는 FRED를 켜면서 `X86_FEATURE_SYSFAST32`와 `X86_FEATURE_SYSCALL32` 기능 비트를 지운다. 주석대로 "FRED 모드에서 32비트 시스템 콜은 `int $0x80`만 쓴다". 32비트 호환 바이너리의 시스템 콜은 느린 경로로 떨어지지만, 대신 진입 경로의 조합 수가 줄어든다.

**3. opt-in에서 opt-out으로 넘기는 시점의 위험**

기본값을 뒤집는다는 것은 그동안 `fred=on`을 붙인 소수만 밟던 경로를 지원 CPU 전체가 밟게 된다는 뜻이다. 앞서 본 SEV-ES/SNP 부팅 실패 같은 문제가 남아 있었다면 대량의 부팅 실패로 나타났을 것이다. 이 위험을 감수한 근거가 두 가지였다.

- 2년간 축적된 수정으로 코드가 충분히 두들겨 맞았다는 판단(병합 요청의 표현)
- 하드웨어가 실제로 출시되어, 더 미룰수록 오히려 검증 기회를 놓친다는 점

빠져나갈 구멍은 남겼다. `fred=off`는 그대로 동작하며, 조건문이 "정확히 `off`일 때만"으로 좁아졌기 때문에 오타가 난 인자는 이전과 달리 조용히 FRED를 끄지 않는다. 다만 이 엄격함은 양날인데, 예컨대 `fred=0`이나 `fred=disable` 같은 표기를 쓰던 스크립트가 있었다면 이제 의도와 반대로 FRED가 켜진 채 부팅된다.

같은 시리즈의 두 번째 커밋 `f0958d58`이 FRED 초기화 로그 메시지를 삭제한 것도 기본값 전환의 연장선이다. opt-in 시절에는 "FRED가 실제로 켜졌는지" 확인할 수단이 필요했지만, 기본값이 된 이상 CPU마다 그리고 suspend/resume마다 찍히는 이 줄은 소음일 뿐이라는 판단이다.

```
[변경 후] FRED 이벤트 전달 (7.1부터 지원 CPU에서 기본값)

  이벤트 발생
        │
        ▼
  ┌──────────────────────────────────────────────────────┐
  │ CPU: MSR_IA32_FRED_CONFIG가 가리키는 진입점으로 직행    │
  │  - ring 3에서: asm_fred_entrypoint_user   (+0, 4K 정렬)│
  │  - ring 0에서: asm_fred_entrypoint_kernel (+256)      │ ← HW가 출처 구분
  │  - 64바이트 프레임에 type/vector/error/event data push │
  │    (event data = #PF의 CR2, #DB의 DR6)                │
  │  - 스택 레벨(0~3)이 올라갈 때만 스택 교체, 되감기 없음   │
  │  - GS base 스왑과 NMI 차단은 하드웨어가 처리            │
  └───────────────────┬──────────────────────────────────┘
                      ▼
     fred_entry_from_user() / fred_entry_from_kernel()   (C 코드)
                      │
        1단계: fred_ss.type 분기
        (EXTINT / NMI / HWEXC / SWINT / PRIV_SWEXC / SWEXC / OTHER)
                      │
        2단계: fred_ss.vector 분기
        (#PF를 switch 앞에서 먼저 검사하도록 손으로 정렬)
                      ▼
        기존 C 핸들러 그대로 재사용 (exc_page_fault 등)
          └ exc_nmi FRED 스텁: 상태 기계 없음, #DB 허용
                      │
                      ▼
        ERETU (→ ring 3)  /  ERETS (ring 0 유지)
          └ 스택 프레임이 지시할 때만 NMI 차단 해제

  ※ CR4.FRED를 세운 뒤 idt_invalidate() 호출
    ("Any further IDT use is a bug")
  ※ CPU가 FRED 미지원이면 위 경로 전체가 선택되지 않고 IDT 경로 유지
```

## 더 살펴볼 점

- FRED 진입점이 정확히 두 개라는 점은 커널 진입 지점을 노리는 투기 실행 공격의 표면을 어떻게 바꾸는가?
- 지원 CPU가 늘어나면 `entry_64.S`의 `paranoid_entry` 계열 코드는 언제쯤 유지보수 부담이 되기 시작할까?
- AMD가 FRED에 해당하는 자체 메커니즘을 내놓을 경우, 지금의 2경로 구조에 세 번째가 붙는 형태가 될까 아니면 FRED가 사실상 표준이 될까?
