## 개요

containerd v2.3.4는 CRI `CreateContainer` 요청으로 체크포인트를 복원하는 실험 경로를 기본 비활성화했다. 기존의 `enable_criu`는 체크포인트 생성과 복원을 함께 제어했지만, 새 `enable_experimental_restore_via_create` 설정은 복원만 별도로 차단한다. 운영자는 포렌식용 체크포인트 생성은 유지하면서, 일반 컨테이너 생성 API 안에 섞여 있던 복원 동작은 명시적으로 승인한 노드에서만 허용할 수 있게 됐다.

## 사전 지식

### CRI, CRIU, 체크포인트 이미지

Kubernetes의 kubelet이나 `crictl` 같은 CRI 클라이언트는 컨테이너 런타임에 `CreateContainer`를 요청한다. 보통 이 요청은 이미지에서 새 컨테이너를 준비하는 경로다. Linux의 CRIU를 쓰면 실행 중인 컨테이너의 프로세스와 메모리 상태를 아카이브로 저장하는 checkpoint와, 그 아카이브에서 프로세스를 되살리는 restore도 가능하다.

containerd의 기존 CRI 복원 구현은 체크포인트를 OCI 이미지 형태로 참조한 `CreateContainer` 요청을 알아보고 별도 복원 경로로 보냈다. 이 구현은 컨테이너 checkpoint를 생성해 분석하는 포렌식 목적과, 그 상태를 실제로 되살리는 실행 목적을 같은 CRI 생성 진입점 안에 두었다. PR #10365도 checkpoint 이미지를 감지하면 Create와 Start에서 다른 코드 경로를 사용한다고 설명한다.

`enable_criu`는 이 두 동작의 공통 선행조건이었다. 이를 `false`로 두면 CRIU 기반 checkpoint와 restore가 모두 불가능하다. 따라서 포렌식 아카이브 생성은 남겨야 하지만 복원 권한은 더 좁히고 싶은 운영자에게는 충분히 세밀한 정책 수단이 아니었다.

## 변경 분석

### 하나의 생성 API에 결합된 두 제어 흐름

변경 전 `CRImportCheckpoint`는 CRIU 사용 가능 여부만 확인한 뒤 복원을 진행했다. `enable_criu = true`가 기본값이므로 checkpoint 이미지를 전달한 `CreateContainer`도 기본적으로 복원 단계까지 갈 수 있었다. 생성과 복원은 입력 이미지의 종류에 따라 갈리지만, 운영 정책에서는 같은 전역 스위치를 공유했다.

```text
변경 전

[CRI client]
     |
     v
[CreateContainer]
     |
     +-- 일반 이미지 ------------------> [새 컨테이너 준비]
     |
     +-- checkpoint 이미지 --> [CRImportCheckpoint]
                                  |
                                  v
                         [enable_criu = true?]
                                  |
                                  v
                             [CRIU restore]

[CheckpointContainer] ----------> [enable_criu] ----------> [checkpoint export]
```

이 결합에는 두 가지 제약이 있었다.

- 포렌식용 checkpoint export를 유지하려면 복원 경로도 함께 열어야 하는 정책 결합
- 정상 생성과 다른 보안, 자원, 수명주기 의미를 가진 복원이 `CreateContainer` 안에서 선택되는 API 혼합

PR #13913은 이 경로가 실험 기능인데 기본 활성화돼 있었고, normal create와 restore는 운영자가 서로 다른 정책을 적용할 수 있는 별개 흐름이라고 명시한다.

## 설계 결정 및 트레이드오프

### 복원만 별도 opt-in으로 격리

변경은 `RuntimeConfig`에 `enable_experimental_restore_via_create`를 추가하고 기본값을 `false`로 두었다. `CRImportCheckpoint`는 가장 먼저 이 값을 검사해 비활성 상태면 CRIU 확인이나 이미지 처리 전에 오류를 반환한다. 반면 `enable_criu`의 기본값은 계속 `true`여서 checkpoint 생성 기능은 유지된다.

```text
변경 후

[CheckpointContainer] ----------> [enable_criu] ----------> [checkpoint export]

[CRI client]
     |
     v
[CreateContainer + checkpoint 이미지]
     |
     v
[enable_experimental_restore_via_create = true?]
     |                         |
     | false                   | true
     v                         v
[즉시 거부]               [enable_criu 확인]
                                |
                                v
                           [CRIU restore]
```

선택한 방식과 대안의 차이는 다음과 같다.

- `enable_criu = false`로 CRIU 전체 비활성화: 복원은 막지만 포렌식 checkpoint 생성까지 상실
- 기존 기본 허용 유지: 이전 클라이언트와 호환되지만 생성 API의 복원 권한도 기본 허용
- 복원 전용 설정 추가: 기존 흐름은 명시적 opt-in으로만 유지하고 checkpoint 생성 정책은 독립
- 별도 `RestorePod` API: KEP-5823이 CRI의 `CheckpointPod`, `RestorePod`와 kubelet 수명주기를 함께 설계하는 장기 방향, v2.3.4에는 아직 도입되지 않은 대체 경로

그 대가로 기존 `CreateContainer` 기반 restore 사용자는 v2.3.4 이후 설정을 추가해야 한다. `RELEASES.md`는 이 설정을 v2.4 전까지의 deprecated 경로로 표기한다. 즉 이번 변경은 복원을 삭제하는 대신, 포렌식과 복원의 권한 경계를 먼저 분리하고 더 적합한 Pod 수준 API로 옮길 시간을 확보한다.

## 더 살펴볼 점

- KEP-5823의 `RestorePod`가 containerd CRI 구현에 연결되는 시점과 `enable_experimental_restore_via_create` 제거 시점
- checkpoint archive의 원본 이미지, 볼륨, 네트워크 상태가 restore 정책에 미치는 영향
- checkpoint 생성과 restore에 서로 다른 Kubernetes RBAC 및 감사 경로를 적용하는 방식
