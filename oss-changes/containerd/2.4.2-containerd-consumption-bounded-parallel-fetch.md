## 개요

containerd v2.4.2는 이미지 레이어를 병렬로 다운로드할 때 다음 청크를 받을 수 있는 조건을 바꿨다. 이전에는 HTTP 요청이 끝나면 워커가 다음 다운로드를 시작할 수 있었지만, 이미 받은 데이터가 소비되지 않은 채 메모리에 남을 수 있었다. 새 구현은 읽기가 끝난 청크의 자리가 반환되어야 새 pipe를 만들도록 제한한다. 네트워크 요청 수뿐 아니라 다운로드와 콘텐츠 소비 사이에 남는 작업량도 제한하며, 레이어 전체의 청크 수에 비례하던 pipe 사전 생성도 없앤다.

## 사전 지식

### 레이어를 나누어 받아도 읽는 순서는 유지해야 한다

컨테이너 이미지의 레이어는 레지스트리에서 받아야 하는 바이트 스트림이다. 병렬 fetch는 큰 응답을 `chunkSize` 단위로 나누고 여러 워커가 서로 다른 시작 오프셋에서 데이터를 받아 오는 방식이다. 실제 호출자에게는 원래 바이트 순서로 읽히는 하나의 스트림을 제공해야 한다. 먼저 도착한 뒤쪽 청크를 즉시 앞쪽 청크 대신 반환할 수는 없다.

변경 전 구현은 전체 청크 수 `numChunks`를 계산하고 청크마다 메모리 pipe를 미리 만들었다. 워커는 해당 pipe의 쓰기 끝으로 최대 한 청크를 복사하고, 호출자는 `io.MultiReader`를 통해 읽기 끝들을 순서대로 소비했다. 여기서 pipe는 운영체제의 파일 파이프가 아니라 `bytes.Buffer`, 조건 변수와 읽기/쓰기 오류 상태를 가진 containerd 내부 객체다. 쓰기는 버퍼에 데이터를 넣고, 읽기는 데이터가 없으면 쓰기나 종료를 기다린다. [변경 전 구현](https://github.com/containerd/containerd/blob/aec85b3d3281601e953c51bcc2966386295f8ac6/core/remotes/docker/fetcher.go)

### 요청의 완료와 데이터의 소비는 서로 다른 사건

`MaxConcurrentDownloads`에서 정한 병렬도와 요청 limiter는 동시에 진행하는 다운로드를 제한한다. 하지만 요청이 끝나서 워커가 한가해져도 그 결과가 pipe 안에 남아 있을 수 있다. 콘텐츠 저장 경로가 네트워크보다 느리면, HTTP 요청은 계속 완료되고 버퍼에 쌓인 데이터는 천천히 줄어든다. 버퍼 풀도 이 간격을 해결하지 않는다. 풀은 읽기가 끝난 버퍼를 재사용하는 장치이며, 아직 소비하지 않은 데이터를 버릴 수는 없다. 이 구분이 [첫 변경의 문제 설명과 diff](https://github.com/containerd/containerd/commit/6a78f854af4ba1366fb95f0d66324e3e10e250d1)의 출발점이다.

## 변경 분석

### 변경 전: 워커 수를 제한해도 완료된 결과는 계속 남는 구조

기존 큐는 청크 번호를 워커에 전달했다. 워커는 네트워크에서 한 청크를 pipe에 복사한 뒤 writer를 닫고 다음 번호를 가져갔다. 다음 청크를 시작하기 전에 앞선 pipe가 읽혔는지 검사하지 않았기 때문에, 느린 소비자 앞에서 완료된 청크가 레이어 크기에 가까워질 때까지 누적될 수 있었다. 전체 청크의 reader/writer 배열과 pipe 객체도 시작할 때 생성했다. [변경 전 큐, 배열과 워커 루프](https://github.com/containerd/containerd/blob/aec85b3d3281601e953c51bcc2966386295f8ac6/core/remotes/docker/fetcher.go#L548)

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: prepare
    label: 전체 청크의 pipe 사전 생성
  - id: worker
    label: 제한된 워커로 청크 다운로드
  - id: buffered
    label: 완료 데이터는 각 pipe에 잔류
  - id: next
    label: 소비 여부와 무관하게 다음 다운로드
  - id: consumer
    label: MultiReader가 순서대로 천천히 소비
edges:
  - from: prepare
    to: worker
  - from: worker
    to: buffered
  - from: worker
    to: next
  - from: buffered
    to: consumer
```

### 버퍼 윈도에서 pipe 생명주기 제한으로

첫 커밋 `6a78f854`는 청크 `i`를 워커에 넘기기 전에 `i - parallelism` 청크가 소비될 때까지 기다리도록 했다. reader가 버퍼를 풀에 돌려주는 시점에 `drained` 채널을 닫는 방식이다. 이것으로 다운로드 데이터의 선행 범위를 제한했지만, 전체 청크의 pipe와 배열은 여전히 미리 만들었다. [첫 단계 diff](https://github.com/containerd/containerd/commit/6a78f854af4ba1366fb95f0d66324e3e10e250d1)

같은 릴리스의 후속 커밋 `44fd201a`는 이 중간 구현을 다시 바꿨다. **v2.4.2 최종 코드는 `drained` 배열 모델이 아니라 슬롯을 얻은 뒤 pipe를 생성하는 모델**이다. dispatcher는 용량이 유효 병렬도 `P`인 `slots` 채널에 토큰을 넣은 뒤에만 새 pipe를 만든다. 읽기 끝은 순서가 보존되는 `readers` 채널에 전달하고, 쓰기 끝과 청크 번호는 버퍼 없는 작업 큐를 통해 워커에 넘긴다. 전체 청크 수가 커도 활성 pipe 수는 이 슬롯 수로 제한된다. [최종 변경 diff](https://github.com/containerd/containerd/commit/44fd201a89b74fb0f7f41b95ec4622ebd38571f0), [릴리스의 dispatcher와 워커](https://github.com/containerd/containerd/blob/b7a25261e029d68978bbf290df0a62fc819b3c51/core/remotes/docker/fetcher.go#L551)

### 슬롯을 돌려주는 정확한 시점

`io.MultiReader` 대신 도입한 `chunkReader`는 현재 pipe에서 `io.EOF`를 관찰하면 현재 reader를 비우고 슬롯 토큰 하나를 꺼낸다. 이때 pipe의 버퍼는 이미 풀로 반환된 상태다. 따라서 단순히 네트워크 다운로드가 끝났거나 마지막 데이터 바이트를 읽었다는 사실만으로 슬롯이 반환되지는 않는다. 정확히 청크 크기만큼 읽고 호출자가 멈췄다면, 다음 읽기가 EOF를 확인할 때까지 슬롯은 유지된다. 후속 변경의 `TestFetcherOpenParallel_WindowAdvances`도 이 경계를 명시적으로 확인한다. [chunkReader와 테스트 diff](https://github.com/containerd/containerd/commit/44fd201a89b74fb0f7f41b95ec4622ebd38571f0)

취소 처리도 이 생명주기에 맞춘다. dispatcher가 슬롯 또는 워커 인계를 기다릴 때 컨텍스트 취소를 확인하며, 이미 만들었으나 워커에 넘기지 못한 writer는 취소 오류로 닫는다. dispatcher가 종료되면 reader 채널도 닫히고, `chunkReader`는 남은 reader를 지난 뒤 컨텍스트 오류를 반환할 수 있다. `Close`는 컨텍스트를 취소한 뒤 작업 그룹의 종료를 기다린다. 이미 버퍼링한 바이트를 취소 즉시 모두 폐기한다는 보장은 아니다. [릴리스 구현](https://github.com/containerd/containerd/blob/b7a25261e029d68978bbf290df0a62fc819b3c51/core/remotes/docker/fetcher.go#L588), [취소 중 슬롯 대기 테스트](https://github.com/containerd/containerd/commit/44fd201a89b74fb0f7f41b95ec4622ebd38571f0)

## 설계 결정 및 트레이드오프

### 소비자가 다음 다운로드의 진행을 결정

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: slot
    label: dispatcher가 빈 슬롯 확보
  - id: pipe
    label: 청크 pipe를 필요할 때 생성
  - id: worker
    label: 워커가 청크 데이터 다운로드
  - id: reader
    label: chunkReader가 순서대로 소비
  - id: eof
    label: EOF 관찰 후 버퍼와 슬롯 반환
  - id: admit
    label: 다음 청크 생성 허용
edges:
  - from: slot
    to: pipe
  - from: pipe
    to: worker
  - from: worker
    to: reader
  - from: reader
    to: eof
  - from: eof
    to: admit
```

설계의 핵심은 요청 limiter를 없애는 것이 아니라, **미소비 청크가 차지하는 자원에 별도의 제한**을 두는 데 있다. 워커가 빨리 끝났다는 이유만으로 다음 청크를 계속 받을 수 없으므로, 저장 경로가 느려지면 다운로드 생산도 함께 느려진다. 이는 메모리 사용량과 소비 속도를 연결하는 역압력이다. 다음 비교는 실제 변경 전, 중간 커밋, 최종 커밋에서 확인되는 설계 차이를 바탕으로 한 분석이다. 별도의 설계 회의에서 모든 대안을 검토했다는 뜻은 아니다.

| 방식 | 제한하는 대상 | 남는 비용 또는 한계 |
| --- | --- | --- |
| 기존 요청/워커 제한 | 동시 네트워크 작업 수 | 완료되었으나 읽지 않은 데이터의 누적 |
| 첫 커밋의 소비 윈도 | 선행 다운로드 청크 수 | 전체 청크 수에 비례한 pipe와 배열 사전 생성 |
| 최종 슬롯 기반 생성 | 활성 pipe 수와 미소비 데이터 범위 | 슬롯/채널 조율과 EOF 경계 처리의 복잡성 |

유효 병렬도 `P`, 청크 크기 `C`일 때 활성 청크 데이터의 상한은 대략 `P × C`로 설명할 수 있다. 최종 구현은 pipe 생성도 슬롯 뒤로 옮겨 전체 청크 수에 비례한 객체 선할당을 제거한다. 그러나 이 식은 containerd 프로세스 전체의 메모리 상한이 아니다. 버퍼 풀의 보유 용량, allocator, 전송 계층, 압축 해제 버퍼, 다른 레이어의 동시 fetch 등은 별도로 고려해야 한다. `P` 역시 설정값을 그대로 뜻하지 않는다. 작은 응답이나 범위 요청을 지원하지 않는 서버에서는 병렬 경로를 사용하지 않으며, 청크 수가 작으면 병렬도가 줄어든다. [릴리스의 조건과 할당 경로](https://github.com/containerd/containerd/blob/b7a25261e029d68978bbf290df0a62fc819b3c51/core/remotes/docker/fetcher.go#L491)

소비 순서를 보존하므로 앞쪽 청크가 늦으면 뒤쪽 워커가 끝나도 다음 윈도를 무한히 앞당길 수 없다. 네트워크를 최대한 앞서 읽는 여유를 줄이는 대신, 데이터와 pipe의 생명주기를 제한하는 선택이다. 처리량 변화는 네트워크와 콘텐츠 저장 속도에 따라 달라지며 이 보고서에서는 측정하지 않았다. 근거로 읽은 테스트는 큰 `Content-Length`, 윈도 전진, 슬롯 대기 중 취소, 쓰기 오류 후 종료를 다루지만, 대상 프로젝트의 빌드나 테스트는 실행하지 않았다. [변경과 테스트](https://github.com/containerd/containerd/commit/44fd201a89b74fb0f7f41b95ec4622ebd38571f0)

## 더 살펴볼 점

1. 여러 레이어를 동시에 받는 실제 환경에서 활성 버퍼와 버퍼 풀의 메모리 비중은 어떻게 달라질까?
2. 느린 저장 장치와 높은 네트워크 지연이 함께 있을 때 병렬도와 청크 크기는 처리량에 어떤 영향을 줄까?
3. 호출자가 청크 경계에서 읽기를 오래 멈추는 경우 EOF 기반 슬롯 반환 지연은 얼마나 중요할까?
