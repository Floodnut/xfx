## 개요

Envoy v1.40.0은 network filter가 listener의 `DrainDecision`을 조회하던 종료 판단을 연결에 전달된 drain 이벤트 기반으로 전환했다. 핵심은 drain 대상의 선택과 각 프로토콜의 종료 시점을 분리하는 것이다. listener 계층은 대상 연결에 시작 시각과 전략을 전달하고, filter는 그 정보를 이용해 자신의 안전한 시점에 종료를 판단한다. Redis proxy에서는 inbound listener의 연결도 `All` 범위로 조회하던 문제를 없애면서, 대기 중인 응답을 모두 처리한 뒤 종료하는 기존 조건을 유지한다. [변경 diff][change], [릴리스 Redis 구현][redis]

## 사전 지식

### 연결을 받는 listener와 요청을 처리하는 filter

Envoy의 listener는 연결을 받아 filter chain에 연결한다. Redis proxy filter는 한 downstream 연결의 요청과 응답을 관리한다. 여러 요청이 진행 중이면 응답 도착 순서가 요청 순서와 다를 수 있으므로, `pending_requests_`에 결과를 보관하고 앞선 응답부터 내보낸다. 모든 요청이 처리되기 전에 연결을 닫으면 남은 응답을 전달할 수 없다. 따라서 기존 Redis 종료 판단도 이 큐가 비었을 때 수행했다. [변경 전 Redis 구현][old-redis]

**Drain**은 이런 진행 중 작업을 고려하며 연결을 정리하는 과정이다. drain 시작 통지, 종료해도 되는지의 판단, 실제 연결 종료는 서로 다른 단계다. Redis는 응답 큐가 비었을 때 drain 조건을 확인하고, 종료를 선택하면 `FlushWrite`로 남은 쓰기를 내보내며 연결을 닫는다. drain 통지가 곧바로 모든 연결의 강제 종료를 뜻하지 않는다. [릴리스 Redis 구현][redis]

### 이전 종료 판단은 범위를 인수로 받는 조회

기존 `DrainDecision::drainClose()`는 호출자가 `InboundOnly` 또는 `All` 범위를 전달하는 인터페이스였다. `DrainManagerImpl`은 현재 drain 상태와 요청 범위를 비교한다. 서버가 inbound만 정리하는 중인데 호출자가 `All`을 조회하면, 그 요청 범위 전체가 drain 대상은 아니므로 false를 반환한다. immediate 전략은 범위 확인 후 즉시 true를 반환하고, gradual 전략은 drain 시간 경과에 따라 true가 나올 확률을 높인다. [변경 전 DrainManager][old-manager]

이 구조에서 filter는 안전한 종료 시점을 알아야 할 뿐 아니라, 조회할 drain 범위와 자신이 참조하는 listener 쪽 판단 객체도 올바르게 선택해야 했다. PR은 여러 listener 사이에서 공유되는 filter chain에도 올바른 연결별 종료 판단이 필요하다는 점을 변경 동기로 제시한다. 공유 설정 객체의 관점과 실제 연결을 받아들인 listener의 관점이 항상 같다고 가정할 수 없다는 설계 문제다. [PR 설명](https://github.com/envoyproxy/envoy/pull/46985)

## 변경 분석

### 변경 전의 구체적 실패는 inbound 연결의 All 조회

변경 전 Redis `onResponse()`는 대기 응답이 없으면 `drainClose(All)`을 호출했다. inbound listener에서 받은 연결이라도 인수는 동일했다. 앞서 설명한 범위 비교와 결합하면 `/drain_listeners?graceful&inboundonly`로 시작한 drain은 Redis의 종료 판단을 통과하지 못한다. 여기서 설명하는 것은 **이 경로의 drain-close 누락**이며, 다른 timeout이나 listener 제거로도 영원히 닫히지 않는다는 뜻은 아니다. [변경 전 호출][old-redis], [범위 비교][old-manager]

```diagram
title: "변경 전: inbound 연결도 All 범위 조회"
direction: down
nodes:
  - id: start
    label: "서버가 inbound-only drain 시작"
  - id: response
    label: "Redis 응답 처리, pending 큐 비움"
  - id: poll
    label: "filter가 drainClose(All) 조회"
  - id: mismatch
    label: "현재 범위 InboundOnly보다 넓은 요청"

  - from: mismatch
    to: result
```

### 대상 선택을 이벤트 전달 계층으로 이동

릴리스의 `ListenerManagerImpl::onServerDrainStart()`는 inbound-only drain일 때 방향이 `INBOUND`가 아닌 listener를 건너뛴다. 대상 listener에 대해서만 worker의 `onListenerDrain()`을 호출한다. 따라서 filter가 매번 범위를 다시 해석하는 대신, **통지를 받았다는 사실 자체가 해당 연결이 drain 대상임을 나타낸다**. [listener 대상 선택][listeners]

`ConnectionDrainEvent`에는 main thread에서 잡은 시작 시각과 drain 전략이 들어 있다. worker마다 전달 지연이 다르더라도 같은 이벤트의 시각을 기준으로 판단한다. stream listener는 이 이벤트를 보관해 이미 존재하는 연결에 전달하고, drain 중 새로 수락한 연결에는 filter chain을 만든 뒤 다시 전달한다. 후자는 callback이 준비되기 전에 통지를 잃어버리는 일을 피하는 순서다. [이벤트 구조][event], [기존 연결과 신규 연결 전달][active]

Redis filter의 `onDrain()`은 최초 이벤트를 보관할 뿐 그 자리에서 연결을 닫지 않는다. `initializeReadFilterCallbacks()`에서는 연결의 listener 정보에서 `drain_type`도 가져온다. `shouldDrainClose()`는 이 두 정보를 공통 helper에 전달한다. filter factory의 공유 문맥에만 의존하지 않고 실제 연결이 속한 listener 정보를 사용하는 구조다. [Redis 이벤트 보관][redis-h], [listener 정보와 helper 호출][redis]

### 통지와 응답 완료 조건은 별개

새 Redis `onResponse()`도 `pending_requests_.empty()`일 때만 종료를 판단한다. 그때 helper가 true이고 기존 `redis.drain_close_enabled` 조건도 허용하면 `FlushWrite`로 닫는다. helper는 이벤트가 없으면 false, immediate 이벤트라면 true를 반환한다. gradual에서는 전달받은 시작 시각과 drain 기간으로 확률을 계산한다. Redis는 helper의 기본 `ramp_factor=1.0`을 사용한다. [Redis 종료 조건][redis], [공통 helper][helper], [helper 기본 인수][helper-h]

따라서 이 변경을 응답 때 수행하던 모든 계산이 사라졌다고 설명하면 부정확하다. 바뀐 것은 listener의 공유 판단 객체를 조회하는 경로다. Redis는 여전히 응답 처리 시점에 연결에 저장된 이벤트를 평가한다. idle 연결을 이벤트 도착만으로 즉시 닫는 보장도 이 Redis 경로에는 없다. [이벤트 callback][redis-h], [응답 처리][redis]

## 설계 결정 및 트레이드오프

### 대상 판별과 프로토콜별 종료 시점의 분리

```diagram
type: flow
title: "변경 후: 대상 연결에 통지하고 응답 완료 뒤 판단"
direction: down
nodes:
  - id: select
    label: "listener 계층에서 inbound 대상 선택"
  - id: send
    label: "시작 시각과 전략을 연결에 전달"
  - id: save
    label: "Redis filter가 최초 이벤트 보관"
  - id: response
    label: "응답 완료, pending 큐 비움"
  - id: decide
    label: "연결 이벤트와 listener 속성으로 판단"
  - id: close
    label: "기존 runtime 조건 통과 시 FlushWrite"
edges:
  - from: select
    to: send
  - from: send
    to: save
  - from: save
    to: response
  - from: response
    to: decide
  - from: decide
    to: close
```

코드에서 확인되는 선택과 비용은 다음과 같다.

- **listener 계층의 대상 선택**: filter마다 방향을 전달할 책임을 줄이는 대신 worker와 연결까지 이어지는 이벤트 전달 및 신규 연결 재전달 상태의 필요
- **최초 이벤트 우선**: 후속 drain 통지로 이미 진행 중인 연결의 기준 시각을 미루지 않는 대신, listener drain과 서버 drain 판단을 함께 조회하던 때의 추가적인 gradual 종료 가속 일부 포기
- **프로토콜별 안전 시점 유지**: Redis의 대기 응답 보호를 유지하는 대신 이벤트 수신 직후 종료나 idle 연결의 즉시 정리를 보장하지 않는 선택
- **연결 생성 시 runtime guard 고정**: `envoy.reloadable_features.use_connection_event_drain`을 반복 조회하지 않는 대신, guard 변경의 효과를 신규 연결에 한정

첫 이벤트 우선의 비용은 `onServerDrainStart()` 주석에도 명시되어 있다. 이미 자체 drain 중인 listener는 새 서버 drain 통지 대상에서 빠지며, 자체 drain의 최종 강제 종료 deadline은 유지된다. runtime guard가 꺼지면 Redis는 기존 `drainClose(All)` 경로를 사용한다. 이는 운영 중 되돌릴 수 있는 경로지만 이미 생성된 filter의 선택을 즉시 바꾸지는 않는다. [대상 선택과 비용 설명][listeners], [guard와 fallback][redis]

### 되돌릴 수 있는 health 상태는 계속 조회

공통 helper는 `DEFAULT` drain type인 listener에서 health check 실패 상태를 먼저 확인한다. 이 상태는 `/healthcheck/ok`로 회복될 수 있으므로 일회성 drain 이벤트에 합치지 않고 현재 상태를 조회한다. 반면 종료 절차의 시작 시각은 연결에 남긴다. 모든 상태를 이벤트로 통일하기보다 **취소 가능한 상태와 진행 중인 종료 절차를 구분한 설계**다. [helper 구현][helper], [설계 주석][helper-h]

분석상 좁은 대안은 Redis가 넘기는 `All` 인수만 실제 listener 방향으로 바꾸는 것이다. 이 방법은 inbound-only 사례를 다룰 수 있지만, PR이 제기한 listener 사이의 filter chain 공유와 연결별 판단 소유권까지 해결한다는 근거는 없다. 이 대안은 보고서의 비교이며 upstream이 구현해 평가했다고 확인된 안은 아니다. [변경 전 호출][old-redis], [PR의 공유 filter chain 동기](https://github.com/envoyproxy/envoy/pull/46985)

### 회귀 테스트가 확인하는 경계

`OutOfOrderResponseWithDrainCloseViaConnectionDrain`은 immediate 이벤트를 주입하고 이전 `DrainDecision`이 한 번도 호출되지 않도록 기대한다. 두 번째 응답이 먼저 도착한 뒤 첫 응답이 도착하면 요청 순서대로 인코딩하고, 쓰기를 수행한 다음 `FlushWrite`로 닫는 기대를 둔다. 새 판단 경로가 응답 순서와 완료 조건을 유지하는지 확인하는 테스트다. 다만 이 단위 테스트만으로 main thread부터 실제 inbound listener까지의 전체 전달 경로를 검증했다고 말할 수는 없다. 본 보고서는 해당 경로를 릴리스 코드로 별도 확인했으며, 대상 프로젝트를 빌드하거나 실행하지 않았다. [릴리스 회귀 테스트][test]

## 더 살펴볼 점

- drain 도중 새 연결이 만들어질 때 프로토콜마다 이벤트 재전달과 callback 등록 순서가 어떻게 보장되는가?
- 최초 drain 이벤트를 유지하는 정책은 listener 변경과 서버 종료가 겹칠 때 어떤 연결 수명 분포를 만드는가?
- Redis의 응답 기반 종료 판단과 idle timeout을 함께 보면 실제 종료 시간의 상한은 어디에서 정해지는가?
