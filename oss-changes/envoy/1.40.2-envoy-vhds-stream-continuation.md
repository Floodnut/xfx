## 개요

Envoy의 on-demand VHDS는 요청에 필요한 virtual host 설정이 없을 때 제어면에서 이를 가져온다. 이전에는 설정을 얻은 뒤 조건이 맞으면 HTTP 스트림을 다시 만들어 필터 체인을 처음부터 실행했다. 이 과정에서 앞선 필터의 헤더 추가 같은 작업이 반복될 수 있었다. v1.40.0의 변경은 진행 중인 스트림의 라우트 설정 스냅샷과 조회 캐시를 갱신하고 기존 디코딩을 이어가는 방식으로 바꾸었다. 뒤이어 virtual host의 존재와 실제 요청에 맞는 route의 존재를 구별하는 검사가 추가되었다. 두 변경 모두 v1.40.2 소스에 남아 있으며, 설정 발견 완료를 요청 전체의 재실행으로 처리하던 경계를 좁힌 사례다.

## 사전 지식

### Virtual host를 찾는 일과 route를 찾는 일

HTTP 요청을 전달하려면 Envoy는 요청의 호스트명에 해당하는 virtual host를 찾고, 그 안에서 경로 등의 조건에 맞는 route를 선택해야 한다. route는 전달할 upstream cluster를 가리킬 수 있다. VHDS(Virtual Host Discovery Service)는 이러한 virtual host 설정을 동적으로 받는 경로이며, on-demand 필터는 필요한 설정을 아직 모를 때 현재 요청의 디코딩을 멈추고 설정 갱신을 요청한다.

따라서 virtual host가 발견되었다는 응답이 왔다고 해서 해당 요청을 전달할 수 있는 것은 아니다. 예를 들어 호스트는 존재하더라도 `/bar`와 일치하는 route가 없을 수 있다. route가 있어도 그 route가 가리키는 cluster가 아직 없다면, 설정에 따라 on-demand CDS가 추가로 필요할 수 있다. 이 분리는 [on-demand 필터의 route 요청 및 cluster 발견 코드](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/source/extensions/filters/http/on_demand/on_demand_update.cc)에 나타난다.

### 설정 스냅샷과 조회 결과 캐시는 다른 상태

HCM(HTTP Connection Manager)의 스트림은 라우트 설정 스냅샷을 가지고 그 설정에서 찾은 route를 별도로 캐시한다. 설정 공급자가 새 virtual host를 반영하더라도 이미 진행 중인 스트림의 스냅샷이 자동으로 같은 내용으로 바뀌는 것은 아니다. 조회 결과 캐시만 비워도 다시 조회하는 대상이 이전 스냅샷이면 새 virtual host를 보지 못한다.

추가된 `refreshRouteConfigSnapshot()`은 설정 공급자에서 스냅샷을 다시 얻는다. 반면 `clearRouteCache()`는 선택한 route와 cluster 정보의 캐시를 비우며, route cache가 차단된 상태에서는 아무 작업도 하지 않는다. 두 API를 분리한 이유와 적용 범위는 [콜백 인터페이스의 설명](https://github.com/envoyproxy/envoy/blob/d450cd21ce016668a09c787a58173ea0f52a4298/envoy/http/filter.h)과 [릴리스 HCM 구현](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/source/common/http/conn_manager_impl.cc#L2681)으로 확인할 수 있다.

## 변경 분석

### 변경 전에는 조건부 스트림 재생성이 앞선 필터까지 재실행

변경 전 완료 콜백은 설정 조회에 성공했고 요청 본문을 끝까지 읽은 상태에서 `recreateStream(nullptr)`이 성공하면 새 스트림으로 처리를 넘겼다. 헤더만 있는 요청도 이 경로를 탈 수 있었다. 조건이 충족되지 않거나 재생성이 실패하면 기존 체인의 디코딩을 계속했다. 따라서 모든 VHDS 요청이 무조건 재생성되었다고 해석하면 안 된다. [최초 변경 diff](https://github.com/envoyproxy/envoy/commit/d450cd21ce016668a09c787a58173ea0f52a4298)는 이 기존 분기를 legacy 경로로 남겨 두었다.

문제는 재생성이 성공한 경우다. 새 스트림은 최신 설정을 볼 수 있지만 on-demand 앞에 있는 디코더 필터도 다시 실행한다. 앞선 필터가 요청 헤더에 값을 추가하는 작업처럼 반복 실행 시 결과가 달라지는 동작을 한다면, 설정을 한 번 더 읽기 위해 요청의 부수 효과까지 반복하게 된다. 아래 그림은 본문 읽기와 재생성 조건을 충족한 성공 경로다.

```diagram
type: flow
title: 변경 전, VHDS 성공 후 조건부 스트림 재생성
direction: down
nodes:
  - id: first
    label: 앞선 필터가 헤더 추가
  - id: missing
    label: on-demand가 VHDS 요청 후 대기
  - id: found
    label: virtual host 발견, 본문 읽기 완료
  - id: recreate
    label: 스트림 재생성 성공
  - id: repeated
    label: 앞선 필터가 헤더를 다시 추가
  - id: router
    label: 새 설정에서 라우팅
edges:
  - from: first
    to: missing
  - from: missing
    to: found
  - from: found
    to: recreate
  - from: recreate
    to: repeated
  - from: repeated
    to: router
```

### 변경 후에는 스냅샷을 바꾸고 필요한 발견 단계만 재평가

기본 활성화된 `on_demand_vhds_no_recreate_stream` 경로에서 완료 콜백은 다음 순서를 따른다. [v1.40.2 완료 콜백](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/source/extensions/filters/http/on_demand/on_demand_update.cc#L245)에 실제 분기가 있다.

1. VHDS 성공 시 설정 스냅샷 재획득
2. 이전 route/cluster 조회 캐시 제거 요청
3. 새 설정에서 실제 route의 존재 확인
4. route가 있으면 on-demand 자체의 `decodeHeadersBehavior()` 재평가
5. 추가 CDS 대기로 `StopIteration`이면 대기 유지, 그렇지 않으면 `continueDecoding()` 호출

여기서 재평가하는 것은 전체 필터 체인이 아니라 **on-demand 필터 내부의 발견 동작**이다. 앞선 필터는 재실행하지 않으면서 새 route가 아직 없는 cluster를 가리키는 경우의 CDS 요청을 보존한다. VHDS 실패 시에는 성공 경로의 스냅샷 갱신 없이 디코딩을 이어간다. 콜백이 원래 `decodeHeaders()` 실행 도중 동기적으로 호출된 경우에는 중간에 `continueDecoding()`을 호출하지 않도록 기존 보호 분기도 유지한다.

### Virtual host만 발견된 경우에는 router까지 진행

첫 번째 변경만으로는 VHDS 응답이 뜻하는 성공의 범위가 충분히 구분되지 않았다. virtual host는 있지만 요청과 맞는 route가 없는데 내부 발견 동작을 다시 실행하면 동일한 virtual host를 다시 요청할 수 있다. 후속 [d1586477 diff](https://github.com/envoyproxy/envoy/commit/d1586477ee0a4731a737de258755d4889493d21b)는 `on_demand_vhds_require_route_match` guard 아래에서 `route().has_value()`를 검사한다.

기본값에서는 일치하는 route가 없으면 재발견을 시작하지 않고 router까지 진행한다. 통합 테스트는 `/bar`에 맞는 route가 없는 virtual host를 받은 요청이 404로 끝나고 요청 카운트가 1인 것을 검사한다. 이 검사도 legacy 재생성 경로에 적용되므로 두 guard의 역할은 독립적이다. [통합 테스트](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/test/integration/vhds_integration_test.cc#L458)

## 설계 결정 및 트레이드오프

### 요청 실행 상태를 보존하면서 설정 관측 시점만 이동

선택한 설계는 스트림 전체를 새로 만드는 대신 설정을 관측하는 시점과 route 캐시를 갱신한다. 이 선택은 앞선 필터의 부수 효과를 보존하는 대신, 그동안 스트림 재생성이 암묵적으로 수행했던 일을 명시적으로 관리하게 한다. 새 스냅샷을 얻는 것, 기존 조회 결과를 없애는 것, 새 route에 필요한 CDS를 시작하는 것은 각각 별도의 책임이 되었다. [최초 변경의 API/HCM/필터 diff](https://github.com/envoyproxy/envoy/commit/d450cd21ce016668a09c787a58173ea0f52a4298)

```diagram
type: flow
title: 변경 후, 기존 스트림에서 VHDS 결과 반영
direction: down
nodes:
  - id: response
    label: VHDS 완료 콜백
  - id: refresh
    label: 성공 시 스냅샷 갱신과 캐시 제거
  - id: match
    label: 새 설정에서 route 확인
  - id: discovery
    label: route 존재, 필요한 CDS 발견 재평가
  - id: wait
    label: 추가 CDS가 필요하면 대기
  - id: resume
    label: 기존 스트림의 디코딩 재개
  - id: miss
    label: route 부재, router에서 404 처리
edges:
  - from: response
    to: refresh
    label: VHDS 성공
  - from: refresh
    to: match
  - from: match
    to: discovery
    label: 일치
  - from: discovery
    to: wait
    label: cluster 미발견
  - from: discovery
    to: resume
    label: 추가 대기 불필요
  - from: wait
    to: resume
    label: CDS 완료
  - from: match
    to: miss
    label: 불일치
```

이 그림은 두 guard가 기본값인 성공 콜백의 주요 분기를 나타낸다. 비교 가능한 선택과 비용은 다음과 같다.

- 기존 스트림 재생성 유지: 설정을 다시 보는 효과와 함께 앞선 필터의 중복 실행 가능성 유지
- 캐시만 제거: 조회 결과는 다시 계산해도 이전 설정 스냅샷을 보는 한계
- 스냅샷 갱신 후 즉시 재개: 앞선 필터 중복은 없지만 새 route가 가리키는 cluster의 추가 발견 단계 누락 가능성
- 채택한 갱신/재평가/재개: 기존 스트림 보존과 CDS 연계, 대신 콜백의 분기와 상태 관리 증가

마지막 두 항목의 차이는 [단위 테스트의 `NoRecreateStreamVhdsResolutionTriggersOnDemandCds`](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/test/extensions/filters/http/on_demand/on_demand_filter_test.cc)에 명시되어 있다. 앞선 필터 반복 문제는 통합 테스트가 헤더 전용 요청과 본문이 있는 요청을 각각 구성하여, guard 활성 시 헤더 추가 1회, legacy 경로에서 2회를 기대하는 방식으로 검증한다. 이 보고서는 해당 테스트 코드를 읽었으며 실행 결과를 새로 측정하지 않았다.

또한 route가 없는 요청은 미래 VHDS 업데이트에서 route가 추가되기를 계속 기다리지 않는다. 새 설정에서 불일치가 확인되면 router의 404 처리를 허용하는 선택이다. 일반 필터까지 임의로 최신 스냅샷을 가져오게 하는 변경도 아니다. API 주석은 일반적인 route 재평가에는 기존 `clearRouteCache()`를 쓰도록 구분한다. 두 guard는 [runtime 정의](https://github.com/envoyproxy/envoy/blob/b2d89e0ae53916f28770771fbdd49c5c99c5c5a2/source/common/runtime/runtime_features.cc)에서 기본 true이며, 각각 이전 동작으로 돌아갈 수 있는 전환 경로를 남긴다.
