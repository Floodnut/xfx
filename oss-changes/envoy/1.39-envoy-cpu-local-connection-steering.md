## 개요

Envoy v1.39은 고연결률 Linux TCP listener를 위해, user space의 정확한 connection-count 균형기 대신 수신 CPU에 고정된 worker socket으로 새 연결을 보내는 `cpu_locality_balance`를 추가했다. 이 기능은 먼저 worker마다 process affinity mask의 CPU 하나를 고정하고, `SO_REUSEPORT` BPF 프로그램이 수신 CPU에 대응하는 socket index를 고르게 한다. accept마다 mutex를 잡고 모든 worker의 연결 수를 비교하던 경로를 없애며 cache와 NUMA locality를 얻지만, 정확한 연결 수 균등성 대신 수신 CPU 분포와 Linux 커널 기능에 의존한다.

## 사전 지식

### SO_REUSEPORT listener와 Envoy worker

Linux의 `SO_REUSEPORT`는 같은 주소와 port에 여러 listening socket을 묶는다. Envoy의 각 worker는 이 socket group의 한 socket에서 TCP 연결을 받아 event loop로 처리할 수 있다. 기본적으로 kernel은 flow hash로 어느 socket에 새 연결을 줄지 고른다. 이 선택은 accept 이전에 이뤄지므로, kernel이 고른 worker와 NIC가 패킷을 수신한 CPU가 꼭 같을 필요는 없다.

Envoy는 connection balancer를 통해 accept 뒤의 worker 배치를 추가로 조정할 수 있다. `exact_balance`는 worker별 connection count를 공유 자료구조에 기록하고, 새 연결마다 mutex를 잡아 가장 적은 worker를 찾는다. 연결 수를 거의 동일하게 만드는 대신, 모든 accept가 같은 lock과 worker count scan을 거친다. 높은 connection churn에서는 이 직렬 구간이 처리량과 CPU cache locality에 불리하다.

### CPU affinity가 제공하는 안정적인 배치표

v1.39의 `enable_worker_cpu_affinity`는 Linux에서 worker `i`를 process affinity mask에 있는 i번째 CPU에 오름차순으로 고정한다. 이 배치표가 있어야 수신 CPU 번호를 worker socket index로 결정할 수 있다. affinity를 켜지 않으면 worker가 어느 CPU에서 실행될지 scheduler가 바꿀 수 있으므로, CPU-based socket steering은 locality를 보장할 수 없다.

## 변경 분석

### 변경 전: 정확한 connection count를 위해 accept 경로에서 mutex를 사용

```
[변경 전]

NIC 수신 CPU
    │
    ▼
kernel 기본 SO_REUSEPORT hash
    │
    ▼
accept한 worker
    │
    ▼
┌───────────────────────────────────────────┐
│ ExactConnectionBalancer                    │
│  mutex 획득                                │
│  모든 worker의 connection count 비교        │
│  가장 적은 worker로 연결을 배치              │
└───────────────────────────────────────────┘

연결 수는 균등하게 맞추기 쉽지만 수신 CPU와 최종 worker가 달라질 수 있고
모든 accept가 공유 lock을 통과
```

이전 `ExactConnectionBalancerImpl`은 정확한 분산이 필요한 listener에 유용했다. 그러나 각 accept마다 global count를 읽고 갱신해야 하므로 worker 수가 많고 짧은 연결이 많은 환경에서 경쟁 지점이 된다. 특히 kernel이 이미 패킷을 특정 CPU에서 처리한 뒤에 다른 worker로 넘기면, 수신 처리와 user space connection 처리가 다른 CPU와 NUMA node에 걸칠 수 있다.

### 변경 후: 수신 CPU가 kernel BPF를 통해 worker socket을 직접 선택

PR #45722가 worker CPU assignment를 만든 뒤, PR #45734는 `ConnectionBalanceConfig.cpu_locality_balance`를 추가했다. 이 옵션이 켜진 TCP listener는 reuse-port BPF steering을 지원하는 Linux kernel에서 BPF socket option을 socket group에 붙인다. 프로그램은 새 connection을 받은 CPU를 읽고, 미리 계산해 둔 worker CPU 배치표에서 같은 CPU의 worker socket index를 반환한다.

kernel이 accept할 socket을 이미 정했으므로 Envoy는 user space에서 `NopConnectionBalancer`를 사용한다. `cpu_locality_balance`가 설정됐지만 reuse port, worker CPU affinity, BPF steering 지원, process affinity mask 안의 충분한 CPU 중 하나라도 없으면 BPF program을 붙이지 않는다. 이 경우 listener는 실패하거나 `exact_balance`로 되돌아가지 않고, Nop balancer와 kernel 기본 reuse-port hashing으로 계속 서비스한다. PR 리뷰에서 exact fallback을 제거한 이유도, lock을 피하려는 설정을 다시 lock 기반 balancer로 보내는 것이 기능 의도와 맞지 않기 때문이라고 명시됐다.

```
[변경 후]

NIC 수신 CPU
    │
    ▼
┌───────────────────────────────────────────┐
│ SO_REUSEPORT BPF                           │
│ 수신 CPU -> CPU에 고정된 worker socket index │
└──────────────────┬────────────────────────┘
                   ▼
        해당 CPU의 worker socket에서 accept
                   │
                   ▼
            NopConnectionBalancer
                   │
                   ▼
       같은 worker가 connection event loop 처리

조건 불충족: BPF attach 생략 -> kernel 기본 reuse-port hash 유지
```

`ListenerManagerImpl`은 worker count와 process affinity mask가 시작 뒤 바뀌지 않는다는 전제에서 이 CPU assignment를 한 번 계산해 cache한다. 따라서 static listener와 LDS로 나중에 추가되는 listener가 같은 mapping을 사용한다. 이 세부 사항은 listener마다 CPU mapping을 다시 계산해 달라질 위험을 피한다.

## 설계 결정 및 트레이드오프

### 정확한 균등성보다 lock 없는 locality를 선택했다

`exact_balance`는 worker별 connection count가 가장 낮은 곳으로 넘기므로 분포를 강하게 맞춘다. CPU-locality 방식은 NIC receive steering과 process CPU mask가 만든 수신 분포를 따른다. 한 CPU에 수신이 치우치면 connection count도 치우칠 수 있지만, accept-path mutex, 모든 worker count scan, CPU 간 handoff를 줄인다. v1.39은 고연결률 bare-metal 환경에서 후자의 비용을 더 크게 봤다.

### 구성 불가를 listener 실패로 만들지 않고 kernel 기본 동작으로 저하시킨다

Linux kernel version, container CPU mask, reuse-port BPF 지원은 노드마다 다를 수 있다. Envoy는 prerequisites가 모자란 경우 `cpu_locality_balance` 설정 자체를 거부하지 않고 kernel 기본 hashing으로 저하시킨다. 같은 bootstrap과 LDS를 heterogeneous fleet에 배포하기 쉬운 대신, 운영자는 warning과 실제 worker CPU affinity를 관측하지 않으면 일부 노드에서 locality가 적용되지 않은 사실을 놓칠 수 있다.

### worker affinity와 listener 옵션을 함께 요구한다

BPF가 CPU 번호를 socket index로 바꾸려면 worker와 CPU의 일대일 mapping이 필요하다. 그래서 `cpu_locality_balance`는 `enable_worker_cpu_affinity`와 독립적인 성능 knob가 아니다. 이 결합은 scheduler 이동으로 locality가 무너지는 일을 막지만, worker count가 available CPU보다 많지 않아야 하고 CPU quota, cpuset, NIC receive-side scaling 설정까지 운영 설계에 들어온다.

## 더 살펴볼 점

- receive-side scaling queue와 Envoy worker CPU assignment가 다른 NUMA node를 가리킬 때 locality 이점이 얼마나 줄어드는지
- connection count가 아니라 per-CPU load와 queue depth를 함께 보는 adaptive steering이 필요한 workload가 있는지
- hot restart에서 draining parent와 새 process의 reuse-port socket group이 공존하는 동안 새 연결의 CPU-local 배치가 어떻게 관찰되는지
