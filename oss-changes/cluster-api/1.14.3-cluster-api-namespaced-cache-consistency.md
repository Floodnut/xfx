## 개요

Cluster API v1.14.3은 특정 네임스페이스만 관찰하는 컨트롤러에서도 캐시 일관성 검사가 동작하도록 informer와 내부 저장소 사이의 연결을 수정했다. 기존 검사는 모든 informer가 `SharedIndexInformer`라고 가정했지만, 네임스페이스를 지정한 controller-runtime 캐시는 이를 다른 객체로 감싼다. 새 코드는 이 래퍼에서 실제 informer 하나를 꺼내 기존 검사를 유지한다. 기능을 끄는 대신 캐시 추상화 경계를 연결한 변경이며, 공개 API가 없는 부분에 reflection과 `unsafe`로 접근한다는 유지보수 비용도 함께 드러낸다.

## 사전 지식

### API 쓰기 성공과 컨트롤러 캐시의 갱신은 다른 시점

Cluster API는 Cluster와 Machine 같은 리소스를 관찰하고 실제 클러스터의 상태를 원하는 상태에 맞춘다. 이 반복 작업이 reconcile이다. 컨트롤러가 API 서버에 변경을 기록했다고 해서, 관찰에 쓰는 로컬 캐시에도 그 결과가 즉시 반영되는 것은 아니다. 다음 reconcile이 오래된 캐시를 읽으면 방금 수행한 작업을 아직 수행하지 않은 것으로 판단할 수 있다.

이를 줄이기 위해 `consistencyStore`는 상위 객체별로 자식 리소스에 기록한 `resourceVersion`을 저장한다. `WroteAt`은 리소스 종류와 표현 방식별로 기록을 관리하고, `EnsureReady`는 해당 informer 저장소가 관찰한 버전이 기록한 버전까지 따라왔는지 확인한다. 객체 하나를 다시 조회하는 대신 저장소의 `LastStoreSyncResourceVersion()`을 확인하는 구조다. 소유 객체의 UID도 보관하므로 같은 이름으로 다시 생성된 객체는 이전 기록과 구분된다. [릴리스의 일관성 저장소](https://github.com/kubernetes-sigs/cluster-api/blob/825a79dc92ddcca6acc935e233201c697a2f7488/util/controller/consistency.go)

이 검사는 모든 reconcile에 무조건 적용되는 것은 아니다. 릴리스의 `reconcilerWrapper.Reconcile`은 `ReconcilerRateLimiting` 기능이 꺼져 있으면 원래 reconciler를 직접 호출한다. 해당 경로가 활성화되면 캐시 검사를 수행하고, 버전이 뒤처진 경우 100ms 뒤 재실행을 요청한다. 저장소를 얻는 과정 자체에서 오류가 나면 그 오류를 반환한다. [reconcile 진입 경로](https://github.com/kubernetes-sigs/cluster-api/blob/825a79dc92ddcca6acc935e233201c697a2f7488/util/controller/controller.go)

### Informer를 사용할 수 있다는 것과 저장소에 접근할 수 있다는 것

controller-runtime의 `Informer` 인터페이스와 client-go의 `SharedIndexInformer`는 같은 계약이 아니다. 일관성 검사는 단순한 이벤트 구독보다 더 깊은 기능인 `GetStore()`가 필요하다. 따라서 `getStore`는 controller-runtime에서 받은 informer를 client-go 인터페이스로 변환해 내부 저장소를 얻는다.

네임스페이스를 지정한 캐시는 `multiNamespaceInformer`라는 비공개 타입으로 내부 informer를 감싼다. 네임스페이스가 하나뿐이어도 이 래퍼가 사용되며, 래퍼 자체는 `SharedIndexInformer`를 구현하지 않는다. 새 구현의 주석은 바로 이 차이를 설명한다. 이름에 multi가 들어간다는 사실과 실제 관찰하는 네임스페이스가 여러 개라는 사실은 구분해야 한다. [변환 함수와 설계 주석](https://github.com/kubernetes-sigs/cluster-api/blob/e987eabc86957d9ed0b668b60170f7c3ef034d1f/util/controller/consistency.go)

## 변경 분석

### 변경 전: 내부 캐시 형태를 하나로 가정

PR #14290의 제거된 코드는 `GetInformer` 결과를 곧바로 `SharedIndexInformer`로 단언한다. 실패하면 저장소를 반환하지 못하므로, 캐시가 최신인지 비교하기도 전에 `EnsureReady`가 오류로 끝난다. 실제 데이터가 얼마나 빨리 갱신되는지와 무관한 타입 경계의 문제다. [전후 diff](https://github.com/kubernetes-sigs/cluster-api/pull/14290/files)

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: check
    label: 기록한 쓰기 버전 확인 요청
  - id: cache
    label: 네임스페이스 지정 캐시
  - id: wrapper
    label: multiNamespaceInformer 반환
  - id: cast
    label: SharedIndexInformer 직접 단언
  - id: error
    label: 변환 실패로 검사 오류 반환
edges:
  - from: check
    to: cache
  - from: cache
    to: wrapper
  - from: wrapper
    to: cast
  - from: cast
    to: error
```

### 변경 후: 하나의 실제 저장소까지 연결

새 `toSharedIndexInformer`는 일반 `SharedIndexInformer`이면 즉시 반환한다. 그렇지 않으면 reflection으로 구조체의 `namespaceToInformer` 필드를 찾고, 그 값이 map인지 확인한다. 이 필드는 비공개이므로 `reflect.NewAt`과 `unsafe.Pointer`를 이용해 map 안의 값을 읽는다. 각 값이 실제 `SharedIndexInformer`인지 검사한 뒤, 정확히 하나가 들어 있을 때만 반환한다. `getStore`는 그 결과의 `GetStore()`를 기존 종류별 저장소 캐시에 등록한다. [구현](https://github.com/kubernetes-sigs/cluster-api/blob/e987eabc86957d9ed0b668b60170f7c3ef034d1f/util/controller/consistency.go)

여기서 **하나만 허용한다는 제한**이 핵심이다. 코드 주석은 Cluster API가 전체 네임스페이스 또는 단일 네임스페이스 관찰만 지원한다고 명시한다. 단일 네임스페이스 모드에서 namespaced 리소스는 해당 네임스페이스의 informer 하나, cluster-scoped 리소스는 전체 범위 informer 하나로 처리된다. 이 패치는 여러 저장소의 버전을 합성하는 기능을 추가하지 않는다. 내부 informer 수가 1이 아니면 오류를 반환한다.

캐시 버전 비교 자체는 바뀌지 않는다. 관찰 버전이 비어 있으면 아직 동기화되지 않은 것으로 처리하고, 기록 버전보다 뒤처지면 기다린다. 버전 비교에서 오류가 발생한 경우에는 기존 코드처럼 해당 비교를 건너뛴다. 따라서 이 변경을 모든 상황에서 강한 일관성을 새롭게 보장하는 기능으로 해석하면 안 된다. 기존 검사에 필요한 저장소 접근을 네임스페이스 지정 모드까지 연결한 것이다. [릴리스에서 유지된 비교 로직](https://github.com/kubernetes-sigs/cluster-api/blob/825a79dc92ddcca6acc935e233201c697a2f7488/util/controller/consistency.go)

### 테스트가 확인하는 경계

추가된 테스트는 `DefaultNamespaces`에 네임스페이스 하나를 지정한 실제 controller-runtime 캐시를 만든다. 그 안에서 namespaced `ConfigMap`과 cluster-scoped `Node`의 저장소를 각각 얻고, 생성 응답의 버전을 `WroteAt`에 기록한다. 두 저장소의 관찰 버전이 따라온 뒤 `EnsureReady`가 오류 없이 준비 상태가 되는지를 확인한다. 래퍼가 없는 가짜 informer만으로는 놓치던 경로를 직접 다룬 구성이다. 본 보고서는 테스트 소스를 읽었으며 테스트를 실행하지 않았다. [추가 테스트](https://github.com/kubernetes-sigs/cluster-api/blob/e987eabc86957d9ed0b668b60170f7c3ef034d1f/util/controller/consistency_test.go)

## 설계 결정 및 트레이드오프

### 일관성 검사를 유지하는 좁은 어댑터

이 구현은 기존 일관성 검사와 저장소 캐시를 그대로 두고, informer를 얻는 경계만 수정한다. 다음 그림의 버전 비교와 재실행 결정은 기존 경로이며, 새 부분은 래퍼에서 내부 informer 하나를 얻는 단계다. [변환 구현](https://github.com/kubernetes-sigs/cluster-api/blob/e987eabc86957d9ed0b668b60170f7c3ef034d1f/util/controller/consistency.go), [재실행 결정](https://github.com/kubernetes-sigs/cluster-api/blob/825a79dc92ddcca6acc935e233201c697a2f7488/util/controller/controller.go)

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: wrapper
    label: multiNamespaceInformer
  - id: unwrap
    label: 비공개 map에서 informer 추출
  - id: one
    label: 타입 및 정확히 1개인지 확인
  - id: store
    label: 실제 Store의 관찰 버전 조회
  - id: compare
    label: 기록한 쓰기 버전과 비교
  - id: wait
    label: 뒤처지면 재실행 예약
  - id: ready
    label: 따라왔으면 reconcile 진행
edges:
  - from: wrapper
    to: unwrap
  - from: unwrap
    to: one
  - from: one
    to: store
  - from: store
    to: compare
  - from: compare
    to: wait
    label: 캐시 지연
  - from: compare
    to: ready
    label: 검사 통과
```

구현에서 확인되는 선택과 비용은 다음과 같다.

- 기존 검사 유지: 네임스페이스 지정 여부 때문에 쓰기 이후 캐시 확인 절차를 우회하지 않는 구조
- 지원 범위 제한: 여러 informer의 관찰 버전을 결합하는 문제를 피하고 실제 Cluster API 구성 범위만 처리
- 내부 구현 의존: 비공개 필드 이름, map 구조, 내부 값의 타입에 결합되는 reflection/`unsafe` 경로
- 일반 경로 보존: 이미 `SharedIndexInformer`인 경우 reflection 없이 직접 반환

대안으로는 네임스페이스 모드에서 검사를 생략하거나, controller-runtime이 저장소를 공개하는 인터페이스를 제공하도록 바꿀 수 있다. 전자는 검사 의도를 약화시키고, 후자는 상위 의존성의 API 변경이 필요하다. 이는 코드 구조에서 도출한 비교이며, 두 대안을 프로젝트가 정식 설계안으로 평가했다는 뜻은 아니다. 실제 구현 주석은 공개 접근 수단이 없다는 제약과 여러 네임스페이스 처리를 피한다는 선택을 명시한다. 비공개 필드 접근에 의존하는 만큼 의존성 업그레이드 때 추가 테스트가 중요한 회귀 검증 지점이 된다.

## 더 살펴볼 점

- controller-runtime이 저장소 접근 인터페이스를 제공하면 reflection 의존을 제거할 수 있을까?
- 여러 네임스페이스 관찰을 지원할 경우 각 저장소의 진행 상태를 어떤 단위로 비교해야 할까?
- 의존성 변경 시 namespaced 리소스와 cluster-scoped 리소스를 함께 다루는 테스트가 계속 유지될까?
