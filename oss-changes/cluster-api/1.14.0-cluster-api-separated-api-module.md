## 개요

Cluster API v1.14.0은 `sigs.k8s.io/cluster-api/api`를 별도 Go 모듈로 만들었다. 이제 Cluster, Machine 같은 선언 타입만 사용하는 provider나 도구는 컨트롤러, 웹훅, CLI가 들어 있는 루트 모듈을 함께 가져오지 않아도 된다. 이 변경은 단순히 의존성 수를 줄이는 정리가 아니라, 외부 소비자에게 약속하는 API 경계와 Cluster API 자체를 실행하는 제어면 구현의 변경 주기를 분리한 아키텍처 변경이다.

## 사전 지식

### Go 모듈의 의존성 경계

Go에서 import 경로가 하위 디렉터리를 가리켜도, 그 디렉터리에 별도 `go.mod`가 없다면 의존성의 단위는 저장소 루트 모듈 하나다. 따라서 애플리케이션이 `api/...` 아래의 Kubernetes Custom Resource 타입만 import하더라도, 의존성 해석은 루트 `go.mod`가 선언한 직접 의존성을 출발점으로 삼는다.

Cluster API의 루트 모듈에는 컨트롤러를 실행하는 `controller-runtime`, etcd 클라이언트, CLI, 메트릭, 테스트 도구 등이 필요하다. 하지만 다른 provider나 관리 도구가 Cluster API의 `Cluster` 타입을 직렬화하거나 스키마에 등록하려는 경우에는 이런 실행 계층을 쓸 이유가 없다. API 타입의 안정성 기대치와 제어면 구현의 빠른 변경 주기가 같은 모듈에 묶이면, 타입 소비자도 불필요한 버전 제약과 CVE 영향을 함께 받는다.

### API 타입, 웹훅, 컨트롤러의 역할 차이

API 타입 패키지는 Kubernetes API 서버에 저장되는 리소스의 Go 구조체와 변환 코드를 제공한다. 반면 기본값 주입, 유효성 검사, 버전 변환을 요청 경로에서 수행하는 웹훅과, 리소스를 관찰해 실제 클러스터를 바꾸는 컨트롤러는 실행 환경과 `controller-runtime`에 의존한다. 이 셋은 같은 도메인 모델을 공유하지만, 외부 소비자가 필요한 것은 항상 타입 패키지뿐이라는 점이 모듈 경계를 나눌 근거다.

### 하위 모듈의 배포 규칙

하위 디렉터리에 `go.mod`를 두면 그 디렉터리는 `sigs.k8s.io/cluster-api/api`라는 독립 모듈이 된다. Go 도구가 그 모듈의 버전을 찾을 수 있도록 태그는 루트의 `v1.14.0`이 아니라 `api/v1.14.0`처럼 디렉터리 접두사를 가져야 한다. 저장소 안에서 전체 프로젝트를 개발할 때는 루트 모듈의 `replace sigs.k8s.io/cluster-api/api => ./api`가 로컬 API 모듈을 가리킨다.

## 변경 분석

### 변경 전: API 타입 소비자가 루트 제어면의 의존성까지 함께 받는다

#9011은 `api/v1beta1` 타입 하나만 import한 최소 프로그램에서 `go mod tidy`가 56개 의존성을 만들고, 그 안에 `controller-runtime`이 포함된다고 재현했다. 이는 API 타입이 실제로 컨트롤러를 호출한다는 뜻이 아니라, 타입 패키지와 컨트롤러 패키지가 같은 루트 모듈의 의존성 선언을 공유했기 때문이다.

`controller-runtime`처럼 빠르게 바뀌는 라이브러리는 Cluster API 제어면에는 자연스러운 의존성이지만, 타입 소비자에게는 불필요한 호환성 제약이 된다. 다른 버전의 `controller-runtime`을 써야 하는 provider는 단지 Cluster API 타입을 사용했다는 이유만으로 버전 선택 충돌을 겪을 수 있었고, 타입을 복사해 자체 저장소에 두는 우회책도 생겼다.

```
[변경 전] 타입 디렉터리는 있어도 모듈 경계는 루트 하나

Provider 또는 도구
  │ import: Cluster API API 타입
  ▼
sigs.k8s.io/cluster-api 루트 모듈
  ├── api/... 타입과 변환 코드
  ├── 웹훅과 controller-runtime 기반 컨트롤러
  ├── clusterctl, 메트릭, 테스트 도구
  └── 루트 go.mod의 넓은 의존성 그래프
          │
          ▼
타입만 필요해도 제어면 의존성의 버전 제약과 CVE 영향 범위가 전파
```

### 변경 후: 타입을 독립 모듈로 배포하고 경계를 검사한다

PR #13762는 `api/go.mod`를 추가해 API 타입의 module path를 `sigs.k8s.io/cluster-api/api`로 선언했다. v1.14.0 태그에서 이 모듈의 직접 요구사항은 `k8s.io/api`, `apiextensions-apiserver`, `apimachinery`, `cluster-bootstrap` 네 Kubernetes API 계층이다. 루트 모듈이 갖는 `controller-runtime`, etcd, CLI, 테스트 의존성은 API 모듈의 직접 요구사항에 없다.

후속 PR #13825는 API 디렉터리에 있던 OpenAPI generator와 생성 schema를 `hack/tools/runtime-openapi-gen`으로 옮겼다. 그 결과 API 모듈은 `k8s.io/kube-openapi`를 직접 require하지 않는다. 타입 자체와 그것을 사용하는 OpenAPI 생성 도구의 의존성까지 분리한 것이다.

루트 `go.mod`는 API 모듈을 require하고 개발 시에는 `./api`로 replace한다. 따라서 Cluster API 내부의 컨트롤러와 웹훅은 계속 같은 작업 트리에서 타입을 사용하지만, 외부 소비자는 API 모듈만 선택할 수 있다. 이 방향은 저장소를 두 개로 분리하지 않고도 의존성 해석과 호환성 약속의 경계를 분리한다.

경계는 문서상의 약속으로 끝나지 않는다. PR은 릴리스 workflow가 `api/go.mod`가 존재할 때 `api/${RELEASE_VERSION}` 태그도 푸시하도록 바꾸고, lint에 API 패키지용 `depguard` allow-list를 추가했다. 후자는 API 코드가 향후 `controller-runtime` 같은 제어면 의존성을 다시 import해 모듈 경계를 무너뜨리는 일을 CI에서 막는다.

## 설계 결정 및 트레이드오프

### 별도 저장소가 아닌 하위 Go 모듈을 택한 이유

문제 제기 #9011은 API 타입을 복사해 각 소비자 저장소에 두는 방법을 덜 바람직한 대안으로 명시했다. 타입 사본은 원본의 변환, CRD 계약, 버그 수정을 계속 따라가야 하므로 provider와 Cluster API 사이에 드리프트를 만든다. 반대로 하위 모듈은 한 저장소와 한 변경 흐름을 유지하면서, 소비자가 해석하는 의존성 그래프만 좁힌다.

웹훅과 컨트롤러를 API 타입과 같은 모듈에 계속 넣는 선택도 가능했지만, #9011이 지적한 `controller-runtime` 제약을 제거하지 못한다. v1.14.0은 타입 모듈을 작게 유지하고 실행 코드는 루트에 남기는 대신, 내부 개발에는 `replace`를 사용해 두 계층을 함께 변경할 수 있게 했다.

대가는 멀티 모듈 운영 비용이다.

- API의 별도 `go.mod`와 `go.sum` 유지
- API 모듈용 `api/vX.Y.Z` 태그 생성
- 생성 코드, tidy, lint, Dependabot 대상에 API 모듈 추가
- 루트 모듈과 API 모듈 사이 import 방향을 CI 규칙으로 지속 관리

```
[변경 후] 소비자 API와 실행 제어면이 서로 다른 모듈 경계를 사용

외부 Provider 또는 도구                     Cluster API 제어면
          │                                         │
          │ require                                │ require + replace ./api
          ▼                                         ▼
sigs.k8s.io/cluster-api/api  ◀────────────  sigs.k8s.io/cluster-api
  ├── Cluster, Machine 등의 타입                   ├── 컨트롤러와 웹훅
  ├── Kubernetes API 기계 의존성                   ├── controller-runtime와 운영 의존성
  └── api/v1.14.0 태그                             └── v1.14.0 태그
          │                                         │
          └──── depguard가 API 쪽 제어면 import를 차단 ────┘

효과: 타입 소비자는 작은 API 모듈만 선택하고, 제어면은 같은 소스 트리에서
      API를 계속 사용한다.
```

## 더 살펴볼 점

- 후속 API 버전에서 API 모듈의 의존성 allow-list가 얼마나 안정적으로 유지되는지
- provider 생태계가 루트 모듈 대신 `api/vX.Y.Z` 태그를 얼마나 빠르게 채택하는지
- API 모듈과 루트 모듈의 호환성 정책을 릴리스 문서에서 어떻게 더 명확히 드러낼지
