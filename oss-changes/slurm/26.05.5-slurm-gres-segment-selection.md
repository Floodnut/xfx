## 개요

Slurm 26.05.5는 작업 전체의 GPU 요구량과 세그먼트 하나의 노드 선택 목표를 분리했다. 이전에는 노드를 세그먼트 단위로 선택하면서도 GRES 충족 여부는 작업 전체 요구량으로 판단했다. 새 구현은 전체 요구량을 세그먼트 수로 나눈 임시 목표를 사용하고, 다음 세그먼트를 선택할 때 누적량을 초기화한다. 작업의 원래 요구량을 보존하면서 노드 선택의 평가 범위를 맞추는 변경이다. 최종 노드별 GRES 배치는 여전히 작업 전체 단위라는 경계도 유지한다.

## 사전 지식

### 노드 선택과 장치 할당의 서로 다른 범위

Slurm은 HPC 작업이 요청한 CPU, 메모리와 함께 GPU 같은 **GRES(Generic RESources)**를 관리한다. 작업 전체에 필요한 GPU 수를 요청하는 경우, 스케줄러는 후보 노드들을 모으면서 해당 요구를 만족할 수 있는지 평가해야 한다. 이때 `gres_per_job`은 작업의 요구량이고 `total_gres`는 선택 과정의 누적량이다. 둘을 비교하는 공통 평가 함수가 완료 여부와 후보 노드의 충분성을 판단한다.

topology/block은 노드의 블록 구조를 고려해 배치하는 플러그인이다. 세그먼트를 요청한 작업은 하나의 전체 노드 집합을 한 번에 고르는 대신, 세그먼트별 노드 집합을 차례로 고른다. 릴리스 코드에서는 필요한 노드 수와 세그먼트 크기로 세그먼트 수를 계산하고, 선택이 성공한 세그먼트를 작업 정보에 추가한 뒤 다음 세그먼트로 진행한다. 따라서 현재 선택 중인 세그먼트의 목표와 작업 전체의 목표는 다르다.

여기서 후보 노드를 고르는 판단과 최종 장치 배치를 구분해야 한다. 노드 선택 과정에서 각 세그먼트가 필요한 GRES를 공급할 수 있는지 검사하는 것과, 작업에 배정할 실제 GPU를 노드별로 확정하는 것은 같은 보장이 아니다. 이 보고서는 전자의 변경을 다룬다. 위 설명은 [공통 평가 변경](https://github.com/SchedMD/slurm/commit/02af18e57dad699ca06efa37984f283de22c99c3)과 [릴리스 block 구현](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/plugins/topology/block/eval_nodes_block.c#L1208)에 근거한다.

## 변경 분석

### 세그먼트의 완료 조건에 작업 전체 목표를 사용한 문제

변경 전 공통 GRES 평가 함수는 `gres_per_job`과 누적량을 직접 비교했다. block 구현은 이미 세그먼트별 노드 선택을 수행했지만, GRES 목표를 같은 범위로 줄이거나 세그먼트 사이에서 GRES 누적량을 초기화하는 연결이 없었다. 노드 수와 CPU 요구는 세그먼트 범위로 계산하면서 GRES만 전체 작업의 범위에 남는 불일치다. 이는 두 커밋의 삭제/추가 문맥에서 확인할 수 있다. [공통 평가 diff](https://github.com/SchedMD/slurm/commit/02af18e57dad699ca06efa37984f283de22c99c3), [block 연결 diff](https://github.com/SchedMD/slurm/commit/0ba9792c15ddce91951bc8f0c60dfd2bc0061514)

설명을 위해 GPU 8개를 요구하고 2개 세그먼트를 선택하는 작업을 생각할 수 있다. 세그먼트 하나가 GPU 4개를 공급해도, 기존 완료 검사가 전체 목표 8개를 요구하면 해당 세그먼트의 충분성을 인정하지 못한다. 이는 평가 범위를 보여주는 예시이며 실제 실행 측정이나 모든 배치 실패 원인을 나타내는 예시는 아니다.

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: request
    label: 작업 전체 GRES 요구량
  - id: segment
    label: 세그먼트 하나의 후보 노드 선택
  - id: test
    label: 전체 GRES 목표로 충족 여부 검사
  - id: mismatch
    label: 노드 선택 범위와 목표 범위 불일치
edges:
  - from: request
    to: segment
  - from: segment
    to: test
  - from: test
    to: mismatch
```

### 요청량을 보존하고 평가 목표를 별도로 도입

공통 변경은 `gres_job_state_t`에 `gres_per_job_segment`를 추가한다. 이 값이 0이 아니면 공통 평가에서 세그먼트 목표를 사용하고, 0이면 기존 전체 작업 목표를 사용한다. 완료 검사뿐 아니라 후보 노드를 더할 때 남은 요구량을 계산하는 부분과 GRES가 부족한 후보를 판별하는 부분도 같은 목표를 사용한다. 완료 검사 한 군데만 낮춰 다른 판단과 엇갈리는 방식이 아니다. [공통 구현 diff](https://github.com/SchedMD/slurm/commit/02af18e57dad699ca06efa37984f283de22c99c3)

block 구현은 세그먼트 수를 계산한 뒤 `gres_sched_segment_set()`을 호출한다. 이 함수는 작업 단위 GRES 각각에 대해 요구량이 세그먼트 수로 나누어떨어지는지 검사하고, 가능한 경우 몫을 임시 목표로 저장한다. 하나라도 나눌 수 없으면 block 평가를 중단하고 `ESLURM_REQUESTED_TOPO_CONFIG_UNAVAILABLE`을 반환한다. 단순히 정수 나눗셈으로 나머지를 버려 요구를 낮추지 않는다. [릴리스 목표 설정](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/interfaces/gres.c#L10900), [block 호출](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/plugins/topology/block/eval_nodes_block.c#L365)

한 세그먼트가 성공하고 다음 세그먼트가 남아 있으면 `gres_sched_reset()`으로 작업 단위 GRES의 누적량을 0으로 되돌린다. 세그먼트 목표는 유지하므로 다음 세그먼트도 자기 후보 노드만으로 같은 목표를 만족해야 한다. 새 평가의 초기화인 `gres_sched_init()`은 누적량과 임시 목표를 모두 지운다. 목표 설정 중 뒤쪽 GRES에서 나눗셈 검사가 실패해 앞쪽 항목에 값이 남더라도, 해당 평가를 중단하고 다음 초기화에서 제거하는 구조다. [릴리스 초기화/설정](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/interfaces/gres.c#L10850), [세그먼트 전환](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/plugins/topology/block/eval_nodes_block.c#L1220)

## 설계 결정 및 트레이드오프

### 작업 요구와 탐색용 상태를 분리

핵심 선택은 원래의 `gres_per_job`을 덮어쓰지 않고 별도 필드로 탐색 목표를 표현한 것이다. 변경 커밋은 최종 노드별 GRES 배치를 계속 작업 전체 단위로 결정한다고 명시한다. 따라서 세그먼트별 노드 선택 목표가 같아졌다는 사실을 실제 GPU의 최종 배분도 반드시 균등하다는 보장으로 확대해서는 안 된다. [block 변경 설명](https://github.com/SchedMD/slurm/commit/0ba9792c15ddce91951bc8f0c60dfd2bc0061514)

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: job
    label: 원래 작업 GRES 요구량 보존
  - id: target
    label: 나눗셈 검증과 세그먼트 목표 설정
  - id: select
    label: 해당 목표로 한 세그먼트 노드 선택
  - id: reset
    label: 다음 세그먼트 전 누적량 초기화
  - id: next
    label: 같은 목표로 다음 세그먼트 선택
  - id: allocation
    label: 최종 GRES 배치는 작업 전체 단위
edges:
  - from: job
    to: target
  - from: target
    to: select
  - from: select
    to: reset
    label: 성공 후 다음 세그먼트가 있는 경우
  - from: reset
    to: next
  - from: next
    to: allocation
    label: 전체 노드 선택 완료 후
```

다음 비교는 구현에서 읽을 수 있는 대안과 비용에 대한 분석이며, 업스트림이 모든 대안을 논의했다는 뜻은 아니다.

- 원래 작업 요구량을 직접 축소하는 방식: 필드 추가를 줄일 수 있지만 탐색용 목표와 최종 작업 요구가 섞이는 위험
- 전체 요구량만 검사하는 기존 방식: 단일 목표의 단순함과 세그먼트 선택 범위 불일치
- 별도 목표와 세그먼트별 누적량을 사용하는 방식: 원래 요청 보존과 공통 검사 일관성, 추가 상태의 초기화 수명주기 관리 비용
- 나누어떨어지지 않는 요청의 거부: 균등한 탐색 목표의 명확성, 나머지를 일부 세그먼트에 배분하는 유연성의 제한

별도 목표가 없는 일반 평가에서는 기존 목표로 돌아가는 fallback이 유지된다. 다만 이 변경만으로 노드 수, CPU, 다른 GRES 제약까지 모두 해결되는 것은 아니다. 릴리스 노트가 함께 언급한 topology/torus3d의 개별 구현은 이 보고서의 정적 검증 범위에 포함하지 않았다. [공통 목표 선택](https://github.com/SchedMD/slurm/blob/ad46cad8e0969e8e5945b88f0a21f6bed0f9a3bf/src/plugins/topology/common/gres_sched.c#L113)

## 더 살펴볼 점
