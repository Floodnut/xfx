## 개요

etcd v3.7.3은 Raft가 만든 메시지 묶음을 필터링한 뒤에도 원래 순서를 유지하도록 `processMessages`를 수정했다. 기존 구현은 마지막 응답만 남기려고 배열을 뒤에서 읽으면서 살아남은 메시지를 곧바로 출력 배열에 추가했다. 이 과정에서 로그 복제 요청까지 역순이 됐다. 변경 후에는 역방향 순회에서 보존 여부만 기록하고 정방향 순회에서 출력 배열을 만든다. 이 작은 분리는 응답 축약 정책과 로그 복제 요청의 순서를 동시에 지키며, Raft가 소유한 메시지 객체도 직접 변경하지 않는다.

## 사전 지식

### Raft와 etcd 사이의 Ready 경계

Raft 라이브러리는 합의를 진행하며 외부로 보낼 메시지와 저장할 항목을 생성한다. etcd의 `raftNode.start`는 `Ready`를 받아 저장, 적용, 전송 작업을 연결한다. 이 중 `rd.Messages`는 전송할 메시지의 배열이고, `processMessages`는 이를 실제 transport에 넘기기 직전 처리하는 단계다. 리더의 전송 경로와 비리더의 전송 경로 모두 이 함수를 사용한다. [릴리스 구현](https://github.com/etcd-io/etcd/blob/0a173d0410a96d01091b484daae81365bbcde57e/server/etcdserver/raft.go)

메시지는 모두 같은 목적이 아니다. `MsgApp`은 팔로어에 로그 항목을 복제하는 요청이고, `MsgAppResp`는 그 요청에 대한 응답이다. `MsgApp`에는 앞선 로그의 인덱스와 term이 포함된다. 팔로어는 이 지점을 자신의 로그와 맞춰 본 뒤 새 항목을 받아들인다. 앞선 지점이 맞지 않으면 거절 응답을 보낼 수 있으므로, 서로 이어지는 요청을 뒤집어 보내면 아직 갖고 있지 않은 앞선 로그를 요구하는 요청이 먼저 도착할 수 있다. [Raft 수신 처리](https://github.com/etcd-io/raft/blob/b867cf13f6bc0dae21204302df97bc2355c3af55/raft.go)

### 필터에는 순서와 별개의 정책이 존재

`processMessages`는 제거된 멤버를 향하는 메시지를 버리고, 한 묶음에서 마지막 `MsgAppResp` 하나만 남긴다. `MsgSnap`은 일반 전송 결과에서 제외하고 별도 snapshot 채널로 넘긴다. `MsgHeartbeat`에는 지연 관측 처리도 적용한다. 마지막 응답을 먼저 찾으려면 역방향 순회가 편리하지만, 이 선택 방식이 다른 메시지의 출력 순서까지 결정할 필요는 없다. [백포트 diff](https://github.com/etcd-io/etcd/commit/d6876b69ce42f37103049f09a5a8ab91521c0ce3)

여기서 마지막 응답은 목적지별 마지막 응답이 아니다. 코드의 `sentAppResp`는 한 번 호출되는 메시지 묶음 전체에서 공유하는 단일 불리언이다. 제거된 목적지 검사에 걸리지 않은 응답 중 배열상 마지막 하나를 보존하는 기존 정책이며, 이번 수정도 이 범위를 바꾸지 않았다.

## 변경 분석

### 역방향 선택이 역방향 전송으로 이어진 문제

변경 전에는 배열 끝에서 시작해 필터를 통과한 메시지를 즉시 `messages`에 추가했다. 따라서 입력이 같은 팔로어를 향하는 `MsgApp` 인덱스 10, 11, 12 순서이면 출력은 12, 11, 10 순서가 됐다. 이는 추정 사례만이 아니다. 백포트의 `TestProcessMessagesOrder` diff에는 해당 역순 기대값을 정순 기대값으로 바꾸는 변경이 있다. 테스트의 `Index` 값은 요청이 참조하는 앞선 로그 위치이며, 여기서는 출력 순서를 구분하는 값으로 사용한다. [실제 테스트 변경](https://github.com/etcd-io/etcd/commit/d6876b69ce42f37103049f09a5a8ab91521c0ce3)

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: ready
    label: Ready의 MsgApp 순서 10, 11, 12
  - id: scan
    label: 뒤에서 읽으며 필터 적용
  - id: append
    label: 통과 즉시 출력 배열에 추가
  - id: send
    label: transport에 12, 11, 10 전달
edges:
  - from: ready
    to: scan
  - from: scan
    to: append
  - from: append
    to: send
```

Raft의 `handleAppendEntries`는 앞선 로그와 맞지 않는 요청에 `Reject`가 설정된 응답을 반환한다. 따라서 뒤쪽 요청부터 보내는 동작은 아직 필요한 앞선 로그가 없는 팔로어에서 거절과 재전송을 유발할 수 있다. 공식 변경 기록도 이를 성능 회귀로 분류한다. 이 자료만으로 데이터 손실이나 합의 안전성 위반을 주장할 근거는 없다. [Raft 구현](https://github.com/etcd-io/raft/blob/b867cf13f6bc0dae21204302df97bc2355c3af55/raft.go), [릴리스 변경 기록](https://github.com/etcd-io/etcd/blob/ba2f7625c3f707fd958a79ab3ede857e82b405dc/CHANGELOG/CHANGELOG-3.7.md)

### 보존 여부와 결과 배열을 따로 구성

변경 후에도 필터 순회는 뒤에서 앞으로 진행한다. 다만 통과한 메시지를 출력하지 않고 입력 위치에 대응하는 `keep[i]`를 참으로 표시하며 개수를 센다. 모든 필터 처리가 끝나면 앞에서부터 `keep`을 읽고 보존 표시가 있는 원래 포인터만 새 배열에 넣는다. 남는 항목이 없으면 `nil`을 반환한다. [v3.7.3 구현](https://github.com/etcd-io/etcd/blob/0a173d0410a96d01091b484daae81365bbcde57e/server/etcdserver/raft.go)

결과적으로 마지막 응답 선택은 유지하면서 살아남은 메시지 사이의 상대 순서를 보존한다. 릴리스 테스트는 같은 목적지의 연속 `MsgApp`, 요청과 응답의 혼합, 제거된 목적지, 서로 다른 목적지의 응답을 다룬다. 특히 서로 다른 목적지의 응답도 마지막 하나만 남기는 기대값이 있어, 목적지별 응답 병합으로 오해할 여지가 없다. 각 사례는 입력 메시지의 요약이 호출 전후 동일한지도 비교한다. 이 보고서에서는 테스트를 실행하지 않고 그 검증 조건을 읽었다. [TestProcessMessagesOrder](https://github.com/etcd-io/etcd/blob/0a173d0410a96d01091b484daae81365bbcde57e/server/etcdserver/raft_test.go)

## 설계 결정 및 트레이드오프

### 필터 정책은 유지하고 출력의 순서를 복원

이번 수정은 Raft 프로토콜이나 transport 자체를 재설계하지 않는다. etcd가 Raft의 출력물을 가공하는 경계에서, 어떤 항목을 보낼지 결정하는 순서와 어떤 순서로 보낼지를 분리한다. 아래 그림의 응답 선택과 snapshot 분리는 첫 순회에서 처리되고, 일반 전송 결과의 상대 순서는 두 번째 순회에서 복원된다. [구현과 diff](https://github.com/etcd-io/etcd/commit/d6876b69ce42f37103049f09a5a8ab91521c0ce3)

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: ready
    label: Ready의 메시지 배열
  - id: filter
    label: 역방향 필터와 keep 위치 기록
  - id: snapshot
    label: MsgSnap은 별도 채널로 전달
  - id: gather
    label: 정방향으로 보존 포인터 수집
  - id: send
    label: 원래 상대 순서로 transport 전달
edges:
  - from: ready
    to: filter
  - from: filter
    to: snapshot
    label: snapshot 분기
  - from: filter
    to: gather
    label: 일반 전송 대상
  - from: gather
    to: send
```

코드에서 확인되는 선택과, 그에 대한 분석상 대안은 다음과 같다. 대안이 모두 업스트림에서 논의됐다고 해석해서는 안 된다.

- 역방향 순회 중 즉시 출력: 별도 보존 배열은 불필요하지만 살아남은 요청의 순서 역전
- 입력 메시지의 직접 수정: 추가 자료구조를 줄일 여지는 있으나 Raft 소유 메시지를 건드리는 소유권 문제
- 채택한 두 단계 구성: 입력 길이만큼의 불리언 배열과 두 번의 선형 순회 비용, 필터 정책과 출력 순서의 분리

실제 구현은 출력에 필요한 개수를 먼저 센 뒤 그 용량의 포인터 배열을 할당한다. 메시지 본문을 깊게 복사하지 않고 기존 포인터를 보존한다. 따라서 추가 보존 공간과 순회 비용을 지불하지만, 입력 메시지 객체를 수정하지 않는 성질을 유지한다. 이는 코드와 입력 불변성 테스트로 확인되는 범위다. [릴리스 구현](https://github.com/etcd-io/etcd/blob/0a173d0410a96d01091b484daae81365bbcde57e/server/etcdserver/raft.go), [테스트](https://github.com/etcd-io/etcd/blob/0a173d0410a96d01091b484daae81365bbcde57e/server/etcdserver/raft_test.go)

순서 보장은 **한 Ready 묶음에서 일반 transport로 반환하는 메시지의 상대 순서**에 한정된다. snapshot은 별도 경로로 빠지고, 네트워크 전체의 도착 순서나 여러 Ready 묶음 사이의 모든 실행 순서를 보장하는 변경은 아니다. 정적 분석만으로 처리량 개선 폭을 수치화할 수도 없다.

## 더 살펴볼 점

- Raft 소유 포인터를 다루는 다른 가공 경계에도 입력 불변성과 출력 순서를 함께 검사하는 테스트가 있는가?
- 큰 Ready 묶음에서 보존 배열의 추가 할당 비용과 재전송 감소 효과는 각각 어느 정도인가?
- snapshot 별도 경로와 일반 메시지 경로가 만나는 지점에서는 어떤 순서 조건을 별도로 유지하는가?
