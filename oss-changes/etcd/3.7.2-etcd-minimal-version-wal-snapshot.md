## 개요

etcd v3.7.2는 최소 호환 버전을 검사할 때 WAL을 다시 여는 기준을 v2 snapshot 파일에서 WAL 내부 snapshot 기록으로 옮겼다. v3store 중심으로 바뀐 3.7의 부트스트랩 설계에서 남아 있던 v2 읽기 의존성을 줄이는 후속 변경이다. [구현 diff](https://github.com/etcd-io/etcd/pull/22201/files)

## 사전 지식

### snapshot과 WAL의 역할

복제 저장소는 현재 상태와 그 상태를 만든 변경 기록을 구분한다. snapshot은 특정 시점의 상태를 나타내며, WAL은 변경을 순서대로 보관하는 로그다. 여기서 다루는 **WAL snapshot entry**는 데이터베이스 전체를 복제한 파일이 아니라, WAL 안에 들어 있는 snapshot 기준 기록이다. 이 구분이 있어야 snapshot 파일을 읽는 일과 WAL에서 snapshot 기준을 찾는 일이 서로 다른 경로임을 이해할 수 있다.

`MinimalEtcdVersion`은 이번 diff에서 WAL을 `Reopen`하기 전에 기준 snapshot을 구한다. index는 로그 위치, term은 Raft의 선거 세대, ConfState는 합의 참여 구성에 해당한다. 이번 변경의 범위는 **이 재개방 기준을 어디서 얻는가**이다. [구현 diff](https://github.com/etcd-io/etcd/pull/22201/files)

### v3store로 옮겨 가는 과정

설계 이슈는 v3.6에서 membership을 포함한 데이터의 기준이 v3store가 되었는데도, 당시 bootstrap은 v2 snapshot을 읽고 그 위치부터 WAL을 재생하던 차이를 설명한다. 3.7의 전환 방향은 v3store의 consistent index를 기준으로 시작하는 것이었다. 따라서 과거 snapshot 파일을 읽는 경로가 다른 기능에 남아 있는지도 별도로 살펴야 했다. [설계 이슈 #20187](https://github.com/etcd-io/etcd/issues/20187)

전체 bootstrap 전환은 3.7.0 계열에 이미 들어온 배경이며, v3.7.2에서 새로 도입한 기능으로 해석하면 안 된다. 이번 원본 PR은 최소 버전 검사에 남은 v2 snapshot 읽기를 누락 사례로 지적하고 3.7 backport를 요구했다. [원본 PR #22171](https://github.com/etcd-io/etcd/pull/22171)

## 변경 분석

### 버전 검사에 남아 있던 두 저장 경로의 결합

변경 전 경로는 WAL을 검사하기 위해 먼저 별도 snapshot loader에 의존했다. 새 경로는 WAL 계층이 제공하는 `LatestSnapshotEntry`를 사용한다. [구현 diff, head 23b61e6](https://github.com/etcd-io/etcd/pull/22201/files)

변경 전:

```text
+---------------------+
| MinimalEtcdVersion  |
+-----------+---------+
            |
            v
+---------------------+
| v2 snapshot Load    |
+-----------+---------+
            | index / term / ConfState 복사
            v
+---------------------+
| WAL Reopen          |
| 버전 검사 경로 계속 |
+---------------------+
```

`LatestSnapshotEntry`는 `ValidSnapshotEntries` 결과의 마지막 항목을 선택한다. 코드 주석상 유효한 항목은 snapshot index가 가장 최근 committed hardstate 이하인 기록이다. 유효한 snapshot이 없으면 빈 구조체를 반환한다. [구현 diff](https://github.com/etcd-io/etcd/pull/22201/files)

## 설계 결정 및 트레이드오프

### WAL 기준으로 일원화하면서 생기는 파일 정리 경쟁

원본 PR 리뷰는 WAL을 읽는 사이 다른 goroutine이 오래된 WAL 파일을 정리할 가능성을 짚었다. 목록을 확인한 뒤 파일을 열기 전에 파일이 사라질 수 있다는 문제다. 논의에서 시도 횟수를 3회로 제한했고 실제 diff에도 반영됐다. 이 경로가 항상 성공한다고 보장하는 설계는 아니다. [원본 PR의 리뷰 논의](https://github.com/etcd-io/etcd/pull/22171)

변경 후:

```text
+-------------------------+
| MinimalEtcdVersion      |
+-----------+-------------+
            v
+-------------------------+
| WAL LatestSnapshotEntry |
+-----------+-------------+
            v
+-------------------------+
| ValidSnapshotEntries    |
| 유효 기록 중 마지막     |
+-----------+-------------+
            | 파일 소멸 오류만 제한 재시도
            v
+-------------------------+
| WAL Reopen              |
| 버전 검사 경로 계속     |
+-------------------------+
```

다음 비교 중 책임 경계와 비용은 코드로부터의 분석이며, 경쟁 조건과 시도 제한은 PR에 명시된 결정이다.

- **v2 읽기 유지**: 기존 호출 경로 유지가 가능하지만 v3store 전환 이후에도 과거 snapshot reader에 남는 의존성
- **WAL 직접 조회**: 같은 저장 계층에서 얻는 검사 기준, 대신 파일 조회와 정리의 경쟁을 처리할 필요
- **제한 시도**: `os.ErrNotExist`에만 최대 3회 전체 시도, 즉 최초 시도 이후 최대 2회 재시도; 다른 오류 또는 시도 소진 시 실패 반환

`ValidSnapshotEntries`가 끝내 오류를 반환하면 `MinimalEtcdVersion`은 이를 `panic`으로 처리한다. 재시도 소진 후 빈 snapshot으로 계속 진행하는 경로는 아니다.

추가 테스트는 첫 파일 open에만 파일 소멸 오류를 주입하고 정상 결과와 같은지 비교한다. 검증 범위는 이 일시 오류 경로에 한정된다. [구현과 테스트 diff](https://github.com/etcd-io/etcd/pull/22201/files)

## 더 살펴볼 점

최소 버전 검사의 호출 경로에서 반복되는 WAL 정리 경쟁을 어떻게 관측할 수 있을까?

후속 릴리스에서 v2 snapshot 생성까지 제거할 때 이전 버전과의 호환 경계는 어떻게 정리될까?
