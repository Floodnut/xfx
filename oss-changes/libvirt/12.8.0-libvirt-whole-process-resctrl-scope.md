## 개요

libvirt v12.8.0은 resctrl 설정의 범위를 vCPU 목록에서 QEMU 프로세스 전체로 확장했다. `cachetune`, `memorytune`, `energytune`에서 `vcpus`를 생략하면 전체 프로세스 범위가 된다. 핵심은 생성된 스레드를 나중에 모아 배치하는 대신, QEMU가 실행되기 전 부모 PID를 resctrl 그룹에 넣어 이후 생성되는 vCPU, I/O 스레드, worker가 그룹을 상속하게 한 점이다. XML 파싱, 시작 순서, monitor 범위와 통계 표현을 함께 바꿔 전체 VM 프로세스에 대한 자원 관리 의도를 일관되게 전달한다.

## 사전 지식

### vCPU 목록은 QEMU 전체 작업의 목록이 아니다

QEMU는 guest CPU를 실행하는 vCPU 스레드 외에도 I/O와 보조 작업을 수행한다. 따라서 `vcpus='0-3'`은 guest의 네 CPU에 대응하는 실행 스레드를 선택하는 표현이며, QEMU 안에서 발생하는 모든 작업을 선택한다는 의미는 아니다. 이 구분은 CPU 실행량뿐 아니라 공유 cache, memory bandwidth, energy 사용을 VM 단위로 관찰할 때도 중요하다.

libvirt는 domain XML의 `cputune` 아래에서 resctrl 설정을 받는다. `cachetune`은 cache 할당, `memorytune`은 memory bandwidth 할당, `energytune`은 energy monitoring 범위를 표현한다. 지원 기능과 최소 할당 단위는 host capability에 의존한다. 이 개념과 기존 `vcpus` 필수 조건은 [설정 문서와 parser 변경 diff](https://gitlab.com/libvirt/libvirt/-/commit/9328b069e008baa013754149a3114dd2c50ef7d7)에서 함께 확인할 수 있다.

### allocation과 monitor의 역할

allocation은 어떤 자원 정책을 적용할지, monitor는 어느 실행 집합의 사용량을 관찰할지를 구분한다. 예를 들어 하나의 allocation 아래에서 일부 vCPU만 따로 관찰할 수 있다. 기존 parser는 monitor가 allocation의 vCPU 범위 밖으로 벗어나지 않는지도 검사했다.

resctrl의 그룹 소속은 스레드 생성과 상속에 연결된다. 이번 구현은 이 특성을 이용한다. 이미 여러 스레드가 생긴 뒤 PID 하나를 배치하는 것과, 스레드를 만들기 전에 QEMU의 PID를 배치하는 것은 같은 범위를 보장하지 않는다. [시작 경로 commit](https://gitlab.com/libvirt/libvirt/-/commit/33c55165c9236b8b0d2729ded0a6108409fd752a)은 pre-exec handshake 시점을 선택한 이유를 이후 스레드의 그룹 상속으로 명시한다.

## 변경 분석

### 변경 전: vCPU 집합으로만 표현하던 자원 범위

`9328b069`의 이전 `virDomainResctrlParseVcpus()`는 `vcpus` 속성이 없으면 XML 오류를 반환했다. 전체 프로세스를 의미하는 별도 상태가 없으므로, 사용자는 vCPU 목록을 작성해야 했다. `33c55165` 이전 `qemuProcessResctrlCreate()`는 allocation과 monitor를 만들지만 전체 emulator PID를 그룹에 넣는 분기가 없었다. vCPU별 설정 경로는 해당 vCPU가 bitmap에 포함되는지 확인하고 그 스레드 PID를 allocation에 넣었다.

이 구조에서 모든 vCPU 번호를 나열해도 설정이 뜻하는 범위는 vCPU 집합이다. I/O 스레드와 worker까지 포괄하는 전체 프로세스 정책은 같은 XML로 표현할 수 없다. 다음 그림은 이 resctrl 설정 경로의 범위를 나타내며, 별도의 host 정책까지 없었다는 뜻은 아니다.

```diagram
type: flow
title: 변경 전 vCPU 목록을 통한 그룹 배치
direction: down
nodes:
  - id: xml
    label: vcpus 속성이 필요한 XML
  - id: create
    label: allocation과 monitor 생성
  - id: match
    label: 각 vCPU 번호와 bitmap 비교
  - id: assign
    label: 선택된 vCPU 스레드 PID 배치
  - id: boundary
    label: 전체 QEMU 프로세스 범위는 표현 불가
edges:
  - from: xml
    to: create
  - from: create
    to: match
  - from: match
    to: assign
  - from: assign
    to: boundary
```

### 속성 생략을 명시적인 범위 상태로 변환

새 parser는 `vcpus`가 없으면 `wholeProcess`를 설정한다. 내부 bitmap은 비어 있지만, 이는 대상이 없다는 의미가 아니라 별도 플래그로 구별되는 전체 프로세스 범위다. XML schema도 속성을 선택 사항으로 바꾸고, 출력 시 전체 프로세스 설정에는 `vcpus`를 다시 붙이지 않는다. 따라서 입력, 내부 상태, 출력이 같은 범위를 유지한다. 근거는 [parser, 구조체, schema와 formatter diff](https://gitlab.com/libvirt/libvirt/-/commit/9328b069e008baa013754149a3114dd2c50ef7d7)다.

monitor에서 속성을 생략할 때는 바깥 allocation 범위를 상속한다. 바깥이 `vcpus='0-1'`이면 monitor 역시 그 두 vCPU 범위이고, 바깥도 전체 프로세스 범위여야 monitor가 전체 프로세스를 뜻한다. 단순히 모든 `vcpus` 생략을 전역 범위로 읽지 않는 것이 중요하다. 추가된 `cachetune-monitor-inherit-alloc` 테스트는 이 범위 상속을 출력 XML로 확인하도록 구성되어 있다.

### 실행 전 배치로 이후 생성되는 스레드까지 포함

[QEMU 시작 경로 변경](https://gitlab.com/libvirt/libvirt/-/commit/33c55165c9236b8b0d2729ded0a6108409fd752a)에서 `qemuProcessResctrlCreate()`는 전체 프로세스 allocation이 비어 있지 않으면 `vm->pid`를 allocation에 넣는다. 전체 프로세스 monitor에도 같은 PID를 넣는다. 이 처리는 pre-exec handshake 중에 수행되므로 QEMU가 이후 만드는 vCPU, I/O 스레드, worker는 이미 정해진 그룹을 상속한다. [v12.8.0의 실제 시작 코드](https://gitlab.com/libvirt/libvirt/-/blob/940c2352cec2f7759d73ad8725d3ce7f3651cbe9/src/qemu/qemu_process.c#L2910)에도 이 분기가 존재한다.

이후 `qemuProcessSetupVcpu()`는 전체 프로세스 allocation에 대한 vCPU별 재배치를 생략한다. 다만 그 아래에 명시적인 vCPU monitor가 있으면 해당 스레드를 monitor에 배치하는 동작은 남긴다. 자원 할당 범위를 전체로 잡으면서 일부 vCPU 사용량을 따로 보는 조합을 유지한 것이다.

### 통계에서도 전체 범위를 빈 vCPU 목록과 구별

[통계 변경 commit](https://gitlab.com/libvirt/libvirt/-/commit/0ce7430ba8209ed1c424c7a7caa54b5d86e7c05e)은 전체 프로세스 monitor의 `vcpus` 문자열을 만들지 않고, cache, memory bandwidth, energy 통계의 해당 typed parameter를 생략한다. 따라서 이 필드를 읽는 관리 도구는 필드 부재를 단순히 빈 vCPU 목록으로 해석해서는 안 된다. 이는 빈 bitmap을 별도 플래그와 함께 해석하는 내부 모델을 외부 통계에도 반영한 변화다.

## 설계 결정 및 트레이드오프

### 범위 상속을 사용하되 혼합 allocation은 거부

실제 선택은 pre-exec PID 배치와 커널의 그룹 상속이다. 생성된 스레드들을 나중에 열거해 각각 넣는 방법은 비교 가능한 대안이지만, 검토한 commit에는 이를 공식 대안으로 평가한 기록이 없다. 여기서는 설계상 비교로만 다룬다. 현재 구현은 스레드 종류를 하나씩 열거하지 않아도 이후 생성 경로에 같은 범위를 적용할 수 있지만, 그 의미를 유지하려면 일부 vCPU가 다른 allocation으로 빠져나가는 설정을 막아야 한다.

`virDomainResctrlValidateScope()`의 주석은 이 이유를 직접 설명한다. 전체 프로세스 allocation과 vCPU별 allocation을 섞으면 명시적인 vCPU 배치가 그 스레드를 전체 그룹 밖으로 옮기기 때문에, parser가 혼합을 거부한다. 반면 전체 allocation 아래의 vCPU별 monitor는 허용한다. 다음 제약은 [검증 코드와 XML 테스트](https://gitlab.com/libvirt/libvirt/-/commit/9328b069e008baa013754149a3114dd2c50ef7d7)에 근거한다.

- domain 내 전체 프로세스 allocation과 vCPU별 allocation의 혼합 금지
- 같은 allocation 내 전체 프로세스 monitor와 명시적 vCPU monitor의 혼합 금지
- 자원 종류별 전체 프로세스 monitor 중복 금지
- 전체 프로세스 allocation 아래 명시적 vCPU monitor 허용

```diagram
type: flow
title: 변경 후 실행 전 그룹 배치와 범위 상속
direction: down
nodes:
  - id: xml
    label: vcpus 생략으로 전체 범위 선언
  - id: validate
    label: 범위 혼합과 monitor 중복 검증
  - id: preexec
    label: pre-exec에서 QEMU PID 그룹 배치
  - id: inherit
    label: 이후 생성 스레드가 그룹 상속
  - id: whole
    label: 전체 프로세스 allocation 유지
  - id: monitor
    label: 선택 시 vCPU별 monitor 추가 배치
edges:
  - from: xml
    to: validate
  - from: validate
    to: preexec
  - from: preexec
    to: inherit
  - from: inherit
    to: whole
  - from: whole
    to: monitor
```

### 전체 프로세스의 경계와 검증 범위

이 기능은 기존 vCPU별 조정 방식에 전체 프로세스 범위를 추가한다. 전체 범위를 선택하면 일부 vCPU만 다른 allocation 정책으로 분리하는 자유는 포기해야 한다. 대신 QEMU가 나중에 생성하는 스레드까지 같은 정책에 포함한다. 그룹 경로 역시 전체 범위에서는 vCPU suffix 없이 machine 이름을 사용하도록 변경됐다.

상속에 기반하므로 별도로 시작된 모든 VM 보조 프로세스까지 자동 포함된다고 확대해석해서는 안 된다. 확인한 코드와 문서는 QEMU 프로세스와 그 스레드, 자식 프로세스의 범위를 설명한다. 또한 이번 정적 분석은 XML 왕복 변환, 잘못된 조합 거부 테스트와 시작 경로를 확인한 것이며, 실제 장비에서의 성능 개선 수치나 실행 중 범위 변경을 검증한 결과는 아니다.

## 더 살펴볼 점

- 전체 allocation 아래 vCPU별 monitor를 쓸 때 I/O 작업의 사용량을 함께 해석할 기준
- VM 관리 도구가 통계의 `vcpus` 필드 부재를 전체 프로세스 범위로 처리하는지 여부
- QEMU와 별도로 실행되는 보조 프로세스까지 관찰해야 하는 환경의 범위 정의
