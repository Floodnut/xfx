## 개요

libvirt v12.6.0은 QEMU 가상 머신의 `<on_crash>`에 `preserve-running`을 추가했다. 기존 정책은 guest가 panic을 알리면 QEMU를 멈춘 뒤 libvirt가 종료, 재시작, 보존, core dump 처리 중 하나를 맡는 구조였다. 새 정책은 panic 통지는 기록하되 QEMU를 멈추지 않아, Windows처럼 guest 내부에서 crash dump를 쓴 뒤 스스로 재부팅하는 운영체제가 자신의 복구 절차를 끝낼 시간을 준다.

## 사전 지식

### libvirt domain lifecycle action

libvirt domain XML의 `<on_poweroff>`, `<on_reboot>`, `<on_crash>`는 guest가 전원 종료, 재부팅, crash를 알렸을 때 host가 취할 lifecycle 정책을 선언한다. 기존 crash 정책에는 `destroy`, `restart`, `preserve`, `coredump-destroy`, `coredump-restart`가 있었다. `preserve`는 domain을 메모리에 남겨 수동 분석을 가능하게 하지만, guest 실행을 계속 허용한다는 뜻은 아니다.

QEMU driver는 이 선언을 QMP의 `set-action` 명령으로 QEMU에 전달한다. panic action이 `pause`이면 QEMU는 guest panic 통지를 받은 직후 guest CPU 실행을 멈춘다. 그 뒤 libvirt의 panic-event 처리기가 domain 상태와 lock, 프로세스 종료, 재시작, host 쪽 core dump 처리를 결정한다.

### crash 통지와 guest 내부 복구는 서로 다른 단계

guest OS가 panic을 QEMU에 알리는 일과 crash dump를 쓴 뒤 재부팅하는 일은 항상 같은 순서가 아니다. 구현 commit은 일부 guest OS가 자체 dump와 reboot를 수행할 수 있지만, dump를 쓰기 전에 host에 crash를 먼저 통지한다고 설명한다. host 정책이 통지를 받은 즉시 QEMU를 pause하면, guest가 아직 실행해야 할 dump writer와 reboot 경로도 함께 멈춘다.

### lock과 domain 상태의 의미

libvirt는 실행 중 domain이 사용하는 disk, network, host resource의 소유권을 lock state로 관리한다. crash 뒤 domain을 종료하거나 재시작하려면 이 자원을 정리하거나 다시 획득해야 한다. 반대로 guest를 계속 실행하게 하려면 QEMU 프로세스와 자원 lock을 유지하면서, 관리 도구에는 실행 중이지만 crash를 경험했다는 상태를 별도로 보여야 한다.

## 변경 분석

### 변경 전: crash 통지가 guest 자체 복구보다 먼저 실행을 멈춘다

`cdea89dd` 이전 QEMU driver의 lifecycle setup은 `onReboot=destroy`만 QMP action으로 특별 처리했다. `30a548c`의 이전 코드는 이 제한을 명시적으로 남기고 나머지 shutdown, watchdog, panic action은 `KEEP`으로 QMP에 전달했다. 실행 중 lifecycle update도 reboot action만 바꿀 수 있었다.

이 구조에서 v12.6.0이 지원하던 기존 `<on_crash>` 결과는 QEMU panic action을 `pause`로 두고, panic event 뒤 libvirt가 host 관점의 정책을 실행하는 흐름이다. `preserve`는 종료하지 않은 domain의 메모리를 남겨 분석할 수 있지만, guest가 계속 실행해 자기 dump를 쓰고 reboot하도록 하는 경로는 아니었다.

```
[변경 전] host가 panic 직후 QEMU 실행을 멈춘다

Guest OS
  │ panic 통지
  ▼
QEMU panic action = pause
  │ guest CPU 실행 정지
  ▼
libvirt QEMU driver
  ├── destroy 또는 restart
  ├── preserve 후 수동 분석
  └── host 쪽 core dump 후 종료 또는 재시작

결과: guest 내부 crash dump와 자체 reboot는 pause 이전에 끝나야 한다.
```

### 변경 후: panic을 상태로 기록하고 guest 실행과 lock을 유지한다

구현 commit은 공통 `VIR_DOMAIN_LIFECYCLE_ACTION_PRESERVE_RUNNING` enum과 XML 값 `preserve-running`을 추가했다. domain XML 문서도 이 값을 v12.6.0부터 guest가 내부 crash dump와 reboot를 직접 수행할 때 쓰는 정책으로 설명한다.

QEMU 시작 경로 `qemuProcessSetupLifecycleActions()`는 `<on_crash>preserve-running</on_crash>`일 때 QMP panic action을 `NONE`으로 설정한다. 다른 crash 정책은 `PAUSE`를 선택한다. `qemuDomainModifyLifecycleActionLive()`도 같은 shutdown, reboot, watchdog, panic action 구조로 일반화되어, 실행 중 정책 변경에서 crash action을 업데이트할 수 있다.

QEMU가 panic event를 보낸 뒤 `processGuestPanicEvent()`는 이 정책에서 domain 상태를 `RUNNING`과 사유 `CRASHED`로 기록하고 상태를 저장한다. 구현은 preserve-running의 경우 lock을 유지해야 한다고 명시하고, 종료, 재시작, host core dump를 수행하는 분기로 들어가지 않는다. 따라서 guest는 QEMU 안에서 계속 실행되며 자신의 dump 작성과 reboot 절차를 완료할 수 있다.

회귀 테스트도 기존 async teardown XML의 `<on_crash>` 값을 `destroy`에서 `preserve-running`으로 바꾸고, QEMU XML configuration test가 이 action을 검사하도록 추가됐다. 이는 문법만 늘린 변경이 아니라 QEMU driver의 실제 lifecycle 설정과 상태 처리 경로가 함께 바뀐 근거다.

## 설계 결정 및 트레이드오프

### QMP action을 일반화한 뒤 panic 정책을 추가한 이유

보조 commit `30a548c`는 시작 경로를, `79b6d701`은 live update 경로를 각각 일반화했다. 이전 코드는 reboot만 조정했지만, 변경 뒤에는 shutdown, reboot, watchdog, panic 값을 모두 `qemuMonitorSetAction()`에 전달할 수 있다. preserve-running은 이 공통 경로에서 panic만 `NONE`으로 바꾸는 작은 정책 추가가 된다.

`771f17c`은 `set-action` QMP 명령이 QEMU 6.0에 도입됐고 libvirt가 지원하는 최저 QEMU가 7.2이므로, capability check 없이 이 명령을 항상 쓸 수 있다고 정리했다. 이 선택은 panic 정책 구현을 단순하게 하지만, 기능 범위를 libvirt가 보장하는 QEMU 버전대에 묶는다.

즉시 pause, destroy, restart를 유지하는 기존 정책은 host가 crash 이후 자원을 빠르게 회수하고 결과를 결정해야 할 때 여전히 적합하다. preserve-running은 guest가 복구 주체가 되는 경우만 겨냥한다. 그래서 이 정책의 대가는 명확하다.

- crash 뒤에도 guest CPU, disk, network, lock이 계속 점유되는 운영 부담
- guest가 dump 또는 reboot에 실패했을 때 host가 자동으로 회수하지 않는 상태
- QEMU driver에 한정된 동작 차이
- 실행 중이지만 crash 상태인 domain을 관찰하고 수동 개입할 monitoring 요구

```
[변경 후] panic 통지는 남기되 guest가 자체 복구를 끝낼 때까지 실행을 유지한다

Domain XML
  <on_crash>preserve-running</on_crash>
  │
  ▼
libvirt QEMU driver
  ├── 시작 또는 live update: QMP set-action panic = none
  ▼
Guest OS panic 통지
  │
  ▼
processGuestPanicEvent()
  ├── domain state = RUNNING, reason = CRASHED
  ├── QEMU 프로세스와 resource lock 유지
  └── 종료, 재시작, host core dump 분기 생략
          │
          ▼
guest 내부 crash dump 작성 후 자체 reboot
```

## 더 살펴볼 점

- `RUNNING/CRASHED` 상태를 monitoring 시스템과 자동 복구 정책이 어떻게 구분할지
- guest 자체 dump가 끝나지 않을 때 운영자가 적용할 timeout과 강제 회수 기준
- QEMU 외 driver가 동일한 crash 복구 의미를 제공할 필요가 있는지
