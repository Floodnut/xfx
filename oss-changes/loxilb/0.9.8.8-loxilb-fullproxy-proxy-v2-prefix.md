## 개요

LoxiLB는 fullproxy 모드의 backend 연결에 PROXY protocol v2 헤더를 먼저 전송하는 기능을 추가했다. 프록시가 만든 별도의 TCP 연결에서도 backend가 원래 클라이언트 주소와 포트를 알 수 있게 하는 변경이다. 핵심은 주소 정보를 패킷 내부에 끼워 넣는 대신, 새 backend 소켓에 애플리케이션 데이터와 선택적 TLS handshake보다 먼저 쓰는 것이다. 기존 fullnat 경로를 교체한 변경이 아니라 fullproxy 경로에 같은 목적의 기능을 추가한 것이며, 이 보고서는 v0.9.8.7에 도입되고 v0.9.8.8에 유지된 구현을 다룬다.

## 사전 지식

### 프록시 연결은 원래 클라이언트 연결과 다르다

fullproxy는 클라이언트가 접속한 소켓과 backend에 접속하는 소켓을 따로 관리한다. backend 연결을 만드는 `proxy_setup_ep_connect()`는 endpoint 주소로 새 소켓을 생성하고 `connect()`를 호출한다. 이 연결 자체의 상대편은 프록시이므로, 원래 클라이언트의 주소를 전달하려면 별도의 정보 전달 방법이 필요하다.

이 코드에는 backend TLS를 사용하는 경우도 있다. 연결 수립 후 `ssl_ctx`가 있으면 TLS 객체를 만들고 handshake를 진행한다. 따라서 연결의 첫 바이트에 어떤 형식을 놓을지는 단순한 메타데이터 선택이 아니라, backend가 연결을 해석하는 순서에 영향을 주는 결정이다. [변경 전 연결 수립 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/e706682b9223dd2695b97e00f5bbf54c3aed414b/common/sockproxy.c#L730)

### PROXY v2는 연결 앞부분의 주소 정보다

이번 구현은 IPv4/TCP용 PROXY v2 헤더를 28바이트로 만든다. 16바이트 공통 영역 뒤에 클라이언트 IPv4 주소, 목적지 IPv4 주소, 두 포트를 담는 12바이트 주소 영역을 붙인다. 이는 backend TCP 연결의 IP 헤더를 원래 클라이언트 주소로 바꾸는 동작이 아니다. 수신 측이 먼저 해석할 수 있도록 스트림 앞부분에 주소 정보를 추가하는 방식이다.

여기서 목적지는 backend endpoint 주소가 아니라 **클라이언트가 접속한 VIP**다. `setup_proxy_path()`는 받아들인 클라이언트 소켓의 peer 주소와 local 주소로 헤더를 만든다. 이후 선택되는 backend는 그 정보를 전달받는 상대이고, 헤더가 설명하는 원래 접속 목적지는 VIP로 남는다. [헤더 생성과 주소 선택 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/common/sockproxy.c#L1904)

## 변경 분석

### fullproxy 연결에 없던 선행 전송 단계

변경 전 `proxy_setup_ep_connect()`는 TCP 연결을 수립한 뒤 곧바로 선택적 TLS 초기화로 진행했다. 함수 인자에도 PROXY 헤더가 없었다. 따라서 기존 fullproxy 연결 수립 경로에는 원래 클라이언트 주소를 PROXY v2 형식으로 먼저 내보내는 단계가 없었다. 이는 기존 fullnat 기능의 존재 여부와 구분해야 한다. 이 보고서의 변경 전후 비교 대상은 fullproxy의 backend 연결 수립 경로다. ### 설정 전달과 연결 수립을 함께 변경

구현 diff는 `proxy_arg`와 `proxy_val`에 `ppv2` 플래그를 추가한다. NAT action을 proxy 설정으로 변환할 때 플래그를 넘기고, `proxy_add_entry()`가 이를 규칙 상태에 저장한다. 연결 처리 코드는 이 상태를 읽어 PPv2가 켜진 TCP 규칙에만 헤더를 만든다. 옵션을 인식하는 일과 실제 backend 연결에 적용하는 일이 이어진 것이다. [구현 diff](https://github.com/loxilb-io/loxilb-ebpf/commit/84fcb5fe39c1e4fc502c340fe9f3e47482a2172f)

헤더는 클라이언트 주소에서 한 번 만들어 endpoint 설정 함수에 전달된다. endpoint 설정 함수는 backend 연결 생성 함수에 같은 헤더를 전달하므로, 각 backend 연결은 자기 스트림의 시작에서 헤더를 받는다. 새 `proxy_setup_ep_connect()`는 TCP 연결 완료 후 헤더 전송을 마친 다음에야 선택적 TLS 초기화로 넘어간다. 헤더 전송이 실패하면 소켓을 닫고 실패를 반환한다. [릴리스의 연결 수립 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/common/sockproxy.c#L773)

이 순서는 헤더가 TLS 데이터 안에 섞이거나 일부만 전송된 상태에서 다음 단계가 진행되는 것을 막는다. `proxy_send_all()`은 짧은 쓰기가 발생하면 전송한 길이만큼 위치를 옮겨 나머지를 보낸다. 재시도 가능한 오류에서는 `poll()`로 쓰기 가능 상태를 기다린다. 코드의 500ms는 각 `poll()` 호출의 제한이며, 함수 전체의 누적 실행 시간을 500ms로 제한하는 deadline은 아니다. [전송 완료 처리](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/common/sockproxy.c#L752)

## 설계 결정 및 트레이드오프

### 패킷을 편집하는 대신 소켓의 전송 순서를 이용

fullproxy는 이미 backend TCP 소켓을 직접 만드는 계층이다. 여기에 선행 쓰기를 추가하면 PROXY 헤더와 뒤따르는 데이터의 순서를 소켓 스트림에서 표현할 수 있다. 헤더 전송 코드는 패킷별 segmentation 상태를 검사하지 않고 `send()`로 바이트를 보낸다. 이는 커널 패킷 내부 공간을 늘려 헤더를 삽입하는 접근과 책임 경계가 다르다.

구현 PR은 기존 fullnat의 GSO 관련 문제를 동기로 설명한다. 다만 이 변경은 fullnat의 패킷 처리 코드를 수정하지 않는다. fullnat 문제의 별도 수정 여부와 무관하게, 여기서 검증할 수 있는 설계는 **fullproxy backend 연결의 시작 순서를 명시적으로 확장한 것**이다. 커널 segmentation 전체 동작이나 모든 환경의 성능 우위까지 이 diff로 입증할 수는 없다.

코드에서 읽을 수 있는 선택과 비용은 다음과 같다.

- **연결 수립 단계의 순서 보장**: TLS 초기화와 데이터 처리보다 앞선 주소 헤더 전송
- **Backend의 프로토콜 이해 필요**: 일반 데이터보다 먼저 도착하는 PPv2 헤더를 해석할 수 있는 수신 설정
- **연결 시작 시 대기 가능성**: 헤더 전송이 밀리면 `poll()`과 재시도를 거친 뒤 다음 단계 진행
- **실패 시 연결 종료**: 불완전한 헤더 뒤에 TLS나 애플리케이션 데이터를 이어 보내지 않는 처리
- **IPv4/TCP 범위**: IPv4 주소와 TCP family 값으로 고정된 헤더 생성, IPv6용 형식은 별도 구현 필요

이 비용은 fullproxy 자체의 별도 소켓 관리 위에 추가된다. 해당 변경에는 fullnat 대비 처리량이나 지연을 일반화할 측정 자료가 없으므로, 성능 수치 대신 구현이 보장하는 전송 순서와 지원 범위로 판단해야 한다. [헤더 형식과 전송 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/common/sockproxy.c#L732)

## 더 살펴볼 점

IPv6를 추가할 때 헤더 생성뿐 아니라 클라이언트 주소를 보관하는 경로도 함께 확장해야 할까?

Backend의 연결 수립 지연과 헤더 쓰기 지연을 각각 관측하면 운영 중 실패 원인을 더 쉽게 구분할 수 있을까?
