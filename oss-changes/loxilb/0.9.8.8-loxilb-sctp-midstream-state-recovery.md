## 개요

LoxiLB v0.9.8.8은 SCTP 연결 추적 상태가 CLOSED일 때 이미 진행 중인 통신의 일부 패킷을 받아 EST로 복구하는 경로를 재통합했다. 기존 경로는 DSR 예외를 제외하면 최초 INIT 패킷을 요구했으므로, 로드밸런서의 로컬 상태와 양 끝단의 통신 상태가 어긋난 상황에서 데이터나 heartbeat를 오류로 처리할 수 있었다. 새 경로는 inbound 방향, NAT 설정, 0이 아닌 verification tag, 제한된 chunk 종류를 함께 검사한다. 핵심은 전체 handshake 이력을 재구성하는 대신 제한된 중간 흐름 관측으로 로컬 상태를 다시 established로 분류하는 선택이다.

## 사전 지식

### 통신 당사자의 상태와 로드밸런서의 관측 상태

SCTP 통신을 추적하는 로드밸런서는 패킷을 보면서 자체 상태를 관리한다. 여기서 CLOSED는 `dp_ct_sctp_sm()`이 읽는 로컬 연결 추적 상태다. 이 값만으로 양 끝단의 애플리케이션 통신도 종료되었다고 단정할 수는 없다. 예를 들어 로컬 추적 정보가 사라진 뒤 기존 통신의 패킷을 다시 관측하면, 추적기는 시작 상태에서 중간 패킷을 해석해야 한다. 최초 구현 커밋도 idle aging 뒤 재개되는 트래픽을 변경 동기로 명시한다. [최초 구현](https://github.com/loxilb-io/loxilb-ebpf/commit/869b4d1fa977711e43c85d3a185c99189fdc96fa)

기존 코드는 inbound INIT을 읽으면 초기 tag를 저장하고 INIT 상태로 이동한다. 이후 INIT ACK와 cookie 관련 상태를 거치며 저장한 tag와 패킷의 verification tag를 비교하는 분기가 있다. handshake를 처음부터 관측한 경우에는 이런 이력을 이용할 수 있다. 반면 데이터 전송 중간부터 관측하면 INIT에 들어 있던 정보를 같은 방식으로 얻을 수 없다. [릴리스 상태 기계](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L851)

### 상태 판정은 NAT 추적 정보의 생명주기로 이어진다

함수는 정방향과 역방향 추적 구조를 받아 양쪽 SCTP 상태를 갱신하고, 호출자에게 EST, ERR 등의 결과를 반환한다. 따라서 EST는 단순한 표시 문자열이 아니다. 호출자는 결과에 따라 established 처리 또는 정방향과 역방향 `ct_map` 항목 및 관련 fast-cache 제거를 수행한다. 특히 `CT_SMR_ERR`는 추적 정보를 정리하는 분기로 이어진다. 중간 패킷을 처음부터 잘못된 연결로 분류하면 이후 NAT 처리에 필요한 추적 상태도 유지하기 어려워지는 이유다. [상태 반환](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L1400), [호출자의 정리 분기](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L1875)

## 변경 분석

### CLOSED에서 INIT만 허용하던 경로

변경 전 `CT_SCTP_CLOSED` 분기는 DSR이면 바로 EST로 이동했다. DSR이 아니면 inbound INIT만 정상 시작으로 받아들였다. DATA, SACK, heartbeat 같은 패킷은 INIT이 아니므로 ERR로 이동했다. 이 설계는 연결 시작을 관측했다는 전제에는 맞지만, 이미 살아 있는 통신을 뒤늦게 관측하는 경우를 구분하지 못한다. [변경 전 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/6b83b070c1243e1914098f6c375ebdc44188dc2d/kernel/llb_kern_ct.c#L911)

### 제한된 패킷 종류를 established의 관측 근거로 사용

PR #90의 최종 diff는 DSR 분기 다음, 기존 INIT 검사 앞에 복구 분기를 넣는다. 다음 조건이 모두 맞으면 `nstate = CT_SCTP_EST`를 설정하고 공통 종료 경로로 이동한다.

- 추적 방향이 `CT_DIR_IN`
- 추적 구조의 `nat_flags`가 0이 아님
- SCTP 헤더의 `vtag`가 0이 아님
- 첫 chunk 종류가 DATA, SACK, HB_REQ, HB_ACK 중 하나

이는 모든 SCTP 패킷을 대상으로 한 허용 규칙이 아니다. 헤더와 첫 chunk의 메모리 범위 검사는 앞에서 수행하며, ERROR, SHUT, ABORT는 복구 검사보다 앞선 분기에서 처리한다. 복구 조건을 만족하지 않으면 기존 INIT 검사로 진행한다. 또한 `c`는 공통 SCTP 헤더 바로 다음 chunk를 가리키므로, 이번 조건이 패킷에 포함된 모든 chunk를 순회하며 찾는다고 해석해서는 안 된다. [복구 분기를 포함한 릴리스 코드](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L874)

복구가 성공하면 공통 종료부가 두 방향의 `state`를 EST로 바꾸고 `CT_SMR_EST`를 반환한다. 이 경로는 INIT 처리 블록을 건너뛰므로 INIT에서 수집하는 tag, multihoming 주소 목록 등의 이력을 복원하지 않는다. **추적 상태의 재분류와 원래 association 정보 전체의 복원은 다른 작업**이다. 이 diff로 보장되는 범위는 전자다. [INIT 처리 및 공통 종료부](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L918)

### 최종 변경에는 종료 상태 기계 재설계가 남아 있지 않다

최초 커밋 `869b4d1`은 CLOSED 복구와 SHUT/SHUTA 변경을 함께 추가했다. 다음 커밋 `9c1a90a`는 SHUT/SHUTA 변경을 되돌리고 CLOSED 복구만 유지했다. 따라서 최종 diff는 chunk 상수 2개와 복구 분기 7줄이다. 초기 커밋 제목만 읽으면 종료 상태 처리까지 개선되었다고 오해할 수 있지만, v0.9.8.8에서 분석해야 할 최종 설계 범위는 더 좁다. [후속 되돌림 diff](https://github.com/loxilb-io/loxilb-ebpf/commit/9c1a90aa15e9649948247ca7b15efaadf0736a1f), [재통합 PR의 최종 diff](https://github.com/loxilb-io/loxilb-ebpf/pull/90/files)

## 설계 결정 및 트레이드오프

### 엄격한 시작 관측 대신 조건부 중간 흐름 수용

기존 방식은 INIT을 관측해야 추적을 시작할 수 있다는 제약을 둔다. 최종 구현은 이 제약을 전부 없애지 않고, NAT inbound 트래픽 중 특정 운영 패킷에만 예외를 둔다. 추적기가 handshake를 놓친 상황에서 데이터 흐름을 다시 established로 분류할 수 있는 대신, 전체 handshake 이력에 기반한 판단은 할 수 없다. 이것은 코드에서 읽을 수 있는 설계의 교환 관계이며, 모든 장애 전환 환경에서 세션이 보존된다는 실험 결과는 아니다.

```diagram

direction: down

  - from: chunk
```

주의할 경계는 다음과 같다.

- **Tag 일치 검증과 구별**: 복구 분기의 조건은 `vtag != 0`, 저장된 association tag와의 동일성이나 인증을 입증하는 검사가 아님
- **입력 방향 제한**: 같은 종류의 outbound 패킷만 관측한 경우에는 이 복구 조건 불충족
- **부분 상태 복구**: INIT 블록을 거치지 않으므로 handshake 때 수집하는 multihoming 정보를 이 분기에서 재구성하지 않음
- **기존 종료 처리 유지**: SHUT/SHUTA 변경은 후속 커밋에서 철회, 종료 동작의 일반적인 개선으로 확장 해석 불가

복구 분기에는 별도 제어면 동기화나 handshake 재실행이 없다. 로컬 데이터 경로에서 관측 가능한 정보만 사용하므로 변경은 작지만, 근거도 그만큼 제한된다. 따라서 운영상의 효과를 평가할 때는 EST 전환 여부와 함께 NAT 대상의 일관성, multihoming 정보 유무를 별도로 확인해야 한다. [최종 구현](https://github.com/loxilb-io/loxilb-ebpf/blob/05742082a6cf62afdd864995f6e96ec7cab18ba4/kernel/llb_kern_ct.c#L918)

## 더 살펴볼 점

복구 분기를 통과한 연결을 별도 계수하면 정상 handshake 경로와 추적 정보 소실 뒤 재개 경로를 구분할 수 있을까?

INIT을 관측하지 못한 SCTP multihoming 통신에서는 상태 재분류 외에 어떤 주소 정보가 더 필요할까?
