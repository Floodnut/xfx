## 개요

Harvester의 `haltAfterRestore`는 백업이나 스냅샷에서 VM을 복원하는 작업과 그 VM을 기동하는 작업을 분리한다. 이전 복원 컨트롤러는 디스크 복원을 마친 뒤 VM을 시작하고 VM의 Ready 상태까지 기다려야 복원 완료를 기록했다. 새 옵션을 명시적으로 켜면 디스크 복원과 정리를 끝낸 시점에 복원을 완료하면서 VM을 정지 상태로 남길 수 있다. **생략 또는 false는 기존 기동 동작을 유지**한다. 이 보고서는 2026-05-11 도입 변경을 출발점으로 삼고, 이후 구조가 재편된 v1.9.0에서 같은 정책이 실제로 어떻게 유지되는지 확인한다.

## 사전 지식

### VM 정의, 실행 상태, 복원 작업의 구분

Harvester의 복원 요청은 `VirtualMachineRestore`라는 Kubernetes 리소스로 저장된다. 요청에는 복원할 백업과 대상 VM, 새 VM 생성 여부 등이 들어간다. 컨트롤러는 이 선언을 읽고 볼륨을 복원한 뒤, VM 정의가 복원된 PVC를 참조하도록 구성한다. VM 정의를 생성하는 것과 실행 중인 VM 인스턴스를 만드는 것은 별도 단계다. `RunStrategy`는 VM의 실행 정책이며, `Halted`는 정지를 표현한다. 따라서 디스크와 VM 정의가 준비되어 있어도 VM을 실행하지 않는 상태를 표현할 수 있다. [변경 전 복원 구현](https://github.com/harvester/harvester/blob/c3cffc1f48f4a1fa0ca7375db200dae392fcceed/pkg/controller/master/backup/restore.go)

기존 `updateStatus()`는 이 구분을 복원 완료 조건에 반영하지 않았다. 먼저 `isVolumesReady`를 확인하고, 준비되지 않았다면 PVC 대기 상태를 기록했다. 볼륨 준비 후에는 `startVM()`을 호출하고 `vm.Status.Ready`를 검사했다. VM이 준비되지 않으면 다음 조정을 기다렸고, 준비된 뒤에야 이전 PVC 정리와 복원 완료 기록으로 진행했다. 즉 복원 완료는 디스크 복원뿐 아니라 VM 기동 성공까지 포함하는 계약이었다. [변경 전 `updateStatus()`](https://github.com/harvester/harvester/blob/c3cffc1f48f4a1fa0ca7375db200dae392fcceed/pkg/controller/master/backup/restore.go)

이 계약에서는 복구된 설정을 검토하거나 네트워크 연결을 변경한 다음 직접 VM을 켜고 싶은 사용자가 곤란해진다. 시작을 막기만 하면 완료 조건인 VM Ready에도 도달할 수 없기 때문이다. 이는 코드의 상태 전이에서 도출한 운영상 함의이며, 특정 환경에서 재현 실험을 수행한 결과는 아니다.

## 변경 분석

### 기동을 생략할 때 완료 조건도 함께 변경

```diagram
type: flow
title: 변경 전 복원 완료 경로
direction: down
nodes:
  - id: request
    label: 복원 요청과 VM 정의 구성
  - id: volumes
    label: 복원 볼륨 준비 확인
  - id: start
    label: startVM 호출
  - id: ready
    label: VM Ready 대기
  - id: finish
    label: 이전 PVC 정리와 복원 완료
edges:
  - from: request
    to: volumes
  - from: volumes
    to: start
    label: 준비 완료
  - from: start
    to: ready
  - from: ready
    to: finish
    label: Ready
```

[도입 커밋](https://github.com/harvester/harvester/commit/2e71d733b20ccbfab1b5a83c3124d28dc3cbe5e8)은 `VirtualMachineRestoreSpec`과 API의 `RestoreInput`에 boolean 필드 `haltAfterRestore`를 추가했다. CRD와 OpenAPI에도 필드를 반영하여 요청을 보존하고, VM 복원 API가 생성하는 복원 리소스에 값을 전달한다. UI에서만 기동 요청을 생략하는 방식이 아니라, 컨트롤러가 반복해서 읽는 복원 작업 자체에 정책을 둔 것이다.

도입 시점에는 새 VM을 만들 때 `resolveRunStrategyFromRestoreAndBackup()`가 실행 정책을 골랐다. `haltAfterRestore=true`이면 원본 백업의 정책보다 `Halted`를 우선했고, 그 외에는 원본 정책 또는 기본 `RerunOnFailure`를 사용했다. 동시에 `updateStatus()`의 시작 호출과 Ready 대기를 모두 `!HaltAfterRestore` 조건 안으로 옮겼다. 시작 호출만 막고 Ready 대기를 남겼다면 정지 상태의 정상 복원을 완료할 수 없으므로 두 변경이 함께 필요하다. [도입 diff와 테스트](https://github.com/harvester/harvester/commit/2e71d733b20ccbfab1b5a83c3124d28dc3cbe5e8)

### v1.9.0의 실제 완료 경계

v1.9.0에서는 복원 구현이 재구성되어 도입 당시의 헬퍼를 그대로 설명하면 부정확하다. 현재 `buildVMFromRestore()`는 새 VM을 먼저 `Halted`로 생성하며, 기존 VM 갱신도 실행 정책을 `Halted`로 설정한다. `updateStatus()`는 볼륨 준비를 확인한 뒤 `ensureVMStartedAndReady()`를 거쳐 `finalizeRestore()`를 호출한다. 이 중 `ensureVMStartedAndReady()`가 `IsKeepHaltedAfterRestore()`를 검사하여 true일 때 시작 호출과 Ready 대기를 모두 건너뛴다. false일 때는 VM Ready 여부를 보고 필요하면 `StartVM()`을 요청한 뒤 아직 준비되지 않았다는 오류를 반환해 완료 경로 진입을 막는다. [v1.9.0 복원 컨트롤러](https://github.com/harvester/harvester/blob/7a1bad0f9b525f6d9b371d952f1f5bbe61c3d4c4/pkg/controller/master/backup/restore.go)

정지 옵션은 볼륨 준비 검사를 우회하지 않는다. `isVolumesReady=false`이면 해당 옵션과 무관하게 대기한다. 옵션이 켜진 정상 경로에서도 이전 PVC를 정리한 다음에야 완료 조건을 기록한다. 따라서 이 옵션의 의미는 복원 검증 전체의 생략이 아니라 **복원 완료에 VM Ready를 요구할지의 선택**이다. [v1.9.0 `updateStatus()`와 `finalizeRestore()`](https://github.com/harvester/harvester/blob/7a1bad0f9b525f6d9b371d952f1f5bbe61c3d4c4/pkg/controller/master/backup/restore.go)

| 요청 값 | 볼륨 준비 대기 | VM 시작/Ready 대기 | 완료 시 의미 |
| --- | --- | --- | --- |
| 생략 또는 false | 필요 | 필요 | 복원과 VM 준비 경로 완료 |
| true | 필요 | 생략 | 복원 완료, VM 정지 유지 |

CRD는 false가 기본이며 성공적인 복원 뒤 VM을 시작한다고 명시한다. 릴리스 소개의 자동 기동을 하지 않는다는 표현을 모든 복원 요청의 기본값 변경으로 해석해서는 안 된다. [v1.9.0 CRD](https://github.com/harvester/harvester/blob/7a1bad0f9b525f6d9b371d952f1f5bbe61c3d4c4/deploy/charts/harvester-crd/templates/harvesterhci.io_virtualmachinerestores.yaml)

## 설계 결정 및 트레이드오프

### 복원 리소스가 실행 정책의 의도를 소유

```diagram
type: flow
title: 변경 후 v1.9.0 복원 완료 경로
direction: down
nodes:
  - id: stopped
    label: VM을 Halted로 구성
  - id: volumes
    label: 복원 볼륨 준비 확인
  - id: policy
    label: haltAfterRestore 확인
  - id: keep
    label: 정지 유지, Ready 대기 생략
  - id: start
    label: 필요 시 시작하고 Ready 대기
  - id: finish
    label: 이전 PVC 정리와 복원 완료
edges:
  - from: stopped
    to: volumes
  - from: volumes
    to: policy
    label: 준비 완료
  - from: policy
    to: keep
    label: true
  - from: policy
    to: start
    label: false 또는 생략
  - from: keep
    to: finish
  - from: start
    to: finish
    label: Ready
```

명시적인 boolean을 복원 리소스에 두면 API 호출 후에도 컨트롤러가 동일한 의도를 다시 읽을 수 있다. v1.9.0의 API 전달 코드와 `IsKeepHaltedAfterRestore()`는 이 값이 요청부터 조정 단계까지 이어짐을 보여준다. 대신 복원 완료 상태를 소비하는 자동화는 정지 복원을 성공으로 처리하되, VM이 실제 실행 중이라는 뜻으로 오해하지 않아야 한다. [API 전달](https://github.com/harvester/harvester/blob/7a1bad0f9b525f6d9b371d952f1f5bbe61c3d4c4/pkg/api/vm/handler.go), [복원 연산자](https://github.com/harvester/harvester/blob/7a1bad0f9b525f6d9b371d952f1f5bbe61c3d4c4/pkg/restore/common/operator.go)

다음 대안 비교는 확인한 코드의 동작에서 도출한 분석이며, upstream이 이 대안들을 공식적으로 심의했다는 뜻은 아니다.

- 복원 직후 별도 중지 요청: 기존 API 유지가 가능하지만 이미 시작된 게스트의 실행을 사전에 방지하지 못하는 한계
- 모든 복원을 기본 정지로 변경: 일관된 수동 기동 경계와 기존 자동 복원 흐름의 호환성 변경
- 명시적 `haltAfterRestore` 선택: 기존 false 기본값 유지와 요청별 완료 조건 분리, 호출자가 옵션을 지정해야 하는 부담

도입 단위 테스트는 정지 옵션의 원본 실행 정책 우선순위와 API 입력 전달을 검증한다. 다만 해당 테스트만으로 비동기 컨트롤러의 모든 완료 분기나 게스트 기동을 검증했다고 볼 수는 없다. 이 보고서는 테스트 코드를 읽었으며 프로젝트를 빌드하거나 실행하지 않았다. [도입 테스트](https://github.com/harvester/harvester/blob/2e71d733b20ccbfab1b5a83c3124d28dc3cbe5e8/pkg/controller/master/backup/restore_test.go)

2. 복원 진행 중 외부 사용자가 VM 시작 요청을 보내는 경우에도 의도한 정지 경계가 유지되는가?
