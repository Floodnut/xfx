## 개요

Istio 1.31.3은 ambient 노드의 준비 상태 taint를 제거하기 전에 CNI뿐 아니라 같은 노드의 ztunnel Pod도 Ready인지 확인하는 선택 기능을 추가했다. CNI 준비 완료를 데이터 경로 전체의 준비 완료로 취급하던 판단을 두 구성요소의 상태 결합으로 바꾼다. 준비된 ztunnel이 없으면 taint 제거 대상에서 제외하고, 이후 ztunnel 상태 변경에 따라 다시 계산한다. 다만 이미 제거한 taint를 복구하는 상시 장애 제어기는 아니며, 릴리스 기본 설정에서는 기존 동작을 유지한다.

## 사전 지식

### 준비 상태 taint와 서로 다른 구성요소

노드에 준비 상태 taint가 있으면 해당 taint를 허용하지 않는 일반 Pod의 배치를 제한할 수 있다. Istio의 node-untaint controller는 이 taint를 새로 설치하는 주체가 아니라, 필요한 구성요소가 준비됐다고 판단했을 때 기존 taint를 제거하는 주체다. 기본 관리 키는 `cni.istio.io/not-ready`이며 다른 키로 설정할 수도 있다.

ambient 환경의 istio-cni와 ztunnel은 서로 다른 Pod다. 전자는 Pod 네트워크 연결을 mesh 경로에 편입하는 구성요소이고, 후자는 노드의 ambient 프록시다. 따라서 CNI Pod가 Ready라는 사실만으로 ztunnel Pod도 Ready라고 결론 내릴 수 없다. 이 보고서가 다루는 준비 상태는 패킷 전달 시험 결과가 아니라 Kubernetes Pod의 `Ready` 조건이다. 구현의 `IsPodReadyConditionTrue`는 그 조건이 존재하고 값이 `True`인지 확인한다. [릴리스 구현](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/controllers/untaint/nodeuntainter.go)

### 파생 컬렉션과 작업 큐

변경 전 구현은 관찰한 Pod 중 CNI 네임스페이스와 `k8s-app=istio-cni-node` 라벨이 맞고 Ready인 Pod만 `readyCniPods` 컬렉션에 남겼다. 이어 각 Pod의 `spec.nodeName`으로 Node를 찾고, 관리 대상 taint가 있으면 `readyCniNodes`에 포함했다. 이 파생 컬렉션에 들어온 Node가 작업 큐에 전달되고, reconciler가 Node의 taint 목록을 갱신했다.

여기서 컬렉션은 단순 목록 이상의 역할을 한다. Istio의 krt를 통해 입력과 조회 의존성을 연결하고, 입력 변화에 따라 파생 결과를 다시 계산한다. 기존 흐름은 CNI와 Node의 관계를 알고 있었지만 ztunnel 준비 상태는 판단 입력에 포함하지 않았다. [변경 diff](https://github.com/istio/istio/commit/88ebabf9ac7ef509b6a27009aee310e3032d7c22)

## 변경 분석

### CNI 준비 완료와 ambient 준비 완료 사이의 공백

기존 코드에서는 CNI가 준비되고 Node에 taint가 있다는 조건만 충족하면 제거 작업을 큐에 넣었다. 따라서 같은 노드의 ztunnel이 아직 없거나 Ready가 아니어도 node-untaint controller의 조건을 통과할 수 있었다. 이 문제는 ztunnel의 상태 계산 오류가 아니라, 노드 배치 허용 판단이 ztunnel을 의존성으로 갖지 않았다는 데 있다. [변경 전후 diff와 소스 내 릴리스 노트](https://github.com/istio/istio/commit/88ebabf9ac7ef509b6a27009aee310e3032d7c22)

```diagram
type: flow
title: 변경 전 CNI만으로 taint 제거 대상 선정
direction: down
nodes:
  - id: cni
    label: CNI Pod Ready
  - id: node
    label: 같은 노드의 관리 taint 확인
  - id: queue
    label: taint 제거 작업 큐
  - id: remove
    label: Node taint 제거
edges:
  - from: cni
    to: node
  - from: node
    to: queue
    label: ztunnel 상태 미참조
  - from: queue
    to: remove
```

### 노드별 준비된 ztunnel 조회

새 구현은 `readyZtunnelPods`를 추가한다. ztunnel 후보 네임스페이스에 속하고 `app=ztunnel` 라벨을 가지며 Pod Ready가 참인 항목만 남긴다. 이 컬렉션에 `spec.nodeName`을 키로 하는 `ztunnelByNode` 인덱스를 만든다. `readyCniNodes`를 계산할 때 새 옵션이 켜져 있으면 같은 노드의 준비된 ztunnel을 조회하고, 하나도 없으면 결과에서 Node를 제외한다. 전체 ztunnel 수가 아니라 **해당 노드에 준비된 ztunnel이 하나 이상 있는지**가 조건이다. [릴리스 구현](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/controllers/untaint/nodeuntainter.go)

조회는 `krt.Fetch`와 `krt.FilterIndex`를 사용한다. 코드 주석은 이 Fetch가 의존성을 등록하므로 ztunnel 준비 상태 변경 때 다시 계산된다고 명시한다. 즉 CNI가 먼저 Ready가 된 뒤 ztunnel만 Ready로 바뀌어도 제거 대상에 진입할 수 있다. `TestNodeStaysTaintedWhileZtunnelNotReady`와 `TestNodeStaysTaintedWithNoZtunnel`은 각각 Ready 전환과 뒤늦은 Pod 추가 경로를 검증하도록 작성됐다. 이 보고서는 테스트를 실행하지 않고 테스트 입력과 기대 결과를 정적으로 확인했다. [추가 테스트](https://github.com/istio/istio/blob/88ebabf9ac7ef509b6a27009aee310e3032d7c22/pilot/pkg/controllers/untaint/nodeuntainter_test.go)

### 관찰 범위도 함께 확장

조건에 ztunnel만 추가하고 Pod 관찰 범위를 CNI 네임스페이스로 유지하면, 다른 네임스페이스에 배치된 ztunnel은 영원히 발견되지 않을 수 있다. 새 코드는 옵션 활성화 시 CNI 네임스페이스와 ztunnel 후보 네임스페이스의 합집합을 관찰한다. ztunnel 후보는 istiod의 시스템 네임스페이스에 `CA_TRUSTED_NODE_ACCOUNTS`의 비어 있지 않은 네임스페이스를 추가해 구성한다. 이 값은 네임스페이스 선정에 사용되며, 해당 ServiceAccount 이름과 Pod의 ServiceAccount를 대조하는 검사는 이 코드에 없다.

테스트는 CNI와 ztunnel의 네임스페이스가 다른 경우, CNI/istiod/ztunnel 모두 다른 경우, 관찰 범위에는 있지만 ztunnel 후보 네임스페이스가 아닌 곳의 Pod를 제외하는 경우를 다룬다. readiness 조건과 입력 관찰 범위를 함께 변경한 것이 이번 수정의 핵심이다. [구현과 테스트 diff](https://github.com/istio/istio/commit/88ebabf9ac7ef509b6a27009aee310e3032d7c22)

## 설계 결정 및 트레이드오프

### 기존 파생 컬렉션에 의존성을 추가

```diagram
type: flow
title: 변경 후 옵션 활성화 시 같은 노드의 두 상태 결합
direction: down
nodes:
  - id: cni
    label: CNI Pod Ready
  - id: ztunnel
    label: 허용 네임스페이스의 ztunnel Ready
  - id: index
    label: ztunnel 노드별 인덱스
  - id: join
    label: CNI 노드와 ztunnel 조회 결합
  - id: queue
    label: 관리 taint가 있으면 제거 큐 진입
  - id: remove
    label: Node taint 제거
edges:
  - from: cni
    to: join
  - from: ztunnel
    to: index
  - from: index
    to: join
    label: Fetch 의존성
  - from: join
    to: queue
    label: 같은 노드에서 하나 이상 발견
  - from: queue
    to: remove
```

이 변경은 별도 주기적 점검 루프를 추가하지 않고 기존 krt 파생 컬렉션에 ztunnel 입력을 결합한다. 아래 대안 비교는 구현 구조에서 도출한 분석이며 upstream이 각 대안을 공식 검토했다는 의미는 아니다. [선택된 구현](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/controllers/untaint/nodeuntainter.go)

- 고정 시간 대기: 준비 완료와 무관한 지연 대신 실제 Pod 조건의 변경을 판단 입력으로 사용
- 모든 노드의 ztunnel을 한꺼번에 기다리는 방식: 다른 노드의 상태에 결합하지 않는 노드별 인덱스 조회
- 별도 폴링 루프: 기존 컬렉션의 이벤트 의존성과 작업 큐를 재사용하는 대신 관찰 네임스페이스 및 인덱스 관리 비용 수용

릴리스의 `NodeUntaintCheckZtunnel`은 `registerAmbient`로 등록된다. ambient에서 기본값은 `false`이며 운영자가 명시적으로 켜야 한다. ambient가 꺼져 있으면 환경변수에 값을 주더라도 `registerAmbient`가 비활성 기본값을 반환하므로 ztunnel이 없는 sidecar 환경의 배치를 막지 않는다. 자동으로 보호 수준이 바뀌지 않는 대신, 기존 배포의 동작을 유지하고 운영자가 활성화 시점을 선택하는 구조다. [옵션](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/features/pilot.go), [ambient 등록 함수](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/features/ambient.go)

보장의 경계도 좁다. `readyCniNodes`의 삭제 이벤트는 무시되며 taint를 다시 넣는 코드가 없다. 또한 준비 상태 검사는 큐에 넣을 대상을 고를 때 이뤄지고, `reconcileNode`는 Node를 다시 읽은 뒤 taint를 제거할 뿐 CNI나 ztunnel의 Ready를 재검사하지 않는다. 따라서 큐 대기 중의 준비 상태 악화까지 원자적으로 차단한다고 해석할 수 없다. JSON Patch의 `test`는 Node taint 목록의 동시 변경을 확인하지만 Pod Ready와 taint 변경을 하나의 트랜잭션으로 묶지 않는다. **초기 taint 제거 판단 강화**와 **지속적인 데이터 경로 건강 보장**을 구분해야 한다. [큐 이벤트 처리, reconciler, JSON Patch](https://github.com/istio/istio/blob/edd80bca5f71bd564711ef43ccd085acb545a6b4/pilot/pkg/controllers/untaint/nodeuntainter.go)

## 더 살펴볼 점

1. taint 제거 작업이 큐에서 대기하는 동안 ztunnel이 Ready를 잃는 상황에서 재검사가 필요한가?
2. 커스텀 ztunnel 배치의 네임스페이스가 후보 집합에서 누락됐을 때 이를 어떤 관측 지표로 구분할 수 있는가?
3. 노드 초기 준비 차단과 이미 서비스 중인 노드의 장애 대응을 어느 제어기가 각각 책임져야 하는가?
