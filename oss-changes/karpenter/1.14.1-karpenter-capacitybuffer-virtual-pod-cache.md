## 개요

CapacityBuffer는 Karpenter가 실제 Pending 파드 외에도 미리 확보할 용량을 스케줄링하도록 가상 파드를 만든다.
초기 구현은 프로비저너가 스케줄링을 시작할 때마다 CapacityBuffer를 API에서 읽고, template 또는 scalable workload를 해석한 뒤, replica 수만큼 가상 파드를 다시 만들었다.

v1.14.1은 그 해석과 생성 책임을 CapacityBuffer controller로 옮기고, 프로비저너에는 공유 메모리 cache의 읽기 전용 스냅샷만 주입한다.
핫패스에서 반복되던 API `List`와 참조 해석을 없애는 동시에, cache 갱신 책임을 controller reconcile, watch, requeue lifecycle로 명시적으로 옮긴 구조 변경이다.

## 사전 지식

### CapacityBuffer와 가상 파드

Karpenter의 CapacityBuffer는 미래에 필요할 용량을 미리 node claim으로 준비하려는 custom resource다.
버퍼는 `podTemplateRef` 또는 `scalableRef`를 통해 어떤 workload 모양을 예약할지 가리키고, controller가 이를 해석해 replica 수만큼 synthetic Pod를 만든다.

이 Pod들은 Kubernetes API에 Pending 상태로 존재하는 workload가 아니다.
하지만 Karpenter scheduler에는 실제 Pending Pod와 같은 입력으로 전달된다.
그래서 scheduler는 가상 파드도 만족시키는 instance type과 node claim 수를 계산하고, 버퍼가 요청한 여유 용량을 실제 capacity로 바꿀 수 있다.

### 프로비저닝 핫패스의 비용

Provisioner는 새 Pending 파드가 생기거나 클러스터 상태가 변하면 scheduling pass를 수행한다.
여기서 `GetPendingPods()`는 실제 Pending Pod를 수집해 `Scheduler.Solve()`에 넘긴다.
CapacityBuffer까지 매 pass에 다시 재료화하면, buffer 결과가 변하지 않아도 API `List`, template 또는 workload 조회, replica 수만큼 Pod object 조립이 반복된다.

이 작업은 한 번의 allocation 결과를 cache하는 문제가 아니다.
가상 파드의 원재료를 해석하는 작업을 어느 컴포넌트가 소유하고, scheduler로 전달할 때 누가 최신성을 보장할지의 책임 경계 문제다.

## 변경 분석

### 변경 전: Provisioner가 매 scheduling pass마다 가상 파드를 재료화

`ac7a021e`의 `pkg/controllers/provisioning/buffers.go`에서 Provisioner의 `appendVirtualPods()`는 매번 준비된 CapacityBuffer를 list했다.
각 버퍼에 대해 `resolveVirtualPodSpec()`으로 reference를 다시 풀고, `buildVirtualPods()`로 replica 수만큼 synthetic Pod를 만들었다.
그 결과를 실제 Pending Pod 뒤에 붙여 scheduler에 넘겼다.

```
변경 전: Provisioner가 API 조회와 가상 파드 구성을 소유

  실제 Pending Pod                  CapacityBuffer CR
        │                                  │
        └─────────────┐                    │
                      ▼                    ▼
             Provisioner.GetPendingPods()
                      │
                      ├─ CapacityBuffer List
                      ├─ podTemplateRef/scalableRef 재해석
                      ├─ replica 수만큼 virtual Pod 재생성
                      │
                      ▼
                Scheduler.Solve()

  다음 scheduling pass
        └─ 버퍼가 바뀌지 않아도 같은 List, resolve, build 반복
```

이전 구현의 TODO와 CapacityBuffer 설계 문서는 shared in-memory store를 후속 방향으로 명시했다.
이 구조에서는 Provisioner가 scheduling 판단뿐 아니라 버퍼 CR의 읽기와 reference 해석까지 맡았고, 빈번한 scheduling pass가 구성 해석 주기를 결정했다.

### 변경 후: controller가 갱신하고 Provisioner는 snapshot을 읽음

PR #3137은 `pkg/state/virtualpods`에 `Cache`를 추가했다.
cache는 `map[types.NamespacedName][]*corev1.Pod`를 mutex로 보호하며, 실제 key는 PR 설명의 UID가 아니라 코드상 namespace/name이다.

`pkg/controllers/controllers.go`는 cache 인스턴스 하나를 만들어 Provisioner, CapacityBuffer controller, StaticCapacity controller에 주입한다.
CapacityBuffer controller의 `Reconcile()`은 reference와 replica를 해석하고 성공하면 `UpdateEntry()`로 cache를 갱신한다.
삭제나 해석 실패에는 `RemoveEntry()`를 호출한다.
성공한 reconcile은 provisioner도 trigger해 새 snapshot으로 다시 scheduling할 수 있게 한다.

```
변경 후: controller-managed virtual pod cache

  CapacityBuffer 또는 PodTemplate 변경
                 │
                 ▼
  CapacityBuffer Controller.Reconcile()
       │ resolve reference, replica 계산
       ├─ 성공: UpdateEntry()
       └─ 삭제 또는 해석 실패: RemoveEntry()
                 │
                 ▼
  virtualpods.Cache
  namespace/name -> []*Pod
                 │
                 ▼
  Provisioner.GetPendingPods()
       │ cache.GetAll() snapshot
       ▼
  Scheduler.Solve()

  API List와 reference 해석은 매 scheduling pass가 아니라
  controller lifecycle과 첫 hydrate에만 수행
```

첫 `GetAll()`은 cold start를 위한 lazy hydration이다.
cache가 아직 warmed 상태가 아니면 CapacityBuffer를 list하고 reference를 해석해 한 번 채운다.
이 단계가 실패하면 warmed를 기록하지 않아 다음 호출에서 재시도한다.
따라서 API 호출을 절대로 하지 않는 cache가 아니라, 정상 steady state의 Provisioner hot path에서 그 호출을 제거하는 cache다.

이후에는 controller가 CapacityBuffer reconcile, PodTemplate watch, 30초 `RequeueAfter`를 통해 cache를 최신 상태로 유지한다.
cache는 노드 상태, 다른 Pending Pod, topology, scheduler의 배치 결과까지 보관하지 않는다.
그 live state는 여전히 매 `Scheduler.Solve()`에서 평가된다.

## 설계 결정 및 트레이드오프

### 읽기 핫패스와 구성 해석의 소유권 분리

Provisioner는 실제 Pending Pod와 이미 준비된 virtual Pod snapshot을 scheduler에 전달하는 일만 한다.
CapacityBuffer controller는 CR 상태, 참조 해석, cache invalidation을 소유한다.
이 분리는 scheduling pass가 늘어날수록 같은 buffer를 반복 해석하던 비용을 줄이지만, 최신성 보장을 단일 함수 호출이 아닌 controller lifecycle 전체로 옮긴다.

### cache invalidation을 controller lifecycle로 지불

CapacityBuffer 수정과 PodTemplate watch, 30초 requeue가 cache 갱신의 트리거다.
이전처럼 매 pass에 API를 다시 보면 곧바로 최신 상태를 얻는 단순함은 줄었다.
그 대신 구성 변경시에만 해석 비용을 치르고, 변경이 없는 pass는 가벼운 memory read로 처리한다.

### cold start와 일시 오류에는 재시도를 허용

첫 `GetAll()`은 API list와 해석을 해야 하므로 첫 scheduling pass의 비용은 완전히 사라지지 않는다.
hydrate 실패 뒤 warmed를 설정하지 않는 선택은 빈 cache를 영구 상태로 굳히지 않고 다음 pass에서 회복하도록 한다.
steady state 성능을 우선하되, process restart와 일시 API 오류에는 기존 source에서 다시 채울 여지를 남긴 것이다.

### deep copy 비용 대신 read-only 계약

cache는 map 동시성은 mutex로 보호하지만, 반환하는 Pod pointer를 deep copy하지 않는다.
현재 scheduler 경로는 `trySchedule()` 직전에 Pod를 `DeepCopy()`하므로 cache 입력을 바꾸지 않는다.
copy 비용을 hot path에서 피하는 대신, 미래의 다른 소비자도 이 Pod를 읽기 전용으로 취급해야 한다.

```
변경 후의 책임 경계

  CapacityBuffer controller
  ┌───────────────────────────────────────────────┐
  │ CR watch, reference 해석, replica 계산          │
  │ cache UpdateEntry/RemoveEntry, provisioner trigger │
  └───────────────────────┬───────────────────────┘
                          ▼
  shared virtualpods.Cache
  ┌───────────────────────────────────────────────┐
  │ virtual Pod spec과 replica 결과                │
  │ mutex 보호 map, lazy hydration, read-only 계약 │
  └───────────────────────┬───────────────────────┘
                          ▼
  Provisioner and Scheduler
  ┌───────────────────────────────────────────────┐
  │ snapshot 읽기, 실제 Pending Pod와 결합          │
  │ 노드, topology, live cluster state 재평가       │
  └───────────────────────────────────────────────┘

  얻는 것: 안정 상태 hot path의 API 조회와 재구성 제거
  감수하는 것: cache 갱신 지연, cold-start hydration, 공유 객체 불변성 계약
```
