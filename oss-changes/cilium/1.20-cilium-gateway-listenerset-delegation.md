## 개요

Cilium v1.20은 Kubernetes Gateway API의 `ListenerSet`을 구현했다. 이전에는 하나의 공유 Gateway의 listener와 TLS 인증서를 인프라 운영 팀이 `Gateway.spec.listeners`에 모두 선언해야 했다. 이제 Gateway 소유자는 어떤 namespace의 ListenerSet을 받을지 명시하고, 애플리케이션 팀은 허용된 범위에서 자신의 listener, certificate reference, route attachment를 별도 리소스로 관리할 수 있다. Cilium operator는 이 리소스들을 한 Gateway의 실제 Envoy 설정으로 합치되, listener 충돌과 cross-namespace Secret 권한은 각 ListenerSet 단위로 검증한다.

## 사전 지식

### Gateway listener와 Cilium Gateway API controller

Gateway API에서 Gateway는 외부 주소와 listener를 선언한다. listener는 포트, 프로토콜, hostname, TLS 인증서 참조, route를 받을 namespace 범위를 정한다. `HTTPRoute` 같은 Route는 `parentRef`로 Gateway와 선택적인 listener section을 가리켜, 어떤 외부 진입점으로 들어온 요청을 어느 Service로 보낼지 정의한다.

Cilium에서는 operator의 Gateway reconciler가 Gateway, Route, Service, Secret 참조를 읽어 내부 모델로 만든다. translator는 그 모델을 CiliumEnvoyConfig와 이를 뒷받침하는 Service, EndpointSlice로 변환한다. 따라서 하나의 Gateway에 들어갈 listener 집합은 단순한 YAML 목록이 아니라, route 연결, TLS Secret 접근, 상태 조건, Envoy 리스너 생성을 함께 결정하는 입력 경계다.

### 공유 Gateway에서 listener 소유권이 막히던 지점

공유 Gateway를 운영하면 인프라 팀은 하나의 공인 IP와 Gateway를 제공하고 여러 애플리케이션 팀은 Route를 붙일 수 있다. 그러나 HTTPS hostname과 certificate reference는 Gateway의 listener에 속한다. 이전 모델에서는 새 도메인이나 인증서가 필요할 때 애플리케이션 팀이 Gateway 자체를 수정하거나, 인프라 팀에 listener 추가를 요청해야 했다.

Gateway API는 여러 Gateway를 구현체가 임의로 병합할 수 있게 허용했지만, 병합 순서, 충돌 상태, Secret 권한, Route의 연결 대상에 대한 공통 계약은 없었다. 이 때문에 구현체마다 공유 listener 위임의 동작과 보안 경계가 달라질 수 있었다.

## 변경 분석

### 변경 전: Gateway 하나가 listener와 인증서의 단일 소유자

```
[변경 전]

인프라 팀
  │ Gateway.spec.listeners에 hostname, TLS Secret, port를 모두 선언
  ▼
┌───────────────────────────────┐
│ shared Gateway                │
│  listener: api.example.com    │
│  certificateRef: infra Secret │
└──────────────┬────────────────┘
               │ Gateway parentRef
     ┌─────────┴─────────┐
     ▼                   ▼
 HTTPRoute A          HTTPRoute B

애플리케이션 팀은 Route는 만들 수 있어도 자체 listener나 인증서를
공유 Gateway에 독립적으로 추가할 표준 입력 경로가 없음
```

기존 Cilium reconciler는 Gateway의 직접 listener를 기준으로 Route를 색인하고, 그 목록을 ingestion 단계에 넘겼다. 따라서 다른 namespace가 Gateway를 공유할 수 있어도 listener의 TLS 구성과 namespace별 route 수용 규칙은 Gateway 소유자가 한꺼번에 관리했다. 단순하지만, platform team과 application team의 운영 경계를 나누지 못한다.

### 변경 후: 허용 목록, 병합, 리소스별 상태를 가진 ListenerSet

GEP-1713과 PR #46303은 Gateway에 `allowedListeners`라는 opt-in 경계를 두고, 별도 `ListenerSet`이 parent Gateway를 참조하게 한다. 기본값은 허용하지 않음이며, Gateway 소유자는 same namespace, label selector, all 중 하나로 연결을 허용한다. ListenerSet은 자신이 정의한 listener, TLS reference, Route 연결을 소유한다.

Cilium의 reconciler는 먼저 `resolveAllowedListeners`로 허용된 ListenerSet과 병합된 listener 목록을 만든다. 그 뒤 각 ListenerSet을 parentRef로 삼는 HTTPRoute, GRPCRoute, TLSRoute, TCPRoute, UDPRoute를 기존 Gateway 직결 Route 목록에 더하고 중복을 제거한다. 이렇게 만들어진 Route와 merged listener 목록이 ingestion으로 전달돼 하나의 Envoy 구성으로 번역된다.

중요한 점은 이 합치기가 권한을 합치는 것은 아니라는 점이다. 구현은 listener의 source namespace와 GVK를 내부 모델에 보존한다. 그래서 ListenerSet이 참조하는 Secret은 parent Gateway용 ReferenceGrant를 물려받지 않고, ListenerSet 자신의 namespace 또는 그에 맞는 ReferenceGrant로만 해석된다. Gateway의 top-level `Accepted`와 `Programmed` 조건은 원래 Gateway 설정만 반영하며, ListenerSet의 수용과 충돌은 ListenerSet 상태에 따로 기록한다.

## 설계 결정 및 트레이드오프

### 명시적 위임을 기본 거부보다 앞세우지 않았다

Gateway API는 `allowedListeners`가 없으면 ListenerSet을 허용하지 않는다. 공유 Gateway의 주소와 listener는 외부 노출 경계이므로, 아무 namespace나 listener를 추가할 수 있게 하면 hostname 탈취나 의도치 않은 TLS 구성 변경으로 이어질 수 있다. opt-in은 도입 절차를 하나 늘리지만, Gateway 소유자가 위임 범위를 선언적으로 통제하게 한다.

### 독립 리소스를 병합하되 순서와 충돌을 결정적으로 처리한다

별도 Gateway들을 구현체가 임의로 합치는 방식은 겉으로는 간단하지만, 어떤 listener가 우선하는지와 어떤 리소스에 실패 상태를 돌려줄지 정의하기 어렵다. ListenerSet 모델은 parent Gateway 우선, 그 다음 생성 시각과 namespace/name 순서라는 병합 규칙을 정하고, 충돌한 ListenerSet에 상태를 남긴다. 그 대가로 Cilium은 더 많은 field index, Route 목록 결합과 deduplication, listener별 상태 계산을 유지해야 한다.

### 공유 데이터플레인과 분리된 권한 경계를 함께 유지한다

모든 listener를 최종적으로 하나의 Envoy configuration으로 변환하므로, 데이터플레인은 공유된다. 반면 TLS Secret과 Route 허용 namespace는 listener를 만든 리소스의 namespace 기준으로 검증한다. 이 선택은 같은 Gateway에 여러 팀을 수용하면서도 Gateway owner의 ReferenceGrant가 child ListenerSet으로 번지는 것을 막는다. 대신 사용자는 Gateway의 AllowedListeners, ListenerSet parentRef, ListenerSet의 AllowedRoutes, ReferenceGrant를 각각 맞춰야 한다.

```
[변경 후]

인프라 팀                              애플리케이션 팀
┌──────────────────────────┐            ┌──────────────────────────┐
│ Gateway                  │            │ ListenerSet              │
│ allowedListeners:        │ parentRef  │ listener, TLS Secret     │
│   namespaces: Selector   │◀───────────│ routes allowed locally    │
│ direct listeners         │            └────────────┬─────────────┘
└────────────┬─────────────┘                         │ ListenerSet parentRef
             │                                       ▼
             └──── Cilium reconciler: validate, merge, deduplicate ────┐
                                                                        ▼
                                                        CiliumEnvoyConfig
                                                        하나의 Service와 Envoy listener 집합

Gateway 상태: Gateway 자체 설정
ListenerSet 상태: 허용, 충돌, 프로그래밍 결과
Secret 권한: 각 source namespace와 ReferenceGrant로 분리
```

## 더 살펴볼 점

- ListenerSet이 늘어난 대규모 shared Gateway에서 Cilium의 Route 색인과 병합 비용이 어느 지점부터 조정 대상이 되는지
- Gateway API ListenerSet의 Extended 지원이 Cilium Gateway API 배포에서 어떤 compatibility policy로 안내되는지
- listener name은 서로 달라도 hostname, port, TLS 조합이 충돌할 때 애플리케이션 팀에 어떤 상태 메시지가 가장 유용한지
