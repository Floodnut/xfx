## 개요

Cilium v1.20.3은 conntrack 가비지 컬렉션(GC)이 배치 조회에서 삭제 대상으로 고른 항목을 실제로 지우기 직전에 다시 조회한다. 그 사이 데이터플레인이 연결을 재개했다면 처음 읽은 만료 정보가 더 이상 유효하지 않을 수 있기 때문이다. 변경은 배치 순회의 효율을 유지하면서 최신 값으로 삭제 정책을 다시 적용한다. 재조회와 삭제를 하나의 원자적 연산으로 묶지는 않으므로 경합을 완전히 없애는 대신 오래된 스냅샷에 의존하는 시간을 줄인다. [릴리스 구현](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L460)

## 사전 지식

### Conntrack 상태와 NAT 매핑의 수명

Conntrack(CT)은 패킷을 개별적으로만 보지 않고 연결 단위로 추적하는 상태다. Cilium의 CT 맵에는 주소, 포트, 프로토콜 등으로 연결을 찾는 키와, 수명 정보인 `Lifetime` 등을 가진 값이 저장된다. 주기적인 GC는 `RemoveExpired` 필터를 사용해 `Lifetime`이 이번 순회의 기준 시각보다 작은 항목을 삭제한다. 별도로 특정 IP와 일치하는 연결을 정리하는 필터도 있다. 따라서 GC의 삭제 조건은 단순히 오래된 연결 하나만을 뜻하지 않는다. [기존 필터](https://github.com/cilium/cilium/blob/4f1afc8fb7fcaa7166a6edce6ba5af299b95268a/pkg/maps/ctmap/ctmap.go#L550)

CT 항목의 삭제는 관련 상태의 정리로 이어진다. `purgeCtEntry`는 CT 키 삭제에 성공한 뒤 `GCEvent`를 다음 처리기로 전달한다. NAT 정리 처리기인 `natMapNext`는 NAT 맵이 있고 튜플이 `TUPLE_F_OUT`인 경우 해당 매핑을 삭제한다. DSR 내부 항목이면 별도의 swapped-mapping 삭제 함수를 선택한다. 이 구조에서 CT 수명을 잘못 판단하면 패킷 주소 변환에 필요한 NAT 상태까지 함께 사라질 수 있다. 모든 CT 삭제가 무조건 NAT 삭제를 일으킨다는 뜻은 아니다. [기존 삭제 경로](https://github.com/cilium/cilium/blob/4f1afc8fb7fcaa7166a6edce6ba5af299b95268a/pkg/maps/ctmap/ctmap.go#L456), [NAT 정리 조건](https://github.com/cilium/cilium/blob/4f1afc8fb7fcaa7166a6edce6ba5af299b95268a/pkg/maps/ctmap/ctmap.go#L226)

### 배치 조회의 값은 현재 상태와 다를 수 있음

기존 `iterate`는 `bpf.NewBatchIterator`로 얻은 키와 값을 `cleanup` 콜백에 전달했다. 콜백은 전달받은 값을 필터로 평가하고, 삭제 대상이면 `purgeCtEntry`를 호출했다. 여러 항목을 배치로 읽는 순회와 각 키의 삭제는 서로 다른 작업이다. 처음 읽은 값은 조회 시점의 관측이며, 실제 삭제 시점까지 그대로 유지된다는 보장은 없다. [기존 배치 순회](https://github.com/cilium/cilium/blob/4f1afc8fb7fcaa7166a6edce6ba5af299b95268a/pkg/maps/ctmap/ctmap.go#L478)

데이터플레인은 GC가 순회하는 동안에도 패킷을 처리하며 CT 상태를 갱신할 수 있다. 새 코드의 주석과 테스트가 다루는 상황은 배치 조회 이후 같은 키의 항목이 갱신되거나 교체되는 경우다. GC가 만료된 값으로 읽었어도, 삭제하려는 순간에는 다시 살아 있는 연결의 값일 수 있다. [경합 설명을 포함한 구현 주석](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L460), [재개 항목 테스트](https://github.com/cilium/cilium/blob/772fd52135254d65de23ec6f9bea10949a10f05d/pkg/maps/ctmap/ctmap_privileged_test.go#L358)

## 변경 분석

### 변경 전

이전 `purgeCtEntry`의 첫 작업은 `DeleteLocked(key)`였다. 배치 조회 이후 그 키의 값이 바뀌었는지 확인하지 않고, `cleanup`이 앞서 내린 삭제 판단을 실행했다. 삭제에 성공하면 처음 읽었던 값으로 후속 GC 이벤트를 만들었다. [변경 전 함수](https://github.com/cilium/cilium/blob/4f1afc8fb7fcaa7166a6edce6ba5af299b95268a/pkg/maps/ctmap/ctmap.go#L456)

### 삭제 후보에만 최신 값 재조회

변경 후에는 첫 필터가 삭제 대상으로 고른 항목에 대해 `LookupInto(key, scratch)`를 실행한다. 이어 같은 `GCFilter`를 최신 값에 적용한다. 필터 결과가 `noAction`이면 `errDeferredReopened`를 반환하고 삭제를 생략한다. 여전히 삭제 대상이면 그때 `DeleteLocked`를 호출한다. 배치 순회 자체는 유지되며, 처음부터 보존 대상으로 분류된 항목에는 이 추가 조회를 수행하지 않는다. [릴리스의 재검증과 호출 경로](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L460)

최신 값이 생겼다는 이유만으로 삭제를 취소하지 않는 점도 중요하다. 필터가 이번 GC의 기준 시각을 계속 사용하므로, 갱신된 `Lifetime`도 여전히 만료 기준보다 작으면 삭제한다. 특정 IP를 제거하는 `MatchIPs` 조건에 맞는 항목 역시 수명이 연장됐더라도 삭제한다. 새로운 검사는 삭제 정책을 바꾸는 것이 아니라 **같은 정책을 최신 값에 다시 적용하는 것**이다. [공유 필터](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L568), [조건별 테스트](https://github.com/cilium/cilium/blob/772fd52135254d65de23ec6f9bea10949a10f05d/pkg/maps/ctmap/ctmap_privileged_test.go#L358)

### 삭제 결과와 후속 이벤트에도 최신 상태 반영

재검증으로 보존한 항목은 `aliveEntries`에 포함한다. 재조회 시 이미 키가 사라진 경우는 `skipped`, 실제 삭제 성공은 `deleted`로 구분한다. 삭제 후 ACT 집계와 GC 이벤트에는 배치에서 읽은 값 대신 `scratch`에 담긴 재조회 결과를 전달한다. 최신 값을 확인하고도 후속 처리에는 오래된 값을 넘기는 불일치를 피하는 구성이다. [삭제 후 처리](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L479), [결과 분류](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L519)

추가된 테스트는 재개된 항목 보존, 여전히 만료된 항목 삭제, IP 조건에 따른 삭제, 사라진 키 처리와 통계 분류를 검증 대상으로 삼는다. 여기서는 테스트 코드의 의도를 정적으로 확인했으며, 테스트 통과 여부나 실제 장애 감소율을 측정하지 않았다. [테스트 코드](https://github.com/cilium/cilium/blob/772fd52135254d65de23ec6f9bea10949a10f05d/pkg/maps/ctmap/ctmap_privileged_test.go#L358)

## 설계 결정 및 트레이드오프

### 배치 순회 유지와 선택적 추가 비용

코드에서 확인되는 선택은 배치 순회를 유지하면서 삭제 경로에만 최신성 검사를 추가하는 것이다. 새 `LookupInto`는 기존 `Lookup`처럼 새 값 객체를 생성하지 않고 호출자가 제공한 버퍼에 조회 결과를 기록한다. `cleanup`은 GC 순회에 사용할 `CtEntry` 하나를 준비하고 순차 콜백에서 재사용한다. [버퍼 재사용](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L519), [LookupInto](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/bpf/map_linux.go#L1241)

아래 비교는 구현으로부터 도출한 선택지이며, 각 대안의 성능을 직접 비교 측정한 결과는 아니다.

| 선택지 | 상태 확인 시점 | 비용과 한계 |
| --- | --- | --- |
| 기존 배치 조회 후 삭제 | 배치 조회 시점 | 추가 조회 없음, 오래된 값에 따른 삭제 가능성 |
| 모든 항목의 추가 재조회 | 각 항목 처리 시점 | 처음부터 보존할 항목에도 조회 비용 발생 |
| 채택한 삭제 후보 재조회 | 실제 삭제 직전 | 삭제 후보에 한정한 조회 비용, 조회와 삭제 사이 경합 잔존 |

삭제 후보가 적으면 추가 조회 대상도 적다. 반대로 맵 전체가 만료된 상태라면 모든 항목이 추가 조회 비용을 부담한다. `LookupInto`와 버퍼 재사용은 이 경로의 값 객체 할당을 줄이지만 BPF 맵 조회 자체를 없애지는 않는다. [후보 선택과 재조회](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L519), [맵 조회 호출](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/bpf/map_linux.go#L1247)

### 남아 있는 조회와 삭제 사이 경합

재조회 직후에도 데이터플레인이 같은 항목을 다시 갱신할 수 있다. 코드 주석은 이 잔여 경합을 명시한다. `DeleteLocked`라는 이름도 조건부 원자 삭제를 의미하지 않는다. 실제 함수는 키 삭제 함수를 호출하며, 방금 확인한 값과 현재 값이 같은지 원자적으로 비교하는 인터페이스를 제공하지 않는다. [잔여 경합 주석](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/maps/ctmap/ctmap.go#L460), [DeleteLocked 구현](https://github.com/cilium/cilium/blob/bf1aba7b34ab6d9c711315d78d8eefbea81962d1/pkg/bpf/map_linux.go#L1442)

따라서 이 변경의 보장은 재검증에서 삭제 조건을 벗어난 항목을 보존한다는 범위다. 모든 살아 있는 연결의 삭제를 불가능하게 만든 것은 아니다. 배치 조회 시점부터 삭제까지의 긴 간격을 재조회부터 삭제까지의 짧은 간격으로 줄이는 실용적 완화로 해석해야 한다.

## 더 살펴볼 점

- 만료 항목 비율이 높은 상황에서 추가 조회가 GC 소요 시간에 주는 영향은 어느 정도인가?
- 재조회와 삭제 사이 갱신을 원자적으로 다루려면 사용자 공간과 데이터플레인의 역할을 어떻게 나눠야 하는가?
- 재개 항목을 alive로 집계하는 변화가 기존 GC 관측 지표의 해석에 어떤 차이를 만드는가?
