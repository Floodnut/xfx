## 개요

Cilium v1.20.4는 에이전트 시작 시 경로 정리에서 제외할 항목을 기존 노드 처리기가 등록할 수 있게 했다. 새로운 버전에서 route reconciler가 관리하던 경로를 이전 버전의 직접 Netlink 호출 방식으로 되돌릴 때, 디스크에 남은 관리 이력과 현재 desired-route 테이블의 차이만으로는 경로가 불필요해졌는지 판단할 수 없다. 이번 변경은 경로를 실제로 재설치한 처리기가 초기 정리의 제외 집합에 해당 키를 남기고, 초기 처리가 끝난 뒤 정리를 허용한다. 이를 통해 서로 다른 버전의 관리 방식 사이에서 필요한 경로를 일시적으로 삭제하는 문제를 줄인다.

## 사전 지식

### 커널 경로와 Cilium의 관리 이력

다른 노드에 있는 Pod로 패킷을 보내려면 목적지 Pod 주소 범위에 맞는 경로가 필요하다. v1.20 계열의 자동 직접 노드 경로 처리기는 노드의 Pod CIDR과 노드 IP로 경로를 만들고 `netlink.RouteReplace`로 커널에 설치한다. 이 방식에서는 호출 성공이 곧 커널 경로 갱신 결과다. 해당 동작은 [노드 처리기 변경 diff](https://github.com/cilium/cilium/commit/9363fbf0cedc1a357698a1fb9b6969a8f45e404f)의 변경 전 코드에도 나타난다.

한편 route reconciler를 사용하는 구성요소는 먼저 StateDB의 desired-route 테이블에 원하는 경로를 기록한다. reconciler는 선택된 경로를 커널에 반영하고, 재시작 뒤에도 이전에 자신이 관리하던 경로를 식별할 수 있도록 `route-reconciler.wal`에 키를 기록한다. 여기서 WAL은 커널 경로 전체의 사본이 아니라 경로 관리 이력을 복원하는 로그다. [릴리스 reconciler 구현](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/reconciler.go)

시작 시 WAL을 읽으면 이전 실행에서 남긴 경로 키 집합인 `persistedKeys`가 만들어진다. 초기 prune은 이 집합을 현재 desired-route 테이블과 비교한다. 이전에는 자신이 설치했지만 지금은 원하는 테이블에 없는 경로를 찾아 삭제하는 방식이다. 이 정리는 노드나 설정이 바뀌어 더 이상 필요하지 않은 경로가 재시작을 넘어 남는 것을 방지한다.

### 관리 방식이 달라지면 테이블의 부재가 뜻하는 것도 달라짐

이 판단은 경로의 관리 주체가 같은 모델을 계속 사용할 때 적합하다. 그러나 직접 Netlink를 호출하는 처리기는 커널에 경로를 설치하면서도 desired-route 테이블에는 같은 항목을 만들지 않는다. 커널에는 필요한 경로가 있고 기존 처리기는 이를 유지하고 있는데, reconciler의 테이블에는 없을 수 있다.

[제외 집합 구현 커밋의 설명](https://github.com/cilium/cilium/commit/eaeb628a1212f179bf7a3eafc8112121c4f0cdd5)은 v1.21의 자동 직접 노드 경로가 reconciler/WAL을 사용하는 구조로 전환하면서, v1.20으로 내릴 때 이 충돌이 발생하는 시나리오를 제시한다. 이 보고서는 v1.20.4에 실제로 들어간 호환 처리에 한정하며, 모든 버전 조합의 다운그레이드 지원을 주장하지 않는다.

## 변경 분석

### 변경 전에는 관리 이력과 현재 테이블만 비교

기존 prune은 WAL에 있는 키를 순회하고, desired-route 테이블에서 찾지 못하면 같은 table/prefix/priority의 커널 경로를 조회해 삭제했다. 경로를 다른 코드가 유지하고 있는지는 확인하지 않았다. [제외 분기가 추가된 실제 diff](https://github.com/cilium/cilium/commit/eaeb628a1212f179bf7a3eafc8112121c4f0cdd5)

따라서 다운그레이드 후 기존 노드 처리기가 경로를 성공적으로 다시 설치해도, 그 키가 이전 WAL에 남아 있으면 초기 prune이 이를 삭제할 수 있었다. 문제는 경로 내용의 비호환성이 아니라, 현재 테이블에 없다는 사실을 현재 관리자가 없다는 뜻으로 해석하는 데 있었다.

```diagram
type: flow
title: "변경 전: 두 관리 방식이 같은 경로를 다르게 판단"
direction: down
nodes:
  - id: wal
    label: 이전 버전 WAL에 경로 키 존재
  - id: legacy
    label: 기존 노드 처리기가 커널 경로 재설치
  - id: absent
    label: desired-route 테이블에는 항목 없음
  - id: prune
    label: 초기 prune이 해당 커널 경로 삭제
edges:
  - from: wal
    to: absent
  - from: legacy
    to: absent
  - from: absent
    to: prune
```

### 설치 성공을 초기 정리의 제외 근거로 전달

변경 후 `installDirectRoute`는 경로를 실제로 추가해야 하는 경우에만 `RouteReplace`를 호출한다. 호출에 성공하면 `PruneExclusion.Add`에 main 테이블, Pod CIDR prefix, priority 0의 키를 등록한다. 도달 불가능한 경로라 추가하지 않거나 Netlink 설치가 실패하면 제외 키도 추가하지 않는다. 제외 대상은 모든 과거 경로가 아니라 **기존 처리기가 성공적으로 설치한 경로**다. [릴리스 node.go](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/node.go)

`PruneExclusion`은 mutex로 보호되는 키 집합이다. `Add`는 WAL 키와 일치하도록 owner를 제거한다. 최초 `consume`은 집합을 반환하고 내부 저장소를 비우며, 이후 추가를 거절한다. 경로의 table/prefix/priority에 맞추는 방식이므로 다음 홉이나 장치 속성 전체의 동일성을 검증하는 장치는 아니다. [릴리스 prune_exclusion.go](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/prune_exclusion.go)

초기 정리의 `removeStaleEntries`는 먼저 현재 테이블에서 경로를 찾고, 없으면 제외 집합을 확인한다. 두 곳 모두 없는 키만 기존의 Netlink 조회/삭제 대상으로 보낸다. 처리가 끝나면 `persistedKeys`도 비운다. 이어지는 WAL compact는 현재 선택되어 있고 오류 상태가 아닌 desired route만 기록한다. 따라서 제외 집합은 과거 WAL의 경로를 영구 보존하는 목록이 아니다. 현재 테이블에 없는 제외 경로의 향후 관리는 직접 설치한 처리기에 남는다. [릴리스 reconciler.go](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/reconciler.go)

### 제외 키를 모으기 전에 prune이 시작되지 않도록 순서 연결

제외 목록만 추가하면 최초 prune이 먼저 실행되어 빈 목록을 소비할 수 있다. 이를 막기 위해 노드 처리기는 생성 시 `auto-direct-node-routes` initializer를 등록한다. 처음 노드 설정을 처리할 때 보관 중인 노드를 순회하며 `nodeUpdate`를 수행한 뒤 initializer를 완료한다. [노드 처리기 연결 diff](https://github.com/cilium/cilium/commit/9363fbf0cedc1a357698a1fb9b6969a8f45e404f)

[DesiredRouteManager](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/manager.go)는 이를 StateDB 테이블 초기화 상태와 연결하며, [포함된 StateDB reconciler](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/vendor/github.com/cilium/statedb/reconciler/reconciler.go)는 테이블 초기화가 끝난 뒤에만 prune을 실행한다. 이 게이트는 초기 처리가 수행될 순서를 보장한다. 다만 `nodeUpdate` 오류를 모은 경우에도 순회 뒤 initializer를 완료하므로, 모든 경로 설치가 성공할 때까지 prune을 무기한 막는 보장은 아니다.

## 설계 결정 및 트레이드오프

### 경로 구현 전체의 역이식 대신 시작 시 관리 책임 확인

선택된 구조는 기존 직접 경로 설치 방식을 유지하면서 초기 정리에 필요한 정보를 전달하는 것이다. `node.go`는 계속 Netlink로 경로를 설치하고, reconciler에는 삭제를 피해야 할 키만 넘긴다. 다음 비교의 대안은 실제 검토 회의 기록이 아니라 구현으로부터 도출한 설계 비교다.

- 기존처럼 테이블 부재만으로 삭제: 단순한 정리 조건, 다른 관리 방식으로 넘어간 경로의 오삭제 가능성
- 과거 WAL 경로를 모두 유지: 전환 중 삭제 방지, 더 이상 원하는 구성요소가 없는 경로도 잔존
- 이번 변경의 초기 제외 집합: 성공적으로 재설치한 키만 보호, initializer 및 일회성 집합이라는 추가 협력 규약

```diagram
type: flow
title: "변경 후: 초기 설치 결과를 prune에 전달"
direction: down
nodes:
  - id: init
    label: 노드 처리기 initializer 등록
  - id: install
    label: 직접 경로 설치 성공 및 제외 키 추가
  - id: finish
    label: 초기 노드 순회 후 initializer 완료
  - id: prune
    label: 테이블 초기화 후 제외 집합 1회 소비
  - id: keep
    label: 원하는 경로 또는 제외 경로 유지
  - id: delete
    label: 양쪽 모두 없는 과거 경로 삭제
edges:
  - from: init
    to: install
  - from: install
    to: finish
  - from: finish
    to: prune
  - from: prune
    to: keep
  - from: prune
    to: delete
```

위 그림은 초기 설치 성공 경로를 나타낸다. 실제 코드는 실패한 경로를 제외 집합에 넣지 않고 초기 순회를 마칠 수 있다. 집합 소비 후 `Add`가 거절되는 설계는 시작 이후 메모리가 계속 늘거나 정리 예외가 누적되는 것을 피하지만, 초기화 순서를 지키는 호출자에 의존한다. 이 범위는 [일회성 집합 구현](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/prune_exclusion.go)과 노드 처리기의 완료 위치에서 확인된다.

[회귀 시나리오](https://github.com/cilium/cilium/blob/beb276d2f38d4aadfda14710acf8d14a0f1ba723/pkg/datapath/linux/route/reconciler/scripttest/testdata/prune-exclusion.txtar)는 이전 실행에서 3개 경로를 만든 뒤, 재시작 후 하나만 desired-route로 다시 넣고 하나는 제외 집합에 등록한다. 기대 결과는 두 경로의 유지와 나머지 경로의 삭제다. 본 조사에서는 이 테스트 정의를 읽었으며 실행하지 않았다. 전체 연결 무중단, 설치 실패 복구, 임의의 외부 경로 관리자와의 조정까지 증명하는 테스트로 확대 해석하지 않았다.

## 더 살펴볼 점

- 초기 노드 순회 중 일부 경로 설치가 실패했을 때 재시도와 prune 사이의 복구 순서는 어떻게 관찰할 수 있을까?
- 다른 경로 구성요소도 관리 방식을 바꾼다면 동일한 초기 제외 규약을 사용할 수 있을까?
- 제외 키가 사용된 횟수와 남은 경로를 함께 확인하면 다운그레이드 후 관리 책임 전환을 검증할 수 있을까?
