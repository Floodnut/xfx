## 개요

ClickHouse 26.10은 `system.metric_log`의 기본 저장 스키마를 메트릭마다 물리 열을 만드는 `wide`에서, 메트릭을 하나의 Map 열로 모으는 `bucketed`로 바꿨다. 기존 메트릭 이름은 ALIAS 열로 유지하면서 저장 스트림 수를 줄이고, 병합된 데이터에서는 Map을 128개 버킷으로 나눠 특정 메트릭 조회가 전체 Map을 읽는 비용을 피하도록 했다. 26.8의 선택 기능을 기본값으로 전환하면서 사용자 지정 엔진, ALIAS 생략 설정, 과거 wide 테이블을 함께 읽는 경로까지 보완한 변경이다.

## 사전 지식

### 메트릭 수집과 메트릭 저장은 별도 문제

`system.metric_log`는 서버 내부 계측 값을 주기적으로 수집하여 디스크에 남기는 테이블이다. `ProfileEvent_*`는 누적 이벤트 카운터의 수집 구간별 증가분이고, `CurrentMetric_*`는 수집 시점의 현재값이다. 예를 들어 요청 처리 횟수의 증가분과 현재 진행 중인 작업 수는 서로 다른 의미를 갖는다. `collectMetricLogElement()`가 이 차이를 처리하고, 로그 구현이 그 결과를 테이블 열에 배치한다. 이번 변경의 두 스키마는 이 수집기를 공유한다. [수집 코드](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/MetricLog.cpp)

기존 기본값인 wide 스키마는 이벤트 하나마다 `UInt64` 열, 현재 메트릭 하나마다 `Int64` 열을 만들었다. `ProfileEvent_Query` 같은 이름이 곧 물리 열 이름이므로, 특정 메트릭만 읽는 쿼리는 해당 열을 직접 선택할 수 있다. 반면 샘플 한 행을 기록할 때는 모든 메트릭의 값을 각 열에 넣는다. 값이 0인 메트릭도 이 경로에서 빠지지 않는다. [wide 열 정의와 기록 경로](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/MetricLog.cpp)

MergeTree 계열 저장소는 INSERT로 생긴 데이터 조각인 part를 보관하고, 배경 병합으로 여러 part를 합친다. 메트릭별 열이 많으면 로그가 작아도 기록과 병합에서 다루는 열별 스트림이 많아진다. 따라서 이 문제에서는 쿼리가 읽는 바이트뿐 아니라 서버가 자신의 상태를 계속 기록하는 비용도 고려해야 한다. PR #118318은 수천 개 열의 스트림을 생성하고 병합하는 비용을 기본값 전환의 이유로 제시한다. [변경 동기](https://github.com/ClickHouse/ClickHouse/pull/118318)

### ALIAS와 Map 버킷

ALIAS 열은 값을 별도로 저장하지 않고 다른 열의 표현식으로 계산하는 조회 인터페이스다. `ProfileEvent_Query`를 `metrics['ProfileEvent_Query']`의 별칭으로 만들면 쿼리 이름을 유지하면서 실제 저장 구조를 바꿀 수 있다.

다만 Map 하나로 합치기만 하면 메트릭 하나를 읽으려고 다른 메트릭까지 읽을 수 있다. bucketed 직렬화는 이 Map의 키들을 여러 버킷에 나누는 방식이다. 이번 로그 스키마는 병합된 part에 고정 128개 버킷을 사용한다. 논리적인 Map 열 하나와 디스크상의 데이터 스트림 하나는 같은 뜻이 아니다. [스키마 정의와 기본 엔진 설정](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/BucketedMetricLog.h)

## 변경 분석

### 변경 전: 조회에 편리한 열 구성이 기록 비용으로 연결

기존 wide 스키마에서는 메트릭이 늘어날 때마다 물리 열도 늘어났다. `MetricLogElement::getColumnsDescription()`은 등록된 모든 이벤트와 현재 메트릭을 순회하며 열을 추가하고, `appendToBlock()`은 같은 순서로 각 값을 넣는다. 전체 스키마의 폭과 샘플 한 행을 기록하는 작업량이 메트릭 수에 따라 함께 커지는 구조다. [wide 구현](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/MetricLog.cpp)

```diagram
type: flow
title: 변경 전, 메트릭별 물리 열
direction: down
nodes:
  - id: sample
    label: 이벤트 증가분과 현재값 수집
  - id: columns
    label: 메트릭마다 물리 열에 값 기록
  - id: parts
    label: 다수 열 스트림의 part 기록과 병합
  - id: read
    label: 메트릭 이름으로 해당 열 조회
edges:
  - from: sample
    to: columns
  - from: columns
    to: parts
  - from: parts
    to: read
```

26.8에는 이미 bucketed 스키마를 명시적으로 선택할 수 있었다. 따라서 위 그림은 26.10 이전의 **기본 wide 경로**를 나타낸다. 모든 이전 버전에 bucketed가 없었다는 의미는 아니다. PR #124016의 diff에도 기존 기본값 `wide`를 읽던 코드가 공통 선택 함수로 바뀌는 모습이 남아 있다. [선행 도입](https://github.com/ClickHouse/ClickHouse/pull/115380), [기본값 변경 diff](https://github.com/ClickHouse/ClickHouse/pull/124016/files)

### 변경 후의 저장 경로와 읽기 경로

`BucketedMetricLogElement`는 이벤트와 현재 메트릭의 이름을 `Enum16` 값에 연결하고, `Map(Enum16(...), Int64)`인 `metrics` 열을 만든다. 기록할 때는 값이 0이면 키와 값 삽입을 생략한다. 조회 시 없는 키의 기본값이 0이므로, 계측 값이 0인 경우를 별도 저장 없이 표현할 수 있다. 타임스탬프와 히스토그램은 별도 열로 남으며, 모든 관측 데이터를 이 Map 하나에 넣는 것은 아니다. [Map 생성과 0 생략](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/BucketedMetricLog.cpp)

각 메트릭 이름에는 Map 원소를 참조하는 ALIAS를 제공한다. 이벤트 별칭은 기존 `UInt64`, 현재값 별칭은 `Int64` 타입을 유지한다. 선행 PR #115380은 Enum 키를 문자열 이름으로 조회하는 경로와, 이 조회를 Map의 키별 subcolumn으로 바꾸는 analyzer 최적화도 함께 추가했다. 이름만 호환시키는 데서 끝나지 않고, 특정 키 조회가 해당 버킷으로 좁혀질 수 있도록 연결한 것이다. [별칭 구현](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/BucketedMetricLog.cpp), [analyzer 변경](https://github.com/ClickHouse/ClickHouse/commit/4faa0468efa076fac468cd5129b24f06d539035f)

기본 엔진 설정은 새 INSERT part에는 `basic`, 병합된 part에는 `with_buckets`를 사용한다. 작은 샘플을 flush할 때마다 128개 버킷으로 나눠 많은 작은 파일을 만들지 않고, 병합 시점에 읽기용 구성을 갖추는 선택이다. 그러므로 **모든 part에서 언제나 한 버킷만 읽거나 읽기량이 정확히 128분의 1이 된다고 볼 수는 없다**. part 상태와 조회 표현식에 따라 실제 읽기 경로가 달라진다. [두 직렬화 설정과 설명](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/BucketedMetricLog.h)

## 설계 결정 및 트레이드오프

### 저장 스트림을 줄이되 이름과 운영 설정의 호환성 유지

```diagram
type: flow
title: 변경 후, 기본 bucketed 경로
direction: down
nodes:
  - id: sample
    label: 기존 수집기로 동일한 값 수집
  - id: map
    label: 0을 제외한 메트릭을 Map에 저장
  - id: insert
    label: 새 part는 basic 직렬화
  - id: merge
    label: 병합 part는 고정 128개 버킷
  - id: alias
    label: 메트릭 이름을 ALIAS로 조회
  - id: read
    label: 키 subcolumn으로 관련 버킷 읽기
edges:
  - from: sample
    to: map
  - from: map
    to: insert
  - from: insert
    to: merge
  - from: merge
    to: read
  - from: alias
    to: read
```

이 설계가 택한 절충은 다음과 같다. [구현과 설정](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/BucketedMetricLog.h), [스키마 선택과 엔진 검증](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/SystemLog.cpp)

- wide 유지 대비: 메트릭마다 독립된 물리 열을 읽는 단순성 대신, 제한된 수의 버킷과 별칭을 통한 저장 스트림 축소
- 단일 Map의 기본 직렬화만 사용 대비: 병합 시 버킷 구성을 추가하는 비용과 특정 메트릭 읽기 범위 축소의 교환
- INSERT부터 버킷화하는 방식 대비: 작은 part의 파일 수 증가 억제와 병합 전 읽기 최적화 지연의 교환
- 조회 호환성 유지 비용: 물리 메트릭 열은 줄어도 메트릭별 ALIAS와 Enum 정의는 스키마에 유지

기본값 전환은 무조건 적용되지 않는다. `getMetricLogSchemaType()`은 명시한 `schema_type`을 우선한다. 이를 생략했을 때 ALIAS 열 생략이 설정되어 있거나 `metric_log.engine`을 직접 지정했다면 기존 wide를 선택한다. 전자는 새 스키마의 메트릭 이름 인터페이스를 없애고, 후자는 기본 테이블 정의에 포함된 버킷 직렬화 설정을 덮어쓰기 때문이다. 릴리스 코드는 `system_tables.skip_alias_columns`를 확인하며, 과거 `default_system_log_flush_policy.skip_alias_columns`도 경고와 함께 지원한다. [릴리스의 선택 함수](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/SystemLog.cpp)

사용자가 custom engine과 bucketed를 둘 다 명시하면 서버는 엔진 설정을 파싱해 필요한 버킷 설정과 비교한다. 값이 다르거나 유효 기본값으로도 충족되지 않으면 경고를 남기지만, 그 이유만으로 테이블 생성을 거부하지는 않는다. Map 모양을 갖추었다는 사실과 실제로 128개 고정 버킷으로 저장된다는 사실을 구분한 처리다. [설정 비교와 경고](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/SystemLog.cpp)

### 과거 wide 테이블을 함께 읽는 경우

테이블 구조가 바뀌면 기존 로그 테이블은 번호가 붙은 이름으로 보존된다. 이때 통합 조회 테이블에 새 Map 기반 ALIAS를 그대로 선언하면 문제가 생긴다. 과거 wide 테이블에는 `metrics` Map이 없기 때문에, 별칭을 먼저 전개하는 조회가 실제 메트릭 열 대신 기본값을 읽을 수 있다.

`getCreateUnionTableQuery()`는 bucketed 로그의 메트릭별 열을 통합 테이블에서 `MATERIALIZED`로 선언한다. 각 하위 테이블이 자신의 물리 열 또는 ALIAS를 제공하게 하고, 동시에 `SELECT *`가 수많은 메트릭 이름을 자동 확장하지 않도록 한다. PR #124016의 테스트는 과거 `metric_log_0`에서 직접 읽은 합계와 통합 테이블에서 같은 과거 테이블을 선택한 합계가 일치하는지 확인한다. 이는 테스트 소스에서 확인한 검증 항목이며, 이번 조사에서 테스트를 실행한 결과는 아니다. [통합 테이블 생성](https://github.com/ClickHouse/ClickHouse/blob/c6428ebcc39fdff48bb0f50e128b2078701901d5/src/Interpreters/SystemLog.cpp), [호환성 테스트](https://github.com/ClickHouse/ClickHouse/blob/a5dff1d90113386e123930fc94e2d24aa2e0cbf9/tests/integration/test_transposed_metric_log/test.py)

## 더 살펴볼 점

- 실제 로그 보존 기간과 flush 주기에서 병합 전 basic part가 차지하는 읽기 비중은 어느 정도인가?
- 메트릭별 이름을 직접 선택하는 쿼리와 `SELECT *`를 사용하는 수집 도구의 스키마 기대 차이는 무엇인가?
- 사용자 지정 엔진을 사용하는 환경에서 기본 스키마 선택과 실제 Map 직렬화 설정을 함께 확인하고 있는가?
