## 개요

Kubernetes v1.37은 Node의 drain, 유지보수, 정상 종료 상황을 표현하는 공통 condition 이름을 도입했다. v1.37.1에서도 이 정의를 확인할 수 있다. 핵심은 운영 도구가 Node의 수명주기 맥락을 같은 이름으로 게시할 수 있게 한 것이다. 이 변경만으로 drain 실행이나 DaemonSet 재배치 정책이 자동화되지는 않는다. 구현 PR은 코어 컨트롤러의 활용을 후속 작업으로 명시한다. [구현 PR](https://github.com/kubernetes/kubernetes/pull/139993)

## 사전 지식

### Node condition은 현재 관찰한 사실

Node는 클러스터의 실행 노드를 나타내는 API 객체다. `NodeCondition`은 `type`으로 관찰 대상을, `status`로 `True`, `False`, `Unknown`을 기록한다. 상태가 바뀐 시각과 원인을 설명하는 `reason`, 사람이 읽는 `message`도 함께 담을 수 있다. 이는 이미 존재하던 구조다. [v1.36.0 API 정의](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.36.0/staging/src/k8s.io/api/core/v1/types.go)

기존 내장 condition에는 `Ready`, `MemoryPressure`, `DiskPressure`, `PIDPressure`, `NetworkUnavailable`가 있다. `Ready`는 kubelet이 건강하고 Pod를 받아들일 준비가 되었는지를 나타낸다. 이 목록은 닫힌 enum이 아니며, 소스 주석도 외부 제공자가 추가 condition을 설정할 수 있음을 명시한다. 따라서 이번 변경을 condition 확장 기능의 최초 도입으로 해석하면 안 된다. 기존 확장 공간에 Kubernetes 공통 수명주기 어휘가 추가된 것이다. [변경 전 정의](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.36.0/staging/src/k8s.io/api/core/v1/types.go)

## 변경 분석

### 상태의 원인을 추측하던 경계에 공통 이름 추가

변경 전 내장 목록에는 유지보수 계획과 drain 진행을 직접 가리키는 이름이 없었다. 건강 상태만으로 관리자의 작업 의도를 전달하기 어렵다는 것이 설계의 출발점이다. 다음 그림은 API 표현 범위의 비교이며 특정 컨트롤러의 실행 순서를 재현한 것은 아니다. [변경 전 코드](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.36.0/staging/src/k8s.io/api/core/v1/types.go)

```diagram
type: flow
title: "변경 전 Node condition 표현"
direction: down
nodes:
  - id: node-conditions
    label: "Node.status.conditions (Ready / Pressure / Network, 외부 정의 condition 가능)"
  - id: observer
    label: "관찰자 (유지보수/drain 공통 이름, 내장 정의 부재)"
edges:
  - from: node-conditions
    to: observer
```

v1.37.1 API에는 다음 다섯 이름이 추가되어 있다. 모두 설정과 해제 책임을 관리자에게 둔다. [변경 후 코드](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.37.1/staging/src/k8s.io/api/core/v1/types.go)

| Condition | 코드에 명시된 의미 |
| --- | --- |
| `GracefulNodeShutdownInProgress` | 정상 종료가 진행 중이라고 판단한 상태 |
| `DrainInProgress` | 관리자 정의에 따라 drain 진행 중 |
| `Drained` | 관리자가 정한 drain 기준 충족 |
| `MaintenancePlanned` | 앞으로 Node에 변경을 수행할 계획 |
| `MaintenanceInProgress` | 유지보수 진행 중 |

`Drained`는 Pod가 반드시 0개라는 뜻이 아니다. 완료 기준을 관리자가 정한다. 또한 유지보수와 drain은 같은 사건이 아니다. 코드 주석은 Kubernetes 업그레이드와 커널 live patch를 대비하며, 후자는 drain 없이도 유지보수 중임을 알릴 수 있다고 설명한다. [API 의미 정의](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.37.1/staging/src/k8s.io/api/core/v1/types.go)

`NodeLifecycleConditions`는 v1.37부터 Alpha, 기본값 `false`로 등록되어 있다. 다만 feature gate 등록과 condition을 소비하는 동작은 별개다. 이 파일만으로 gate를 끄면 API가 해당 문자열을 거부한다고 결론낼 수 없다. [feature gate 정의](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.37.1/pkg/features/kube_features.go)

## 설계 결정 및 트레이드오프

### 공유하는 관찰 값과 후속 제어 동작의 분리

KEP는 다음 대안을 비교한다. 아래는 현재 열람한 설계 문서의 설명이며, 새 컨트롤러가 구현되었다는 증거로 사용하지 않는다. [KEP Alternatives](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/5683-lifecycle-conditions/README.md#alternatives)

- 현상 유지: 도구별 우회 방식과 공통 맥락 부재의 지속
- 적은 condition에 `reason`으로 단계 표현: 이름 수 절약 대신 원인 필드에 상태 전이 의미 부여
- 별도 `Node.status.lifecycle`: 구조화된 소유권/전이 표현 가능성, 조정 모델이 정리되기 전 새 API 표면 도입 부담
- 기존 condition 확장: 관찰 값 전달 구조 재사용, 실행 조정과 소유권 규약은 후속 과제로 유지

```diagram
type: flow
title: "변경 후 Node lifecycle condition 표현"
direction: down
nodes:
  - id: manager
    label: "관리자 / 권한을 받은 도구 (관찰 값 설정, 해제 책임)"
  - id: lifecycle-conditions
    label: "기존 Node.status.conditions (DrainInProgress / Drained / MaintenancePlanned / MaintenanceInProgress / GracefulNodeShutdownInProgress)"
  - id: common-observation
    label: "공통 이름으로 상태 조회 (코어 컨트롤러 동작 연계는 후속 설계/구현 범위)"
edges:
  - from: manager
    to: lifecycle-conditions
  - from: lifecycle-conditions
    to: common-observation
```

KEP는 condition의 `type`과 `status`가 수명주기 관찰 값을 표현하고 `reason`은 원인을 설명하도록 구분한다. 관리자나 위임된 도구가 상태를 정리해야 하므로 오래된 condition이 남을 위험도 있다. 잠금, 다중 작성자 조정, 소유권 API는 이 단계에서 해결하지 않는다. [KEP Writer Ownership 및 Future Extension Points](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/5683-lifecycle-conditions/README.md#writer-ownership)

이를 통해 얻는 것은 도구 간 상태 의미를 맞출 기반이다. drain 완료 판정이나 유지보수 중 스케줄링 회피까지 얻었다고 판단하면 범위를 넘어선다. 구현 PR에서도 이번 릴리스의 작성자를 관리자로 한정하고, 계획의 시간 범위 같은 추가 의미는 후속 확장으로 남긴다. [API 리뷰 논의](https://github.com/kubernetes/kubernetes/pull/139993)

## 더 살펴볼 점

- 여러 운영 도구가 같은 condition을 수정할 때 소유권을 어떻게 정할 것인가?
- 작성자가 중단되어 남은 `DrainInProgress`를 어떤 근거로 해제할 것인가?
- 후속 컨트롤러 연계에서 운영자가 정한 `Drained` 기준을 어떻게 해석할 것인가?
