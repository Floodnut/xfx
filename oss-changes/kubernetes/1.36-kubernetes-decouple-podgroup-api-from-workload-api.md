## 개요

Kubernetes v1.36에서 **gang scheduling을 위한 PodGroup이 Workload 객체 안에 내장(embedded)되어 있던 구조(v1alpha1)에서, PodGroup을 독립적인 최상위 API 객체로 분리(v1alpha2)하는 설계 변경이 alpha로 도입**됐다. v1.35(KEP-4671 alpha)에서 Workload API가 처음 등장했을 때, PodGroup은 `Workload.spec.podGroups[]` 배열 안에 인라인으로 정의되어 있었다. Pod는 `spec.workloadRef`로 Workload를 참조했고, 스케줄러는 Workload 객체 내부의 PodGroup 정보를 읽어 gang scheduling을 수행했다. 이 설계는 etcd 1.5MB 객체 크기 제한, Workload 객체에 대한 상태 업데이트 경합, 정적 정책 정의와 런타임 스케줄링 단위의 결합이라는 세 가지 구조적 문제를 안고 있었다. KEP-5832는 PodGroup을 `scheduling.k8s.io/v1alpha2`의 독립 API 리소스로 분리하고, Workload의 역할을 정적 정책 템플릿으로 한정하며, Pod의 참조 필드를 `spec.workloadRef`에서 `spec.schedulingGroup.podGroupName`으로 교체해 이 문제를 해결한다.

## 사전 지식

### gang scheduling이 Kubernetes에 필요한 이유

ML 학습, HPC 시뮬레이션 같은 대규모 병렬 워크로드는 모든 Pod가 동시에 시작되어야 통신을 시작할 수 있다. 일부 Pod만 먼저 스케줄링되면 나머지를 기다리느라 GPU 같은 비싼 자원이 유휴 상태가 되거나, 애플리케이션 수준 통신 타임아웃으로 작업 자체가 실패한다. gang scheduling은 그룹 내 Pod 전체(또는 최소 `minCount`만큼)가 동시에 배치 가능할 때만 바인딩을 진행하는 all-or-nothing 스케줄링이다. KEP-4671은 이 기능을 kube-scheduler에 내장하기 위해 Workload와 PodGroup이라는 개념을 도입했다.

### v1.35(v1alpha1)의 Workload API 구조

KEP-4671 alpha(v1.35)에서 도입된 v1alpha1 API의 구조를 보자. `scheduling.k8s.io/v1alpha1`에 Workload라는 단일 API 객체가 있었고, PodGroup은 별도 API 객체가 아니라 이 Workload 안에 인라인으로 정의되는 구조체였다.

```go
// v1alpha1 (v1.35)

type WorkloadSpec struct {
    ControllerRef *TypedLocalObjectReference
    PodGroups     []PodGroup   // <-- PodGroup이 인라인 배열로 내장
}

type PodGroup struct {
    Name   string         // Workload 내에서 고유한 이름
    Policy PodGroupPolicy // gang / basic 스케줄링 정책
}

type PodGroupPolicy struct {
    Basic *BasicSchedulingPolicy
    Gang  *GangSchedulingPolicy  // minCount 등
}
```

Pod는 `spec.workloadRef`라는 필드로 자신이 속한 Workload와 그 안의 PodGroup을 참조했다.

```go
// v1alpha1 Pod 필드 (v1.35)

type PodSpec struct {
    ...
    WorkloadRef *WorkloadReference
}

type WorkloadReference struct {
    Name             string  // Workload 객체 이름
    PodGroup         string  // Workload 내 PodGroup 이름
    PodGroupReplicaKey string  // 같은 PodGroup의 서로 다른 레플리카 구분용 키
}
```

v1alpha1에서 스케줄러의 동작 흐름은 다음과 같았다.

1. Pod의 `workloadRef.Name`으로 Workload 객체를 조회
2. `workloadRef.PodGroup`으로 Workload 내부의 `podGroups[]` 배열에서 해당 PodGroup 구조체를 찾음
3. `podGroupReplicaKey`를 사용해 같은 PodGroup 정의의 서로 다른 레플리카 인스턴스를 구분
4. GangScheduling 플러그인의 PreEnqueue에서 PodGroup 존재 확인 및 minCount 조건 확인
5. Permit 단계에서 모든 Pod가 도달할 때까지 대기 후 일괄 바인딩

### v1alpha1 설계의 세 가지 구조적 문제

1. **etcd 1.5MB 크기 제한**: 대규모 워크로드에서 PodGroup이 많아지면(최대 8개까지 허용) 각 PodGroup에 런타임 상태(status)까지 Workload 객체에 쓰게 되면 1.5MB etcd 단일 객체 제한에 걸릴 수 있다. 특히 PodGroup별 스케줄링 상태, 조건(conditions), 메시지를 모두 Workload 하나에 담으면 이 제한이 현실적 문제가 된다.

2. **상태 업데이트 경합(contention)**: 개별 PodGroup의 스케줄링 상태를 업데이트할 때마다 중앙의 Workload 객체 전체를 read-modify-write해야 한다. 수십 개 레플리카가 동시에 스케줄링될 때 이 경합은 심각한 성능 병목이 된다.

3. **정적 정책 정의와 런타임 실행 단위의 결합**: Workload는 장기간 유지되는 정책 정의(configuration-intent) 역할인데, PodGroup은 일시적인 스케줄링 실행 단위(runtime scheduling unit)다. 이 둘을 같은 객체에 넣으면 생명주기 관리가 복잡해진다. 예를 들어 PodGroup 단위로 ResourceClaim을 소유시키고 가비지 컬렉션하고 싶어도, 소유자가 Workload 전체이거나 개별 Pod뿐이라 중간 단위의 생명주기 관리가 불가능하다.

## 변경 분석

### PodGroup 내장 구조의 한계가 현실화되는 시나리오

LeaderWorkerSet(LWS)처럼 리더 Pod 1개 + 워커 Pod N개를 하나의 스케줄링 단위로 묶는 워크로드를 생각해보자. v1alpha1에서는 LWS 컨트롤러가 Workload 객체를 만들 때 `podGroups[]` 안에 각 레플리카의 PodGroup을 인라인으로 정의해야 한다. 레플리카가 100개면 Workload 안에 PodGroup 항목이 100개다. 이 각각의 스케줄링 상태를 Workload.status에 반영하려면 레플리카 하나가 스케줄링될 때마다 Workload 전체를 갱신해야 한다. 100개 레플리카가 동시에 스케줄링되면 Workload 객체에 대한 100회의 동시 갱신 요청이 발생하는 것이다.

```
[변경 전] v1alpha1 (v1.35): PodGroup이 Workload 안에 내장된 구조

                     scheduling.k8s.io/v1alpha1
                     +------------------------------------------+
                     |              Workload                     |
                     |  name: training-workload                  |
                     |  spec:                                    |
                     |    controllerRef: {kind: Job, name: job1} |
                     |    podGroups:      <-- 인라인 배열          |
                     |      - name: workers                      |
                     |        policy:                             |
                     |          gang:                             |
                     |            minCount: 100                   |
                     |                                            |
                     |  (status는 Workload 객체에 통합)            |
                     |  (PodGroup별 상태 = Workload 전체 갱신)     |
                     +------------------------------------------+
                                ^                ^
                                |                |
               workloadRef.Name |                | workloadRef.Name
          workloadRef.PodGroup: |                | workloadRef.PodGroup:
                      "workers" |                | "workers"
          podGroupReplicaKey:   |                | podGroupReplicaKey:
                     "replica0" |                | "replica1"
                                |                |
                     +----------+    +-----------+
                     |  Pod A   |    |   Pod B   |
                     | (worker) |    |  (worker) |
                     +----------+    +-----------+

문제:
- PodGroup은 독립 객체가 아니라 Workload 내부의 배열 요소
- Pod는 workloadRef로 Workload+PodGroup+ReplicaKey 3단계를 참조
- PodGroup별 상태 업데이트 = Workload 전체 read-modify-write
- 대규모 레플리카에서 etcd 1.5MB 제한 및 경합 발생
- PodGroup 단위의 소유권/가비지 컬렉션 불가능
```

### v1alpha2에서 PodGroup이 독립 API 객체가 된 구조

PR #136976이 v1alpha1을 삭제하고 `scheduling.k8s.io/v1alpha2`를 신규 도입했다. 핵심 변경은 세 가지다.

1. **Workload의 `podGroups[]`가 `podGroupTemplates[]`로 변경**: PodGroup 정의가 더 이상 런타임 인스턴스가 아니라 템플릿 역할임을 명확히 한다. 필드 이름이 바뀐 것이 단순한 리네임이 아니라 역할의 전환을 의미한다. Workload는 이제 PodGroup을 직접 포함하지 않고, PodGroup을 만들 때 참고할 청사진(template)만 담는다.

2. **PodGroup이 독립 API 리소스로 분리**: `scheduling.k8s.io/v1alpha2` 그룹에 PodGroup이 최상위 API 객체로 추가됐다. 자체 metadata(이름, 네임스페이스, ownerReferences, finalizer), spec, status를 가진다.

3. **Pod의 `workloadRef`가 `schedulingGroup.podGroupName`으로 교체**: Pod는 더 이상 Workload를 참조하지 않는다. 대신 자신이 속한 PodGroup 이름을 직접 참조한다. 3단계 참조(Workload + PodGroup 이름 + ReplicaKey)가 1단계 참조(PodGroup 이름)로 단순화됐다.

v1alpha2의 API 타입 정의는 다음과 같다.

```go
// v1alpha2 (v1.36)

// Workload: 정적 정책 템플릿
type WorkloadSpec struct {
    ControllerRef      *TypedLocalObjectReference
    PodGroupTemplates  []PodGroupTemplate  // <-- podGroups -> podGroupTemplates
}

type PodGroupTemplate struct {
    Name              string
    SchedulingPolicy  PodGroupSchedulingPolicy  // Policy -> SchedulingPolicy
}

// PodGroup: 독립 런타임 객체 (신규)
type PodGroup struct {
    metav1.TypeMeta
    metav1.ObjectMeta   // 자체 이름, 네임스페이스, ownerReferences 보유
    Spec   PodGroupSpec
    Status PodGroupStatus
}

type PodGroupSpec struct {
    PodGroupTemplateRef  *PodGroupTemplateReference  // 어떤 Workload의 어떤 템플릿에서 왔는지
    SchedulingPolicy     *PodGroupSchedulingPolicy   // 템플릿에서 복사(Copy/Inline)
}

type PodGroupTemplateReference struct {
    Workload *WorkloadPodGroupTemplateReference
}

type WorkloadPodGroupTemplateReference struct {
    WorkloadName         string  // 참조하는 Workload 이름
    PodGroupTemplateName string  // Workload 내 템플릿 이름
}

type PodGroupStatus struct {
    Conditions []metav1.Condition  // PodGroupScheduled 조건 등
}

// Pod: schedulingGroup으로 PodGroup 직접 참조
type PodSpec struct {
    ...
    // WorkloadRef는 tombstone 처리 (v1.36에서 SchedulingGroup으로 교체)
    SchedulingGroup *PodSchedulingGroup
}

type PodSchedulingGroup struct {
    PodGroupName *string  // PodGroup 객체 이름을 직접 참조
}
```

### 스케줄러 동작의 변경

PR #136976에서 스케줄러 내부도 대폭 변경됐다. 핵심 변화는 스케줄러가 Workload informer를 PodGroup informer로 교체한 것이다.

**v1alpha1 흐름**: 스케줄러가 Workload informer를 watch -> Pod의 `workloadRef`에서 Workload 이름 추출 -> Workload 내부의 `podGroups[]`에서 매칭되는 PodGroup 구조체를 찾음 -> gang scheduling 정책 적용

**v1alpha2 흐름**: 스케줄러가 PodGroup informer를 watch -> Pod의 `schedulingGroup.podGroupName`에서 PodGroup 이름 추출 -> PodGroup 객체를 직접 조회 -> PodGroup.spec.schedulingPolicy에서 정책 읽음 -> PodGroup.status에 직접 조건 업데이트

GangScheduling 플러그인(`pkg/scheduler/framework/plugins/gangscheduling/`)의 변경 사항은 다음과 같다.

- **PreEnqueue**: PodGroup 객체 존재 여부를 확인한다. 존재하지 않으면 `UnschedulableAndUnresolvable`을 반환하고, PodGroup이 생성될 때 informer Add 이벤트로 재큐잉한다. 존재하면 `minCount` 조건을 확인한다.
- **Permit**: 각 Pod의 `schedulingGroup.podGroupName`으로 PodGroup을 식별하고, 해당 PodGroup의 모든 Pod가 Permit 단계에 도달할 때까지 대기한다.
- **EventsToRegister**: PodGroup 객체 생성 이벤트를 등록한다.

새로 추가된 `pkg/scheduler/framework/plugins/helper/podgroup.go`는 Pod에서 PodGroup 이름을 추출하는 헬퍼 함수를 제공한다.

### PodGroup 상태 관리(PR #137611)

PR #137611은 스케줄러가 PodGroup의 상태를 직접 업데이트하는 로직을 구현했다.

- `PodGroupScheduled=True`: PodGroup 스케줄링 사이클이 성공하면(Permit 단계를 통과하면) 설정한다.
- `PodGroupScheduled=False` (reason: Unschedulable): 스케줄링 사이클이 그룹을 배치하는 데 실패하면 설정한다. 한 번 True로 전이된 후에는, `minCount`를 초과하는 추가 Pod의 실패로 인해 다시 False로 회귀하지 않는다.

변경된 파일은 `pkg/scheduler/schedule_one_podgroup.go`(+58줄), `pkg/scheduler/util/utils.go`(+45줄), 그리고 관련 테스트 파일이다.

### PodGroup Admission 검증(PR #137464)

PR #137464는 PodGroup 생성 시점에 참조 무결성을 검증하는 admission 플러그인(`plugin/pkg/admission/podgroup/admission.go`)을 도입했다.

검증 규칙은 다음과 같다.
- PodGroup이 `workloadRef`(v1alpha2에서는 `podGroupTemplateRef`)로 Workload를 참조하면, 해당 Workload가 같은 네임스페이스에 이미 존재해야 한다
- PodGroup의 spec 필드가 참조된 Workload의 대응하는 `PodGroupTemplate`과 일치해야 한다(정책 드리프트 방지)
- `workloadRef`가 없는 독립(standalone) PodGroup은 검증 없이 통과한다

## 설계 결정 및 트레이드오프

### Copy/Inline 모델 vs. Reference 모델

PodGroup이 자신의 스케줄링 정책을 어떻게 참조할지에 대해 두 가지 선택지가 있었다.

- **Reference 모델**: PodGroup이 `Workload.podGroupTemplates[x]`를 포인터로만 참조. 단일 소스 유지, 쓰기 증폭이 적음. 단점은 Workload 수정 시 기존의 모든 PodGroup에 영향을 주는 action at a distance 문제 발생
- **Copy/Inline 모델**: PodGroup 생성 시 템플릿의 정책을 복사해서 PodGroup 자체에 인라인으로 보유. PodGroup이 자기 완결적(self-contained) 객체가 됨. Workload 변경이 기존 PodGroup에 영향 없음(새로 생성되는 PodGroup에만 적용). 디버깅이 단순해짐

alpha에서는 Copy/Inline을 채택했다. `ReplicaSet.spec.template` -> `Pod` 패턴과 동일한 검증된 Kubernetes 관용구를 따른 것이다. 향후 확장성 문제가 실제로 발생하면 선택적 참조 필드를 추가하되, 정확히 하나만 설정되도록 검증하는 방식으로 마이그레이션 경로를 남겨뒀다.

### 소유권(Ownership) 구조와 가비지 컬렉션

v1alpha2의 객체 소유 관계는 다음과 같다.

- 워크로드 컨트롤러(Job, JobSet, LWS 등)가 Workload, PodGroup, Pod를 모두 생성하고 소유한다
- PodGroup은 `ownerReferences`로 워크로드 컨트롤러에 소유되므로, 컨트롤러가 삭제되면 PodGroup도 자동으로 가비지 컬렉션된다
- PodGroup은 `podGroupTemplateRef`로 Workload를 참조하지만, Workload가 PodGroup을 소유하지는 않는다(소유자는 컨트롤러)
- Pod는 `schedulingGroup.podGroupName`으로 PodGroup을 참조한다(소유 관계가 아닌 단순 참조)


### 생성 순서 제약과 race condition 방어

컨트롤러가 객체를 생성하는 순서는 엄격하게 `Workload -> PodGroup -> Pod`여야 한다. Pod가 아직 존재하지 않는 PodGroup을 참조하면 스케줄러는 해당 Pod를 `UnschedulableAndUnresolvable`로 표시하고, PodGroup이 생성되면 informer Add 이벤트로 재큐잉한다. 이것이 일시적 race condition에 대한 자연스러운 방어막이 되고, admission 플러그인(PR #137464)이 Workload-PodGroup 간 참조 무결성을 추가로 검증한다.

### Deletion Protection(삭제 보호)

PodGroup을 참조하는 비종료 상태(non-terminal) Pod가 존재하는 동안 PodGroup이 삭제되면 스케줄링이 깨진다. KEP-5832는 PodGroup에 전용 finalizer를 추가하고, 전용 컨트롤러가 참조 Pod가 모두 종료 상태(`Succeeded` / `Failed`)가 된 후에만 finalizer를 제거하는 보호 메커니즘을 설계했다. alpha에서는 nice-to-have이고, beta 졸업의 필수 요건이다.

### 고려했지만 채택하지 않은 대안

1. **내장 유지(Status Quo)**: PodGroup을 Workload 안에 그대로 두는 방안. 단일 객체로 관리가 단순하지만, 스케일링/DRA 통합/생명주기 관리에서 위에 서술한 한계를 해결할 수 없다.

2. **내장 + 독립 혼합 지원**: Workload 안에 내장 PodGroup과 외부 독립 PodGroup을 모두 허용하는 방안. 유연하지만, 두 종류의 최상위 객체 타입이 명확한 책임 분리 없이 공존하게 되고, 내장 PodGroup을 사용하던 사용자가 독립으로 전환하려면 Workload를 재생성해야 하며, 추론과 유지보수가 가장 복잡해진다.

### v1.37 beta 승격 예정 사항

KEP-4671의 kep.yaml에 따르면 v1.37에서 `v1beta1`로 beta 승격이 예정되어 있다. beta에서 추가될 주요 사항은 다음과 같다.

- Workload Scheduling Cycle 도입: 개별 Pod 단위 스케줄링 대신 PodGroup 전체를 하나의 배치로 처리하는 스케줄링 사이클
- 최소 1개의 실제 워크로드 컨트롤러(예: Job)와의 alpha 통합
- PodGroup 삭제 보호 메커니즘의 구현 필수화
- `PodGroupScheduled` 조건이 `PodGroupInitiallyScheduled`로 이름 변경(한 번 True가 되면 영구 유지하는 terminal state 의미를 명확히 하기 위함)

## 더 살펴볼 점

- Hierarchical PodGroups(PodGroup이 부모 PodGroup을 참조하는 계층 구조)가 향후 KEP에서 어떤 형태로 설계될지, 그리고 이것이 JobSet 같은 다단계 워크로드의 복합 gang scheduling에 어떻게 적용될지
- Copy/Inline 모델에서 PodGroup이 100개, 1000개 단위로 생성될 때 etcd 객체 수 증가가 실제 운영 환경에서 어떤 영향을 미치는지(개별 객체 크기는 약 1KB로 작지만, 총 객체 수 자체의 부하)
- Workload-Aware Preemption(KEP-5710)이 PodGroup 단위의 preemption을 어떻게 구현하는지, 특히 PodGroup 내 일부 Pod만 preempt되는 상황의 처리
