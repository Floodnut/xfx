# v1.37.2 Kubernetes 일관된 LIST의 캐시 지연을 429로 되돌리는 선택

- 프로젝트: Kubernetes, kube-apiserver watch cache
- 분석 버전: v1.37.2, 릴리스 공개일 2026-10-28
- 최초 도입: v1.37의 Alpha 기능 `ConsistentListFromCacheSkipTimeoutFallback`, 기본값 `false`

- 검증 리비전: `kubernetes/kubernetes`의 v1.37.2 커밋 [`c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32`](https://github.com/kubernetes/kubernetes/commit/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32)
- 발견 자료: [버전 고정 CHANGELOG의 v1.37.0 기능 목록](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/CHANGELOG/CHANGELOG-1.37.md)

## 개요

Kubernetes는 최신 상태를 요구하는 LIST도 watch cache가 충분히 따라잡았다면 메모리에서 처리한다. 기존에는 캐시가 제한 시간 안에 필요한 리비전에 도달하지 못하면 저장소에 LIST를 다시 요청했다. v1.37에서 추가되고 v1.37.2에서도 확인되는 `ConsistentListFromCacheSkipTimeoutFallback`은 이 특정 우회 경로를 끄고 HTTP 429와 재시도 정보를 반환하는 선택지다. 캐시 지연 시 요청 하나를 저장소에서 완결하는 대신, 추가 목록 조회를 억제하고 클라이언트가 나중에 재시도하도록 하는 설계다. 기본값은 꺼짐이며, 모든 저장소 접근을 차단하는 기능은 아니다.

## 사전 지식

### 캐시에서 읽는 것과 오래된 상태를 읽는 것은 별개의 선택

kube-apiserver의 저장소 경로에는 실제 저장소를 호출하는 구현과 watch 이벤트로 갱신되는 메모리 캐시가 있다. `CacheDelegator`는 LIST의 조건과 캐시 상태에 따라 두 경로 중 하나로 요청을 보낸다. 같은 객체 목록을 여러 클라이언트가 반복해서 읽을 때 캐시를 사용하면 객체 목록을 매번 저장소에서 가져오는 일을 줄일 수 있다.

그러나 캐시는 watch 이벤트를 받아야 갱신되므로, 저장소에 반영된 변경이 아직 캐시에 도달하지 않은 시점이 존재한다. 최신 상태를 요구하는 요청을 단순히 현재 캐시 내용으로 응답하면 요청한 읽기 의미를 만족하지 못할 수 있다. 그래서 일관된 읽기 경로의 `waitAndListConsistent`는 먼저 `getCurrentRV`로 저장소의 현재 **resourceVersion**을 얻고, 캐시가 그 리비전 이상에 도달할 때까지 기다린다. 이 함수는 `Storage.GetCurrentResourceVersion`에 연결되어 있다. 목록 본문을 캐시에서 읽더라도 신선도 기준을 얻는 저장소 호출은 남는다. [캐시 연결 코드](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/cacher.go), [신선도 확인 코드](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/watch_cache.go)

### 제한 시간이 지나면 누가 목록을 읽을 것인가

`waitUntilFreshLocked`는 캐시의 리비전이 목표보다 낮으면 조건 변수를 기다린다. 대기 중에는 watch 진행 알림을 요청하는 경로도 활성화한다. 캐시가 따라잡으면 목록을 읽고, `blockTimeout`인 3초가 지난 뒤에도 따라잡지 못했으면 `TooLargeResourceVersion` 오류를 반환한다. 타이머와 고루틴의 실행 시점이 개입하므로 정확히 3초에 응답한다는 보장은 아니다.

이 오류는 클라이언트가 잘못된 리비전을 보냈다는 뜻으로만 해석하면 안 된다. 일관된 LIST에서는 서버가 방금 얻은 저장소 리비전보다 캐시가 뒤처진 상황도 같은 오류로 표현한다. 기존 `CacheDelegator.GetList`는 이 경우 `storage.GetList`를 호출해 캐시를 우회했다. 캐시가 늦어도 저장소가 목록을 반환할 수 있다면 요청을 완료하려는 선택이었다. [기존 분기를 보여주는 실제 변경 diff](https://github.com/kubernetes/kubernetes/commit/7c7ae728f87f50e77181f4d0ffe42ad6908039de)

## 변경 분석

### 캐시 지연이 저장소 목록 조회로 이어지는 경로

기존 설계에서는 캐시가 지연될 때마다 해당 일관된 LIST가 저장소 LIST로 전환될 수 있었다. 개별 요청에는 복구 경로지만, 여러 요청이 같은 캐시 지연을 만나면 목록 조회가 저장소 쪽으로 이동한다. 이는 코드에서 도출되는 부하 경로이며, 이 보고서가 성능 측정으로 확인한 처리량 수치는 아니다.

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: request
    label: 캐시 대상 일관된 LIST
  - id: rv
    label: 저장소 현재 리비전 확인
  - id: wait
    label: 캐시가 목표 리비전까지 갱신되기를 대기
  - id: cache
    label: 캐시 목록 반환
  - id: fallback
    label: 저장소 GetList로 우회
edges:
  - from: request
    to: rv
  - from: rv
    to: wait
  - from: wait
    to: cache
    label: 신선도 충족
  - from: wait
    to: fallback
    label: 대기 시간 초과
```

변경은 `CacheDelegator.GetList`에서 두 조건이 모두 성립하는 지점에만 들어간다. 요청이 `result.ConsistentRead`로 분류되어 있고, 캐시 조회 오류가 `storage.IsTooLargeResourceVersion`에 해당해야 한다. 그 안에서 기능이 켜져 있으면 저장소 LIST 대신 `errors.NewTooManyRequests`를 반환한다. 재시도 지연 값은 기존 상수 `resourceVersionTooHighRetrySeconds`인 1초를 사용한다. 기능이 꺼져 있으면 기존 `storage.GetList` 호출을 유지한다. [v1.37.2의 최종 분기](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/delegator.go), [대기 및 재시도 상수](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/watch_cache.go)

따라서 새 경로는 캐시의 낡은 목록으로 성공 응답을 만드는 타협이 아니다. 필요한 신선도를 얻지 못했다는 사실을 오류로 전달한다. 대신 과거에 저장소 우회로 성공할 수 있었던 요청이 일시적인 실패 응답을 받는다. 클라이언트의 재시도가 언제 어떤 결과를 얻을지는 이 분기 자체가 보장하지 않는다.

### 테스트가 구분하는 목록 조회와 리비전 확인

병합 diff의 `TestConsistentReadFallback`에는 캐시 리비전 2, 저장소 리비전 42인 상태에서 새 기능을 켜는 사례가 추가되었다. 기대값은 `TooManyRequests`, 대기 발생, 저장소 요청 1회다. 저장소 요청이 0회가 아닌 것은 캐시 신선도를 판단할 리비전 조회가 여전히 필요하기 때문이다. 이 테스트는 저장소 목록 조회를 생략하는 것과 저장소를 전혀 호출하지 않는 것을 구분하는 근거다. 테스트 코드를 정적으로 확인했으며 실행하지 않았다. [추가된 테스트](https://github.com/kubernetes/kubernetes/blob/7c7ae728f87f50e77181f4d0ffe42ad6908039de/staging/src/k8s.io/apiserver/pkg/storage/cacher/cacher_whitebox_test.go)

관측값도 성공 여부와 우회 여부를 분리한다. 새 분기는 `apiserver_watch_cache_consistent_read_total`의 `fallback` 값을 `skipped`, `success` 값을 `false`로 기록한다. 기존 저장소 우회는 `fallback=true`를 사용한다. 따라서 기능을 켠 뒤의 실패와 기존 우회량을 같은 성공 카운터로 혼동하지 않고 살펴볼 수 있다. [카운터 갱신 코드](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/delegator.go)

## 설계 결정 및 트레이드오프

### 기존 복구 경로를 기본값으로 남긴 선택적 역압

기능 정의는 v1.37 Alpha, `Default: false`다. 기존 운영 환경의 LIST 실패 방식은 자동으로 바뀌지 않으며, 운영자가 기능을 켤 때 해당 지연을 클라이언트에 돌려주는 정책으로 전환한다. 여기서 역압은 늦어진 캐시를 저장소 목록 조회로 우회하는 대신 재시도 가능한 실패로 요청을 되돌린다는 의미다. [릴리스의 기능 정의](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/features/kube_features.go)

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: request
    label: 저장소 리비전 확인과 캐시 대기
  - id: fresh
    label: 캐시 목록 반환
  - id: gate
    label: 일관된 LIST 신선도 대기 시간 초과
  - id: retry
    label: HTTP 429와 1초 재시도 정보
  - id: storage
    label: 저장소 GetList로 우회
edges:
  - from: request
    to: fresh
    label: 신선도 충족
  - from: request
    to: gate
    label: TooLargeResourceVersion
  - from: gate
    to: retry
    label: 기능 켜짐
  - from: gate
    to: storage
    label: 기능 꺼짐, 기본값
```

실제 구현이 유지하는 두 정책의 교환관계는 다음과 같다.

- 기존 우회 유지: 저장소에서 요청을 완료할 기회와 캐시 지연 시 추가 목록 조회 부담
- 새 429 반환: 해당 저장소 목록 조회 억제와 클라이언트의 오류 처리, 재시도 부담
- Alpha 기본 꺼짐: 기존 동작 보존과 활성화 여부를 운영자가 판단하는 비용

이 비교는 분기의 동작을 분석한 것이며, 별도 설계 문서에 기록된 대안 검토 목록을 재현한 것은 아니다. 캐시 신선도 검증을 없애거나 오래된 결과를 허용하는 경로는 이 변경에 추가되지 않았다.

적용 범위도 제한적이다. `ShouldDelegateList`가 처음부터 저장소로 보내는 요청, 준비되지 않은 캐시에 대한 일부 제한된 LIST의 위임, `ListFromCacheSnapshot` 경로에서 만료된 리비전 때문에 발생하는 우회는 이 기능 분기 밖에 남는다. 따라서 이를 모든 LIST의 저장소 접근을 막는 보호 장치로 설명해서는 안 된다. 캐시가 따라잡지 못하는 원인을 해결하는 기능도 아니므로, 429 증가만으로 정상 복구를 판단할 수 없다. [위임 및 오류 분기의 전체 순서](https://github.com/kubernetes/kubernetes/blob/c50e5395f1ae2d4a2c05f28fdcc38c0916cc1a32/staging/src/k8s.io/apiserver/pkg/storage/cacher/delegator.go)

## 더 살펴볼 점

- 실제 클라이언트는 429와 재시도 정보를 받았을 때 어떤 대기 및 재시도 정책을 적용하는가?
- `fallback=skipped` 증가는 캐시 신선도 대기 시간과 저장소 목록 조회량에 어떤 관계가 있는가?
- 최초 저장소 위임 경로가 전체 LIST 부하에서 차지하는 비중은 어느 정도인가?
