## 개요

Kubernetes의 validating/mutating webhook과 CEL admission policy 구성은 원래 API 객체로만 존재했다.
그래서 kube-apiserver가 막 시작하는 구간에는 정책 객체를 아직 읽을 수 없고, API에 쓸 권한을 가진 주체가 API 기반 정책을 삭제하거나 바꾸는 일을 그 정책 자신으로 막을 수도 없었다.

v1.36은 `AdmissionConfiguration`에 `staticManifestsDir`를 추가해 호스트 파일의 정적 manifest를 두 번째 admission 구성 source로 도입했다.
API 기반 source는 동적 구성을 계속 제공하고, 정적 source는 API server 준비 전에 읽어 검증한다.
둘은 static-first 순서로 결합되므로 플랫폼 운영자가 파일로 둔 불변 정책이 API 객체 기반 정책보다 먼저 평가된다.

## 사전 지식

### admission control이 요청을 막는 위치

kube-apiserver는 인증과 인가를 마친 API 요청을 저장하기 전에 admission chain에 통과시킨다.
여기에는 외부 HTTPS endpoint를 호출하는 validating/mutating webhook과, API server 안에서 CEL 식을 평가하는 `ValidatingAdmissionPolicy`, `MutatingAdmissionPolicy`가 포함될 수 있다.

Webhook 구성과 policy, binding은 Kubernetes API 객체다.
API server의 admission plugin은 이 객체를 watch해 현재 구성을 동적으로 갱신하고, 그 결과로 각 요청에 적용할 hook과 policy를 찾는다.
이 방식은 평소에는 운영자가 API로 정책을 만들고 바꾸기 편하게 해준다.

그러나 policy를 읽는 source 자체가 API와 etcd에 의존한다는 뜻이기도 하다.
초기 부팅 때 API 객체를 아직 신뢰할 수 없는 시점, 또는 etcd를 읽는 경로에 문제가 난 시점에는 API 기반 정책만으로 먼저 들어오는 요청을 통제할 수 없다.

### bootstrap과 self-protection 공백

예를 들어 플랫폼 운영자가 namespace 생성 규칙을 반드시 적용하려고 webhook 하나를 API 객체로 등록했다고 하자.
그 webhook은 API server가 실행되고 API source가 그 객체를 동기화한 뒤에야 적용된다.
그 전에는 정책이 준비되지 않은 공백이 있다.

또 admissionregistration API 객체는 자신을 관리하는 API 요청에 webhook admission을 적용하지 않아 순환 의존을 피한다.
따라서 충분한 권한을 가진 주체가 중요 webhook 또는 policy 객체를 삭제하려 할 때, 그 객체에 의존하는 webhook으로는 자신의 삭제를 차단할 수 없다.
이는 권한 모델의 결함이 아니라 API 구성과 그 구성을 읽는 admission plugin의 순환을 끊기 위한 기존 구조의 한계다.

## 변경 분석

### 변경 전: API source 하나에 모인 구성과 초기화 공백

v1.35까지 admission 구성은 API source 하나에서 출발했다.
정책과 webhook을 만들고 수정할 수 있는 유연성은 있었지만, API 객체가 동기화되기 전에는 platform invariant를 강제할 독립된 경로가 없었다.

```
변경 전: API/etcd 기반 admission 구성

  kube-apiserver 시작
        │
        ├─ admission plugin 초기화
        │
        ├─ API source가 webhook/policy 객체 list/watch
        │       │
        │       └─ 동기화 전에는 적용할 구성 없음
        │
        ▼
  admission chain
        │
        ├─ 일반 API 요청: 동기화 후 API 객체의 policy 적용
        └─ admissionregistration 구성 변경: 순환 방지를 위해
            그 구성에 의존한 webhook으로 자기 보호 불가

  위험 구간
  - bootstrap 중 정책 적용 전 요청
  - API/etcd 의존이 깨졌을 때 구성 조회 실패
  - API 쓰기 권한자가 중요 API 기반 정책을 수정 또는 삭제
```

이 모델에서 API는 policy payload의 저장소이면서 source의 전달 경로다.
따라서 운영자가 API 밖에서 먼저 준비한 구성과, API로 유입되는 평상시의 동적 구성을 서로 다르게 취급할 수 없었다.

### 변경 후: static source와 API source를 결합

v1.36은 plugin별 `AdmissionConfiguration`에 절대 경로 `staticManifestsDir`를 둘 수 있게 했다.
기능 게이트를 켜면 kube-apiserver initializer가 validating/mutating webhook, validating/mutating policy plugin에 manifest loader factory를 전달한다.

Policy plugin과 webhook plugin은 초기화 도중 `LoadInitial()`을 먼저 호출한다.
정적 policy는 compile까지, webhook은 accessor selector 검증까지 성공해야 한다.
초기 manifest가 틀리면 plugin 초기화가 실패하므로, API server는 정책이 빠진 준비 상태로 뜨지 않는다.

```
변경 후: 정적 manifest와 API source의 이원화

  호스트의 staticManifestsDir                  Kubernetes API / etcd
        │                                             │
        ▼                                             ▼
  LoadInitial()                                 dynamic API source
  parse -> compile/validate                     list/watch
        │                                             │
        │  초기 manifest 오류                         │
        ├─ API server 시작 실패                        │
        │                                             │
        └──────────────┐                 ┌────────────┘
                       ▼                 ▼
             composite source (static-first)
                       │
                       ▼
                 admission chain
                       │
           static policy/webhook 먼저 평가

  정상 실행 중 reload
  변경 manifest -> parse/compile/validate 성공 -> atomic source 교체
                   실패                     -> 마지막 정상 source 유지
```

`composite_policy_source.go`와 `composite_webhook_source.go`는 static source를 API source보다 앞에 결합한다.
이는 API 객체 구성을 폐기하는 방식이 아니다.
API source는 그대로 동적 정책을 제공하고, 파일 source만 bootstrap과 self-protection에 필요한 별도 신뢰 경로를 제공한다.

정적 객체 이름에는 `.static.k8s.io` suffix가 필요하다.
`pkg/apis/admissionregistration/validation/static_suffix.go`는 REST API를 통해 같은 suffix 이름을 만드는 시도를 거부하거나 경고한다.
이 규칙 덕분에 API 객체가 static object의 이름을 선점해 source 경계를 흐리는 것을 막는다.

## 설계 결정 및 트레이드오프

### 정적 source를 API source의 대체물이 아니라 별도 신뢰 경로로 둠

정적 manifest는 API로 list나 watch할 수 없는 out-of-band 구성이다.
그 대가로 API/etcd가 아직 준비되지 않은 bootstrap 구간과 API 기반 self-protection 한계를 피할 수 있다.
운영자는 파일 배포와 호스트 접근 권한을 별도로 관리해야 하고, 일반 정책 운영의 API 친화성은 API source에 남겨둔다.

### 초기화에는 fail-closed, reload에는 last-known-good

초기 부팅은 유효한 정적 policy가 없으면 API server 자체를 시작시키지 않는 엄격한 방식이다.
반면 `manifest/source/source.go`의 reload 경로는 같은 content hash면 재적용하지 않고, parse, compile, validation에 실패하면 현재 source를 바꾸지 않는다.
기동 시에는 보호가 빠진 server를 피하고, 실행 중에는 파일의 일시적인 손상 때문에 이미 검증된 보호를 잃지 않는 선택이다.

### API 의존 기능을 정적 구성에서 제한

정적 policy는 `paramKind`와 `paramRef`를 사용할 수 없고, 정적 webhook도 service reference나 동적 credential 같은 API 의존 구성을 쓰지 않는다.
대신 URL과 정적 kubeconfig 계열 설정처럼 시작 시 이미 이용 가능한 정보만 쓴다.
표현력은 줄지만, API server가 API service와 network를 아직 제공하지 않는 시점에도 결정할 수 있다는 것이 이 설계의 목적이다.

### HA 동기화를 Kubernetes 내부 범위에서 제외

각 API server 인스턴스의 manifest 파일을 일치시키는 일은 이 기능이 하지 않는다.
configuration management가 replica에 같은 파일을 배포해야 한다.
잘못 배포하면 replica마다 admission 판단이 달라질 수 있지만, Kubernetes가 파일 분산과 conflict resolution까지 떠안지 않아 API source의 동기화 모델과 다른 책임을 명확히 유지한다.

```
변경 후의 책임 경계

  configuration management
        │ 정적 manifest를 각 API server에 배포
        ▼
  kube-apiserver
  ┌───────────────────────────────────────────────────────────┐
  │ static loader: bootstrap invariant, parse/compile 검증    │
  │ API source: 일반적인 동적 webhook/policy 구성            │
  │ composite: static-first 결합과 source 동기화              │
  │ admission chain: 결합된 hook/policy를 요청마다 평가       │
  └───────────────────────────────────────────────────────────┘
        │
        ▼
  저장 또는 거부되는 API 요청

  얻는 것: bootstrap 보호, API/etcd 독립성, API self-delete 방어
  감수하는 것: out-of-band 가시성, replica 파일 동기화 책임, 제한된 구성 표현력
```
