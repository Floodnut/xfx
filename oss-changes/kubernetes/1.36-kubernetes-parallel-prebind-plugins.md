## 개요

kube-scheduler의 binding cycle에서 PreBind 확장 지점의 플러그인들은 지금까지 항상 **순차로** 실행됐다.
PreBind는 볼륨 바인딩 완료 대기, DRA 디바이스 attach 대기처럼 API 호출과 폴링을 동반하는 무거운 단계이고, 두 플러그인이 모두 일할 게 있으면 binding cycle의 총 지연은 두 대기 시간의 **합**이 됐다.

v1.36은 `PreBindPlugin` 인터페이스의 `PreBindPreFlight` 메서드가 `*PreBindPreFlightResult`를 함께 반환하도록 바꾸고, 여기서 `AllowParallel: true`를 돌려준 연속된 플러그인들을 하나의 그룹으로 묶어 goroutine으로 동시에 실행한다.
in-tree PreBind 플러그인인 VolumeBinding과 DynamicResources는 둘 다 `AllowParallel: true`를 반환하므로, 기본 프로파일에서는 두 플러그인이 한 그룹으로 병렬 실행되고 총 지연이 두 대기 시간의 **최댓값**으로 줄어든다.

## 사전 지식

### 스케줄링 사이클과 바인딩 사이클

kube-scheduler는 Pod 하나를 처리할 때 두 단계를 거친다.

- **scheduling cycle**: 노드를 고르는 단계. PreFilter, Filter, PostFilter, PreScore, Score, Reserve, Permit 확장 지점이 여기 속한다. 스케줄러 캐시의 일관성을 위해 한 번에 하나의 Pod만 처리하는 직렬 구간
- **binding cycle**: 고른 노드에 실제로 붙이는 단계. WaitOnPermit, PreBind, Bind, PostBind가 여기 속한다

scheduling cycle이 끝나면 스케줄러는 그 결과를 캐시에 assume해두고, binding cycle은 goroutine으로 떼어내 비동기로 돌린다.

```go
// pkg/scheduler/schedule_one.go (v1.36.0)

	// bind the pod to its host asynchronously (we can do this b/c of the assumption step above).
	go sched.runBindingCycle(ctx, state, fwk, scheduleResult, assumedPodInfo, start, podsToActivate)
```

즉 **서로 다른 Pod의 binding cycle끼리는 이미 병렬**이다. 이번 변경이 건드리는 것은 그 아래, **하나의 Pod 안에서 여러 PreBind 플러그인이 도는 순서**다.

### PreBind가 오래 걸리는 이유

in-tree에서 PreBind를 구현하는 플러그인은 v1.36 기준 두 개뿐이다.

- **VolumeBinding**: assume해둔 PVC/PV 바인딩을 API로 실제 기록하고, PV 컨트롤러가 바인딩과 프로비저닝을 끝낼 때까지 기다린다. 주석이 직접 wait until the PV controller has completely finished the binding operation이라고 밝히고 있다
- **DynamicResources**: ResourceClaim을 Pod 앞으로 예약하고, binding condition이 붙은 디바이스라면 디바이스가 노드에 attach될 때까지 5초 간격으로 폴링한다. 기본 타임아웃은 `DynamicResourcesBindingTimeoutDefault = 600 * time.Second`

```go
// pkg/scheduler/framework/plugins/dynamicresources/dynamicresources.go (v1.36.0)

	// We need to wait for the device to be attached to the node.
	pl.fh.EventRecorder()...Eventf(pod, nil, v1.EventTypeNormal, "BindingConditionsPending", ...)
	start := time.Now()
	err = wait.PollUntilContextTimeout(ctx, 5*time.Second, pl.bindingTimeout, true,
		func(ctx context.Context) (bool, error) {
			return pl.isPodReadyForBinding(state)
		})
```

둘 다 CPU를 쓰는 계산이 아니라 **외부 상태가 준비되기를 기다리는 블로킹 구간**이다. 순차 실행에서는 한쪽이 기다리는 동안 다른 쪽은 아예 시작조차 하지 않는다.

### PreBindPreFlight은 원래 무엇이었나

`PreBindPreFlight`은 이번 변경이 만든 훅이 아니다. v1.34의 KEP-5278(NominatedNodeName for expectation)이 도입했고, 목적은 다음 질문에 **가볍게** 답하는 것이었다.

> 이 Pod, 이 노드에 대해 이 PreBind 플러그인이 실제로 할 일이 있는가?

스케줄러는 그 답을 이렇게 썼다.

- 모든 PreBind 플러그인이 Skip을 반환하면 곧 바인딩되므로 아무것도 하지 않는다
- 하나라도 Success를 반환하면(= 실제로 일할 게 있으면) Pod의 `status.nominatedNodeName`을 미리 채워, cluster autoscaler 같은 외부 컴포넌트에 이 Pod가 이 노드로 갈 예정임을 알린다

```go
// pkg/scheduler/schedule_one.go (v1.36.0) bindingCycle

	var preFlightStatus *fwk.Status
	if sched.nominatedNodeNameForExpectationEnabled {
		preFlightStatus = schedFramework.RunPreBindPreFlights(ctx, state, assumedPod, scheduleResult.SuggestedHost)
		...
	}
```

`RunPreBindPreFlights`는 각 플러그인의 판정을 모아 CycleState의 `skipPreBindPlugins` 집합에 저장했고, 이후 `RunPreBindPlugins`는 그 집합에 든 플러그인을 건너뛰었다.
정리하면 v1.35 시점에 이미 **PreBind 직전에 모든 PreBind 플러그인에게 가볍게 물어보는 자리**가 마련되어 있었고, 다만 그 자리에서 얻는 정보는 skip 여부 하나뿐이었다.

## 변경 분석

### 순차 실행이 만든 지연: 합이 되는 대기 시간

v1.35까지의 `RunPreBindPlugins`는 단순한 for 루프였다.

```go
// 변경 전 pkg/scheduler/framework/runtime/framework.go

	for _, pl := range f.preBindPlugins {
		if state.GetSkipPreBindPlugins().Has(pl.Name()) {
			continue
		}
		...
		status = f.runPreBindPlugin(ctx, pl, state, pod, nodeName)
		if !status.IsSuccess() {
			if status.IsRejected() { ... return status }
			return fwk.AsStatus(...)
		}
	}
	return nil
```

문제는 이 루프가 도는 대상이 CPU 작업이 아니라 대기라는 점이다. PVC와 DRA 클레임을 함께 쓰는 Pod, 예를 들어 GPU 디바이스를 DRA로 받으면서 데이터셋을 담은 PV도 붙이는 학습 Pod가 정확히 이 경우에 해당한다.
VolumeBinding이 PV 컨트롤러를 기다리는 동안 DynamicResources는 아직 첫 API 호출도 하지 않았고, DynamicResources가 디바이스 attach를 기다리기 시작하는 시점은 VolumeBinding이 완전히 끝난 뒤다.

```
변경 전: PreBind 확장 지점 (v1.35)

  scheduling cycle (직렬)
        │  노드 선정 + assume
        ▼
  ┌─────────────────────────────────────────────────────────────┐
  │ binding cycle (Pod마다 goroutine, Pod 간에는 이미 병렬)      │
  │                                                             │
  │  RunPreBindPreFlights                                       │
  │    ├─ VolumeBinding.PreBindPreFlight   -> Success/Skip      │
  │    └─ DynamicResources.PreBindPreFlight -> Success/Skip     │
  │         └── 결과: skipPreBindPlugins 집합 하나만 저장       │
  │                                                             │
  │  RunPreBindPlugins  (for 루프, 한 번에 하나)                │
  │                                                             │
  │    t=0s   ┌──────────────────────────┐                      │
  │           │ VolumeBinding.PreBind    │ PV 컨트롤러 대기     │
  │    t=T1   └──────────────────────────┘                      │
  │                                       (이때까지 DRA는 대기) │
  │    t=T1   ┌──────────────────────────┐                      │
  │           │ DynamicResources.PreBind │ 디바이스 attach 대기 │
  │    t=T1+T2└──────────────────────────┘                      │
  │                                                             │
  │  총 PreBind 지연 = T1 + T2                                  │
  │                                                             │
  │  Bind -> PostBind                                           │
  └─────────────────────────────────────────────────────────────┘
```

두 대기가 서로 아무 인과관계도 없다는 점이 핵심이다. PV 바인딩 결과가 디바이스 attach의 입력이 되는 것도 아니고, 그 반대도 아니다. 순서를 지켜야 할 이유가 없는데도 프레임워크가 순서를 강제하고 있었던 셈이다.

한편 프레임워크는 이미 다른 확장 지점에서 병렬 실행을 쓰고 있었다. Filter와 Score는 `Parallelizer().Until`로 노드들을 나눠 처리한다.

```go
// pkg/scheduler/framework/parallelize/parallelism.go (v1.36.0)

// DefaultParallelism is the default parallelism used in scheduler.
const DefaultParallelism int = 16
```

다만 그 병렬화는 **하나의 플러그인을 여러 노드에 대해** 돌리는 것이지, **여러 플러그인을 동시에** 돌리는 것은 아니었다. PreBind는 노드가 이미 하나로 정해진 뒤라 노드 단위로 쪼갤 게 없고, 쪼갤 수 있는 축은 플러그인뿐이다.

### 무엇이 바뀌었나: PreBindPreFlight이 병렬 가능 여부까지 답한다

PR #135393은 이미 존재하던 preflight 질문에 항목 하나를 더 얹는 방식을 택했다. 인터페이스 변경은 다음과 같다.

```go
// staging/src/k8s.io/kube-scheduler/framework/interface.go (v1.36.0)

// PreBindPreFlightResult wraps needed info for scheduler framework to act upon PreBindPreFlight phase.
type PreBindPreFlightResult struct {
	// AllowParallel indicates whether this plugin's PreBind method can be run
	// in parallel with other plugins during PreBind phase.
	// The scheduler groups consecutive plugins that return AllowParallel: true
	// and runs them in parallel.
	// A plugin that returns AllowParallel: false breaks the parallel group
	// and runs sequentially.
	// Note: skipped plugins are effectively ignored, but if a skipped plugin returns
	// AllowParallel: false, it still breaks the parallel group of adjacent plugins.
	AllowParallel bool
}

type PreBindPlugin interface {
	Plugin
	PreBindPreFlight(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) (*PreBindPreFlightResult, *Status)
	PreBind(ctx context.Context, state CycleState, p *v1.Pod, nodeName string) *Status
}
```

`RunPreBindPreFlights`는 이제 skip 집합과 병렬 허용 집합을 **둘 다** 모아 CycleState에 넣는다. CycleState에는 `parallelPreBindPlugins` 필드와 getter/setter가 추가됐다.

```go
// pkg/scheduler/framework/runtime/framework.go (v1.36.0)

		result, status := f.runPreBindPreFlight(ctx, pl, state, pod, nodeName)
		if result != nil && result.AllowParallel {
			parallelPlugins.Insert(pl.Name())
		}
		...
	state.SetSkipPreBindPlugins(skipPlugins)
	state.SetParallelPreBindPlugins(parallelPlugins)
```

실행 쪽에서는 플러그인 목록을 먼저 그룹으로 쪼갠다.

```go
// pkg/scheduler/framework/runtime/framework.go:1681 (v1.36.0)

func (f *frameworkImpl) getPreBindPluginGroups(state fwk.CycleState, skippedPlugins, parallelPlugins sets.Set[string]) [][]fwk.PreBindPlugin {
	var groups [][]fwk.PreBindPlugin
	var group []fwk.PreBindPlugin
	for _, pl := range f.preBindPlugins {
		if parallelPlugins.Has(pl.Name()) {
			if !skippedPlugins.Has(pl.Name()) {
				group = append(group, pl)
			}
			continue
		}
		if len(group) > 0 {
			groups = append(groups, group)
			group = nil
		}
		if !skippedPlugins.Has(pl.Name()) {
			groups = append(groups, []fwk.PreBindPlugin{pl})
		}
	}
	if len(group) > 0 {
		groups = append(groups, group)
	}
	return groups
}
```

규칙을 말로 풀면 이렇다.

- 병렬 허용 플러그인이 연속으로 나오면 하나의 그룹으로 누적
- 병렬 불가 플러그인을 만나면 누적 중이던 그룹을 확정하고, 그 플러그인은 원소 1개짜리 그룹으로 따로 배치
- skip된 플러그인은 그룹에 넣지 않지만, **병렬 불가로 판정된 skip 플러그인은 여전히 그룹을 끊는다**

마지막 항목은 주석에 명시된 의도된 동작이다. skip 여부와 병렬 허용 여부가 서로 독립된 두 축이라 생기는 결과이며, 순서 의미를 보수적으로 지키는 쪽을 택한 것이다.

그리고 그룹 단위로 실행한다.

```go
// pkg/scheduler/framework/runtime/framework.go:1611 (v1.36.0) RunPreBindPlugins

	pluginGroups := f.getPreBindPluginGroups(state, skippedPlugins, parallelPlugins)
	for _, plugins := range pluginGroups {
		// If there is just a single plugin in the group, running it in a separate goroutine
		// does not provide any benefit.
		if len(plugins) == 1 {
			if status := run(plugins[0]); status != nil {
				return status
			}
			continue
		}
		f.Parallelizer().Until(ctx, len(plugins), func(index int) {
			if status := run(plugins[index]); !status.IsSuccess() {
				statusCh.SendWithCancel(status, func() {
					cancel(errors.New("some other PreBind operation failed"))
				})
			}
		}, metrics.PreBind)
		if status := statusCh.Receive(); !status.IsSuccess() {
			return status
		}
	}
```

기존 `parallelize.ErrorChannel`은 `error` 하나만 실어 나를 수 있었는데, PreBind는 Rejected/Error를 구분하는 `*fwk.Status`를 그대로 전달해야 한다. 그래서 같은 PR이 `ErrorChannel`을 제네릭 `ResultChannel[T comparable]`로 일반화하고, 기존 호출부(Score, Filter, preemption)를 `NewResultChannel[error]()`로 옮겼다.

```go
// pkg/scheduler/framework/parallelize/result_channel.go (v1.36.0)

type ResultChannel[T comparable] struct {
	ch chan T
}
```

용량 1짜리 채널이라 **가장 먼저 실패한 하나만 남고 나머지는 버려지는** 성질은 그대로다. 실패가 채널에 들어가는 순간 `cancel`이 불려 같은 그룹의 다른 PreBind는 ctx 취소로 조기 종료한다.

기본 프로파일에서 실제로 만들어지는 그룹은 하나다. `getDefaultPlugins()`의 MultiPoint 순서에서 VolumeBinding과 DynamicResources 사이에 있는 VolumeZone, PodTopologySpread, InterPodAffinity는 PreBind를 구현하지 않으므로, `f.preBindPlugins` 슬라이스에는 `[VolumeBinding, DynamicResources]`만 연속으로 남고 둘 다 `AllowParallel: true`이기 때문이다.

## 설계 결정 및 트레이드오프

```
변경 후: PreBind 확장 지점 (v1.36)

  RunPreBindPreFlights (NominatedNodeNameForExpectation 게이트, 기본 on)
    ├─ VolumeBinding.PreBindPreFlight    -> (AllowParallel:true, Success)
    └─ DynamicResources.PreBindPreFlight -> (AllowParallel:true, Success)
         │
         ├──> CycleState.skipPreBindPlugins     = {}
         └──> CycleState.parallelPreBindPlugins = {VolumeBinding, DynamicResources}
                        │
                        ▼
  getPreBindPluginGroups  (연속된 병렬 허용 플러그인을 묶음)

    f.preBindPlugins = [ VolumeBinding , DynamicResources ]
                          병렬 허용        병렬 허용
                        └────────── group 0 ──────────┘

  RunPreBindPlugins  (그룹 단위 순차, 그룹 내부는 Parallelizer().Until)

    ┌ group 0 ──────────────────────────────────────────┐
    │  t=0s ┌──────────────────────────┐                │
    │       │ VolumeBinding.PreBind    │ T1             │
    │       └──────────────────────────┘                │
    │  t=0s ┌──────────────────────────┐                │
    │       │ DynamicResources.PreBind │ T2             │
    │       └──────────────────────────┘                │
    │                                                   │
    │  둘 중 하나 실패 -> statusCh(용량 1)에 첫 상태만  │
    │                     저장 + cancel(ctx)로 나머지    │
    │                     조기 종료                      │
    └───────────────────────────────────────────────────┘

    총 PreBind 지연 = max(T1, T2)

  (병렬 불가 플러그인 P가 중간에 끼면 그룹이 끊긴다)
    [ A(병렬) , P(불가) , B(병렬) , C(병렬) ]
      └group0┘  └group1┘  └───group2────┘
      그룹 사이 순서는 유지, 그룹 내부만 동시 실행
```

### 새 확장 지점이 아니라 기존 preflight 훅을 재사용

플러그인의 병렬 가능 여부를 알아내는 방법은 여러 가지가 있었다.

- 플러그인 등록 시점의 정적 선언, 예를 들어 새 marker 인터페이스나 KubeSchedulerConfiguration 필드
- PreBind와 별개의 새 확장 지점 추가
- 이미 PreBind 직전에 호출되는 `PreBindPreFlight`의 반환값 확장

세 번째가 채택됐다. 이유는 두 가지로 읽힌다.

- **판정이 Pod/노드마다 달라질 수 있다**: 같은 플러그인이라도 어떤 Pod에서는 병렬로 돌려도 안전하고 어떤 Pod에서는 아닐 수 있다. 정적 선언으로는 이 구분을 표현할 수 없다
- **호출 비용이 이미 지불되어 있다**: `PreBindPreFlight`은 lightweight해야 한다고 인터페이스 주석에 명시된, 실제 작업을 하지 않는 값싼 훅이다. 여기에 필드 하나를 얹는 데 드는 추가 비용은 사실상 없다

대가는 결합이다. `PreBindPreFlight` 호출은 `NominatedNodeNameForExpectation` 게이트 안에 들어 있어서, 이 게이트를 끄면 `parallelPreBindPlugins`가 비어 있는 채로 남고 모든 플러그인이 원소 1개짜리 그룹이 되어 완전히 순차 실행된다. 병렬화라는 성능 최적화가 표면적으로 무관해 보이는 NominatedNodeName 기능의 게이트에 종속되는 셈이다.

### 전체 병렬이 아니라 연속 그룹 병렬

`AllowParallel: true`인 플러그인을 위치와 무관하게 전부 한 번에 돌리는 선택지도 있었지만, 그렇게 하면 사이에 낀 순차 플러그인과의 상대 순서가 깨진다.
연속 그룹 방식은 다음 성질을 유지한다.

- 그룹 사이의 실행 순서는 설정된 플러그인 순서 그대로
- 순차 플러그인은 자기 앞 그룹이 전부 끝난 뒤에 시작하고, 자기 뒤 그룹은 자기가 끝난 뒤에 시작

즉 순차 플러그인 하나가 있으면 그 지점이 그대로 배리어 역할을 한다. 최적 병렬도를 포기하는 대신, 기존 설정이 암묵적으로 기대하던 순서 의미를 깨지 않는 보수적인 선택이다.

### nil 반환을 순차로 해석하는 하위 호환

시그니처가 `*Status`에서 `(*PreBindPreFlightResult, *Status)`로 바뀌었기 때문에 out-of-tree PreBind 플러그인은 **반드시 코드를 고쳐야 컴파일된다**. 릴리스 노트에 ACTION REQUIRED가 붙은 이유다.

다만 의미론적으로는 안전한 기본값을 골랐다.

- 첫 번째 반환값으로 `nil`을 주면 모든 필드가 zero value인 결과로 취급, 즉 `AllowParallel: false`
- 결과적으로 시그니처만 맞춰 놓고 `nil`을 반환하면 기존과 동일한 순차 동작

컴파일은 깨지지만 런타임 동작은 opt-in 전까지 바뀌지 않는다. 병렬 실행이 안전한지 판단할 수 있는 주체는 플러그인 작성자뿐이므로, 프레임워크가 기본값을 true로 밀어붙이지 않은 것은 타당하다.

메서드를 하나 더 추가해 기존 시그니처를 보존하는 대안도 가능했지만, `PreBindPlugin` 인터페이스에 세 번째 메서드가 생기고 preflight와 병렬 판정을 위해 같은 플러그인을 두 번 호출해야 한다. 컴파일 에러는 눈에 띄고 한 번에 고칠 수 있는 종류의 비용이라 이쪽을 감수한 것으로 보인다.

### 그룹 크기 1에 대한 단축 경로

`len(plugins) == 1`이면 goroutine을 띄우지 않고 직접 호출한다. 주석이 이유를 명시한다.

```go
		// If there is just a single plugin in the group, running it in a separate goroutine
		// does not provide any benefit.
```

in-tree PreBind 플러그인이 두 개뿐이고 그중 하나가 skip되는 경우가 흔하다는 점을 생각하면, 이 단축 경로가 실제로는 가장 자주 타는 경로다. 병렬화 도입으로 인한 오버헤드를 일반적인 케이스에서 0으로 유지한다.

### 실패 처리에서 감수한 것

병렬화가 바꾼 실패 의미론은 세 가지다.

- **보고되는 상태가 결정적이지 않다**: 그룹 내 여러 플러그인이 동시에 실패하면 채널에 먼저 도착한 하나만 남는다. 순차 실행에서는 항상 앞선 플러그인의 실패가 보고됐다
- **취소된 플러그인이 중간 상태를 남길 수 있다**: 한쪽이 실패하면 `cancel`로 나머지의 ctx가 끊기는데, 그 시점에 이미 API 호출이 나갔을 수 있다. 이 뒷정리는 binding cycle 실패 경로가 `unreserveAndForget`으로 Unreserve 플러그인을 호출해 처리하는, 병렬화 이전부터 있던 메커니즘에 그대로 의존한다
- **goroutine 회계가 달라진다**: `Parallelizer().Until`이 `metrics.PreBind` 라벨로 `scheduler_goroutines`를 증감시키므로, 이 지표를 보던 대시보드에는 없던 계열이 나타난다

첫 번째와 두 번째는 원래 순차 실행에서도 후행 플러그인 실패 시 선행 플러그인의 작업을 Unreserve로 되돌려야 했던 것과 성격이 같다. 병렬화는 그 창을 넓힐 뿐 새로운 종류의 문제를 만들지는 않는다.

## 더 살펴볼 점

- 그룹 병렬 실행 중 실패로 ctx가 취소된 DynamicResources.PreBind가 이미 예약을 기록한 ResourceClaim은 Unreserve 경로에서 항상 되돌려지는가, 아니면 다음 스케줄링 시도까지 남는 창이 있는가?
- `NominatedNodeNameForExpectation` 게이트를 끈 클러스터는 v1.36에서도 PreBind가 전부 순차로 도는데, 이 종속을 끊고 병렬화를 독립적으로 켤 계획이 있는가?
- in-tree PreBind 플러그인이 둘뿐인 지금 이 변경의 실측 이득은 PVC와 DRA 클레임을 동시에 쓰는 Pod에 한정되는데, 그 비율이 실제로 최적화를 정당화할 만큼인지 측정한 자료가 있는가?
