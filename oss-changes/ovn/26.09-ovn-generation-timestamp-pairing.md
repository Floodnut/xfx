## 개요

OVN 26.09는 설정 세대 번호 `nb_cfg`와 그 세대를 처리하기 시작한 northd의 시각을 함께 Southbound DB에 전달하고, 각 호스트에서 OpenFlow 적용 완료가 확인될 때까지 두 값을 결합해 보존한다. 이로써 호스트별 완료 상태를 중앙 DB에 다시 쓰는 기능을 꺼도, 로컬 OVS DB에서 시작 시각과 완료 보고 시각을 함께 읽을 수 있다. 핵심은 timestamp 필드 추가보다 **비동기 적용 중 세대가 바뀌어도 완료된 세대의 시작 시각을 잃지 않는 것**이다.

## 사전 지식

### 설정 DB와 실제 패킷 처리 사이의 간격

OVN에서는 관리 시스템이 Northbound DB에 논리 스위치, 라우터, 정책을 기록한다. `ovn-northd`는 이를 Southbound DB의 논리 흐름으로 변환하고, 각 호스트의 `ovn-controller`는 자신에게 필요한 흐름을 OVS에 설치한다. DB에 원하는 설정을 기록한 순간과 실제 호스트가 그 설정을 적용한 순간은 다르다.

이 차이를 추적하는 표지가 `nb_cfg`다. northd는 NB의 세대 번호를 SB로 옮기고, controller는 흐름 적용 완료를 확인한 세대를 보고한다. 변경 전 controller의 `store_nb_cfg()`는 완료된 번호와 로컬 시각을 `Chassis_Private`에 쓰고, 로컬 OVS의 `Bridge.external_ids`에도 `ovn-nb-cfg`와 `ovn-nb-cfg-ts`를 남겼다. 중앙 보고 경로에는 `enable_chassis_nb_cfg_update` 조건이 붙지만 로컬 기록 경로에는 이 조건이 없다. [변경 전 controller](https://github.com/ovn-org/ovn/blob/5a72b763166e87a6452ac03254d9a9036ae9fc5f/controller/ovn-controller.c)

### 완료 확인에는 세대의 입력 정보도 필요

controller가 새로운 SB 상태를 읽은 뒤 OVS의 완료 응답을 받기까지 다른 설정 세대가 도착할 수 있다. `ofctrl-seqno`는 애플리케이션의 설정 번호와 흐름 처리 번호를 연결해, 어떤 설정의 적용이 확인되었는지 돌려주는 계층이다. 기존에는 설정 번호만 보존했으므로 로컬 완료 시각은 알 수 있어도 그 세대에 대응하는 northd 시각은 로컬에서 얻을 수 없었다. [변경 diff의 lib/ofctrl-seqno.c](https://github.com/ovn-org/ovn/commit/8b572fe84011311245690fe4277c4c63b0a769ed)

호스트 수가 많으면 각 세대마다 호스트들이 `Chassis_Private`를 갱신하는 작업이 중앙 SB DB에 집중된다. 변경 커밋은 이 쓰기 부하 때문에 완료 보고를 비활성화하는 운영을 직접 동기로 제시한다. 따라서 기존 중앙 보고를 더 자주 수집하는 방식보다, 이미 내려가는 설정에 관측 정보를 실어 보내는 방식이 필요했다.

## 변경 분석

### 변경 전: 완료 시각은 로컬에 있지만 시작 시각은 다른 곳에 존재

```diagram
type: flow
title: 변경 전
direction: down
nodes:
  - id: northd
    label: northd가 NB에 시작 시각 기록
  - id: sb
    label: SB에는 설정 세대만 전달
  - id: controller
    label: controller가 흐름 적용 완료 확인
  - id: local
    label: 로컬 OVS에 세대와 완료 시각 기록
  - id: central
    label: 조건부 Chassis_Private 완료 보고
edges:
  - from: northd
    to: sb
  - from: sb
    to: controller
  - from: controller
    to: local
  - from: controller
    to: central
```

중앙 완료 보고를 끄면 `Chassis_Private` 값은 갱신되지 않는다. 로컬 완료 기록 자체는 계속되지만, 시작 시각이 없는 상태에서는 로컬 두 필드만으로 해당 세대의 전파 시간을 계산할 수 없다. 이는 관측값의 위치 문제다. 이번 변경은 이 간격을 SB의 새 필드와 로컬 기록으로 연결한다.

### 세대와 시각을 동일한 SB 트랜잭션에 기록

`update_sequence_numbers()`는 NB와 SB의 `nb_cfg`가 다를 때, 기존 세대 설정과 함께 `SB_Global.nb_cfg_timestamp`를 `loop_start_time`으로 설정한다. 두 필드는 동일한 SB 트랜잭션에 들어간다. 이 시각은 northd가 엔진 실행 전에 `time_wall_msec()`로 읽은 값이다. 따라서 **클라이언트의 NB 커밋 시각이나 SB 트랜잭션의 실제 커밋 완료 시각과 동일하다고 해석하면 안 된다**. 이 구현으로 측정하는 구간의 시작은 해당 northd 처리 회차의 시작이다. [릴리스 northd 구현](https://github.com/ovn-org/ovn/blob/da7afdb1bffa5ff752f2e8ae50ffd7aecd2907f3/northd/ovn-northd.c)

controller의 `get_nb_cfg()`도 번호 하나 대신 `(nb_cfg, ts)` 스냅샷을 반환한다. SB 모니터 조건 변경에 대한 응답을 기다리는 동안에는 이전 스냅샷 전체를 유지한다. 번호만 새로운 값으로 바꾸거나 시각만 별도로 갱신하지 않아, 서로 다른 관측 상태에서 얻은 값을 결합하는 것을 피한다. [릴리스 get_nb_cfg()](https://github.com/ovn-org/ovn/blob/da7afdb1bffa5ff752f2e8ae50ffd7aecd2907f3/controller/ovn-controller.c)

### 완료 응답까지 시작 시각을 함께 운반

controller는 `ofctrl_stamped_seqno_update_create()`에 세대와 시각을 함께 전달한다. 큐 항목의 `req_ts`가 완료 처리 시 `cur_cfg_req_ts`로 옮겨지고, 소비자는 `last_acked`와 `last_acked_req_ts`를 함께 받는다. 기존 timestamp 없는 API는 새 API에 0을 전달하는 래퍼로 유지된다. [릴리스 ofctrl-seqno 구현](https://github.com/ovn-org/ovn/blob/da7afdb1bffa5ff752f2e8ae50ffd7aecd2907f3/lib/ofctrl-seqno.c)

예를 들어 세대 100을 적용하는 동안 SB가 101로 앞서가더라도, 100의 완료 기록에는 큐에 보존한 100의 시작 시각을 사용한다. 완료 시점에 최신 SB timestamp를 다시 읽었다면 101의 늦은 시작 시각을 빼게 되어 100의 지연을 과소평가할 수 있다. 이 예시는 커밋이 설명하는 비동기 세대 혼합 문제를 풀어 쓴 것이다.

`store_nb_cfg()`는 로컬에 기록된 세대가 완료된 세대와 다르고 OVS 트랜잭션과 브리지가 존재할 때, 번호와 완료 보고 시각에 더해 `ovn-nb-cfg-sb-ts`를 쓴다. 전달된 시작 시각이 0이면 기존 키를 제거한다. 이 로컬 경로는 중앙 완료 보고 옵션과 독립적이다. 도입 테스트도 옵션을 끈 상태에서 로컬 세대와 timestamp가 전진하고 `Chassis_Private.nb_cfg`는 이전 값에 머무는 것을 검사한다. 테스트를 실행한 결과가 아니라 테스트 코드가 표현하는 검증 의도다. [구현 및 테스트 diff](https://github.com/ovn-org/ovn/commit/8b572fe84011311245690fe4277c4c63b0a769ed)

## 설계 결정 및 트레이드오프

### 변경 후: 중앙 쓰기 대신 로컬에서 결합된 관측값 제공

```diagram
type: flow
title: 변경 후
direction: down
nodes:
  - id: northd
    label: northd 처리 회차 시작 시각
  - id: sb
    label: SB에 세대와 시작 시각 동시 기록
  - id: snapshot
    label: controller가 두 값 함께 읽기
  - id: queue
    label: ofctrl 큐에 세대와 req_ts 보존
  - id: ack
    label: 완료된 세대와 원래 시각 반환
  - id: local
    label: 로컬 OVS에 세 필드 기록
  - id: collector
    label: 수집기가 같은 세대의 시각 차이 계산
edges:
  - from: northd
    to: sb
  - from: sb
    to: snapshot
  - from: snapshot
    to: queue
  - from: queue
    to: ack
  - from: ack
    to: local
  - from: local
    to: collector
```

커밋이 제시한 선택은 SB를 통해 시각을 내려보내는 것이다. 호스트는 이미 SB를 구독하므로 수집기가 NB에 별도로 연결할 필요가 없고, 중간 relay를 거쳐 도달하는 시간도 관측 구간에 들어간다. 그 대신 세대 처리 큐까지 timestamp 전달 책임을 확장한다. [변경 동기 및 구현](https://github.com/ovn-org/ovn/commit/8b572fe84011311245690fe4277c4c63b0a769ed)

- 중앙 완료 보고 유지: 기존 `Chassis_Private` 기반 관측을 유지하지만 호스트별 SB 쓰기 부담도 유지
- 완료 시 최신 SB 시각 조회: 큐 확장을 피하지만 비동기 세대 혼합에 따른 지연 오계산 가능성
- 선택된 방식: SB에 시작 시각 추가, 요청 큐에서 해당 세대와 결합, 로컬 OVS에서 완료값 제공

코드에서 도출되는 운영 한계도 있다. 두 timestamp는 서로 다른 호스트의 wall clock에서 생성되므로 정확한 차이 계산에는 시계 정렬이 필요하다. 또한 로컬 필드는 최신 완료 세대의 상태이며 모든 중간 세대를 영구 보관하는 이벤트 로그가 아니다. 수집 주기 사이에 여러 세대가 완료되면 관측하지 못하는 세대가 생길 수 있다. 중앙 SB 쓰기를 줄이는 효과를 전체 관측 비용이 호스트 수와 무관하다는 뜻으로 넓혀서는 안 된다. 로컬 DB 기록과 외부 수집 비용은 남는다. [릴리스 controller와 seqno 구현](https://github.com/ovn-org/ovn/blob/da7afdb1bffa5ff752f2e8ae50ffd7aecd2907f3/controller/ovn-controller.c)

릴리스의 [controller 매뉴얼](https://github.com/ovn-org/ovn/blob/da7afdb1bffa5ff752f2e8ae50ffd7aecd2907f3/controller/ovn-controller.8.xml)은 timestamp가 없는 예로 `enable_chassis_nb_cfg_update=false`를 들지만, 같은 릴리스의 실제 로컬 기록 분기와 도입 테스트는 반대 동작을 보여 준다. 이 보고서는 구현과 테스트를 기준으로 옵션과 로컬 기록의 독립성을 설명한다. 옵션을 껐다는 이유만으로 새 키가 없어야 한다고 판단하면 안 된다.
